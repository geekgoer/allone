# 迁移了什么、真实控制如何执行

## 没有改变的部分

沿用原SD镜像、Linux5.4/PetaLinux2020.1、DPU硬件/驱动、DNNDK动态库和冻结release001的18个ELF。没有重新训练、重新量化、改归一化或增加输入裁剪；输入比例仍由实际getter读取，原失败向量仍status3拒绝。也没有用MPC教师、CPU DNN或分段DNN替代真实DPU。

原快照及补充统一包保持只读；`source_proof_001.json`核对2613+1878文件，并证明所用模型入口、冻结场景、校准及数值fixture对应一致。补充包仅用于原包缺失的native_io和线协议契约，不重新选模型/轨迹。

## 一条请求的真实路径

1. 独立发布器依据PS单调时钟的绝对日历到期释放，不在请求完成后sleep一个周期。每机只允许一个在途槽；忙、过期、计划跳过仍记录。
2. 该机worker用自己的RPC连接依次读取状态和碰撞信息；记录开始、返回及AirSim模拟时间。PS时间与模拟时间不相减。
3. 根据相同冻结轨迹、参考偏移1.5s和当前采样时间，生成21个参考点，分析已实际下发的held control能条件保持多久，构造RAW237。数值部分有短共享PS锁。
4. `queued()`冻结实际期限：周期、保持、新鲜度80ms、欠补更期限取最小值。特征仍是未经归一化的237个float。
5. 唯一DPU executor通过`take()`拿当前真实顺序和模型ID；原Pool只做一次归一化和237→240补齐，保留越界检查，调用真实`dpuRunTask()`。已有硬件调用不可被软件超时抢占。
6. 真实返回后先`dpu_done()`，再唤醒worker。失败/量程拒绝不下发命令；提交前再次检查期限和返回处理预算。
7. `command_begin()`在日历锁内立即使旧保持观测失效，防止RPC在途时规划器利用旧控制证据提交。原生RPC直接发送物理wx/wy/wz和校准throttle；不重复Python pitch/yaw翻转。
8. 收到同连接ping返回代理后才`command_return()`更新held版本，即使晚到也如实更新。再读一个新状态与新held control重新配对分析，最后`finish()`释放该机在途所有权。未确认的RPC发送保留“不确定”，不伪称没发出。

后台planner与定时发布/阻塞RPC/DPU/日志线程分离。规划时使用同一锁下的时钟和状态快照，搜索在锁外，提交锁内重读时间并核对revision/control版本，整组安装或整组拒绝。每次规划后留10ms服务间隔；该后台间隔不等于硬实时10ms规划周期。

## 跳过不是丢包，也不是自动成功

默认关闭。仅实验允许、当前新鲜状态与held版本一致、小误差/低参考速度变化、保持预算覆盖且无既有欠账时才有资格。正式策略仍按原启发式先尝试正常模型/顺序/释放修复，不能为“漂亮结果”强制跳过。

跳过撤回一个未发布的槽；紧邻的**原本就存在**的后继周期承担补更，不虚构额外请求。后继必须走真实DPU及实际命令返回路径，并满足冻结期限才清账。漏更/迟到保持在最终pending中。有限20s试验不批准补更后继落在窗口外的跳过；不会在结束时把欠账清零。

压力试验与正常T50ms工况分开报告，不可把更改允许周期后的结果当作正常负载收益。无触发则明确“未触发”，不能把单元fixture当真实补更证明。

## 计时和证据边界

RAW日志保存计划发布、实际发布、采样/RPC返回、PS锁、参考/保持/特征、入/出队、输入量化、DPU提交/可读、输出、命令提交/返回、成对刷新和最终完成时间。纯硬件时间没有单独工具读取，留空；DPU区间是API调用墙钟。命令返回是ping代理，不是物理电机确认。

状态与参考以实际记录计算跟踪误差，过门用相邻采样的前向线段平面交点，分别报告点净空和机体净空。初/末暂停状态是边界时间代理；不是连续扫掠机体安全证明。误差/期限/飞行三者分别判定，delivered不等于飞行通过。

所有线程仍是默认Linux SCHED_OTHER，没有假定PREEMPT_RT或把DPU核亲和误称PS绑核。成本是观测包络×1.25而非WCET；数值PS工作有共享锁，但RPC可并行，检查器的单PS全RPC墙钟计费是明确的保守经验建模，不是已证明覆盖所有多核竞争的硬实时证明。

## 修复且保留的失败

- 本地DPU检查首次：C++14旧JSON临时对象生命周期错误，所有已完成黄金和失败原件保留。
- 一次部署：上传未结束就执行导致Text-file-busy，之后明确等待上传完成，失败日志保留。
- 单机诊断001：400条已完成但最终JSON计数遇到求值顺序/空值错误；journal完整，修复后正式002–004另做，不改旧失败。
- 双机动态v2/002：约10s处`Invalid obligation Drone2:202`早停。已定位快照在锁前取时、锁后取状态，可能把新释放当未来carry而产生prep_ready<release。改为锁内取当前时钟，显式时间测试也拒绝陈旧时刻；补充确定性复现测试，失败轮不算正式通过。
- 派发热路径不再扫描完整历史请求，只检查每机当前所有权；保留所有历史数据，不以删日志消除增长。完成carry的未来模式覆盖也清理。当前可执行是有限实验程序；尚未声称无限期常驻内存有界或长期实时保证。
- 分析器曾用暂停后延迟读回的observed_us核对模拟/PS时钟，导致pressure20-off假阴性。最终使用实际活动样本核对时钟，末端对齐采用已记录pause_return上界代理；原observed_us与旧分析均保留，24项回归通过。这不是修改控制输出或更改原始数据。
