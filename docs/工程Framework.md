# 当前研究框架

这里有两个实验入口。要了解最近四机、六机里的机载控制和固定表，从[当前机载闭环试验](#当前机载闭环试验)读起。要接续运行在 Zynq PS 上的联合调度，先看板端主框架。

## 板端主框架

多架无人机各自按周期发布控制任务，共用一个 DPU。如果让当前飞机运行一个耗时较长的模型，后面的飞机还有多少时间更新控制？路线 B 把这个问题写成一份有限任务日历。

1. **从飞行状态得到期限。** 根据旧命令、匹配的观测及其保持预算估算下一次命令最晚何时应生效。再与任务周期和输入新鲜度期限取最早值。保持预算的物理可靠性仍需实验约束。
2. **把剩余时间分给模型。** 在指定后续顺序和成本下，从后往前倒推，为后续任务预留 DPU 时间。当前任务在剩余连续时间内选择模型。板上使用独立 237D 模型，整任务派发。
3. **当日历排不下时，区分原因。** 发布时间太晚、区间内计算需求过大、执行顺序造成阻塞，对应不同候选动作。真正提交时还要检查其他回路和最新状态版本。跳过一次并限时补更需要额外的物理与时序证据。

完整公式、手算例子和研究假设见[框架规格](../controller_architecture_study/docs/义务保护预算分配Framework_20261116.md)。[目前板端实现](../controller_architecture_study/docs/Route-B实现现状与交接_20261117.md)及[最新板端派发验收](../controller_architecture_study/docs/PS就绪队列派发修复_20261117.md)分别说明实现范围和实测结果。后续工作见[协作看板](协作进度.md)。

## 当前机载闭环试验

### 以前和现在，分别在哪算

以前 Zynq 提供周期性的外环控制。外环在这里指为飞行决定下一条控制目标，底层飞控仍由 Windows 上的 AirSim 执行。最近的机载原型让 AirSim 里的每架飞机都有一个本地外环，基础飞行由它维持。共享 DPU 按机会提供额外修正。

| 工作 | 板端主框架 | 最近的四机、六机原型 |
| --- | --- | --- |
| 仿真物理、传感器和底层飞控 | Windows 上的 AirSim | Windows 上的 AirSim |
| 基础航迹跟踪 | Zynq PS 每周期读状态、准备输入、调度及下发，DPU 算出外环命令 | 每架虚拟飞机的 SimpleFlight 更新路径直接读本机状态，用轻量 C++ 计算前进速度、横向纠偏速度、航向和高度目标 |
| 共用 DPU 时选哪架 | Zynq PS 维护任务与期限 | Windows 的 Python 试验脚本按槽选一架 |
| DNN 输入和命令传递 | Zynq PS 从 AirSim 读状态、构造 237D、得到输出后下发 | Windows 脚本在可用槽通过本机 RPC 采样各机，只为选中的那一架构造 237D。经网线把原始输入发给 Zynq，收到结果后换算油门并提交给 AirSim 裁决 |
| DNN 推理 | Zynq PL 上的真实 DPU | 同一块板上的真实 DPU，固定使用模型 11 |

**下放的是基础控制功能。** 每架飞机用轻量控制维持路线，从读本机状态到写飞控目标都在 AirSim 内完成。共享 DNN 路径保留外部采样、237D 特征、通信和真板推理。上表的四机、六机原型由 Windows 脚本管理；最新两机版本已把这条额外修正路径接到 Zynq PS。[本地控制律与裁决](../controller_architecture_study/airsim_command_timing/onboard_pilot.hpp) · [PS 执行入口](../controller_architecture_study/airsim_command_timing/ps_onboard.cpp)

### 机载算力是怎么模拟的

改动编译进一份独立的 Blocks 工程。AirSim 每次更新一架飞机的物理状态时，会更新该机的 SimpleFlight 控制。新增 C++ 在这个调用里读取本机状态，把目标直接交给同一飞控。每架有独立的目标、序号和控制状态，用飞机名区分。执行这些代码的物理算力来自 **Windows 主机 CPU**。AirSim 内的各架飞机共享同一个仿真进程和主机 CPU，按主机自己的调度运行。这批数据验证的是功能分工和控制链路。每架机的 CPU 配额和嵌入式机载硬件的最坏执行时间还需独立实测。

无可用 DPU 命令时，机载控制的名义更新间隔为 20 ms。新的 DPU 命令按序号和采样时间检查，裁决时的输入年龄须小于 55 ms。采用后给它约 20 ms 的优先窗口，并继续受样本新鲜度约束，随后由机载控制继续提供目标。实际更新间隔受 AirSim 和 Windows 调度影响。[SimpleFlight 接入点](../controller_architecture_study/airsim_command_timing/prepare_onboard.py)

### Zynq PS 接管额外修正

两机版本中，Windows 负责摆场、起飞和收日志。PS 在可用槽采样各机，决定给谁、用哪个模型，只为选中的飞机计算 237D，直接调用板上 DNNDK，再通过 AirSim RPC 交付控制。AirSim 用自己的时钟核对样本年龄，以飞机名、命令序号、采样戳与 PS 记录配对，证明飞控实际采用了哪条命令。

这里的 $T$ 是同一架飞机两次申请中央修正的最短间隔。动态组在预先测得的关键位置附近允许每 180 ms 申请一次，用模型 11。其余位置至少间隔 720 ms，用模型 5。若同槽有多架符合条件，优先给更快离开关键窗口的飞机。每个可用槽最多一次推理。这个入口实现了有界的 $T,c,\sigma$ 联合选择，板端主框架中的义务日历、倒推预算和 A/B/C 修复仍是独立入口。[复现命令](协作复现指南.md#复现-ps-与机载闭环接线)

固定链路试飞中，Drone1 采用两条真实 DPU 命令，之间有 67 次本地更新。后续两组共 8 场留出试飞，过 48 道门，无接触，82 条额外命令全部采用。两组用相同的机载控制、起飞错峰及历史可用槽。静态组从四套配置中选定 360 ms、模型 11，按最久没获推理的顺序派发。

| 留出窗口 | 每场关键位置的采用次数 | 门附近全队最小估计净空，静态 → 动态 | 每场 DPU 调用内累计时间，静态 → 动态 |
| --- | ---: | ---: | ---: |
| w09 | 0 → 0 | 129.50 → 126.62 mm | 13.07 → 0.47 ms |
| w17 | 3 → 6 | 124.56 → 131.16 mm | 17.00 → 8.31 ms |

w09 的可用槽与关键位置错开，降低推理成本伴随约 2.9 mm 净空损失。w17 有机会在关键位置采用更多命令，全队最紧的 Drone2 也从每场 1 条增至 2 条。结果来自同一路线、两架飞机和历史忙闲回放。PS 在每个可用槽仍采样两架飞机，本次资源结果直接量到的是 DPU 调用内耗时。后续比较需要加入能提前排好每个槽接收者的静态表，检验在线选机的独立收益。

### 固定表是什么

固定表是一张**事先排好的 DPU 名单**。最近的实验每 180 ms 有一个候选槽，整个编队共用。历史板端调用日志决定哪些槽被占用，四机、六机对照各用一段有 18 个可用槽和一段有 12 个可用槽的回放。固定表提前知道路线、各机错峰和整张忙闲表，用校准航迹估计飞机到时会在哪，给每个可用槽写定接收者。举例说，六机第一段预先规定第 29 槽给 Drone5，第 30 槽给 Drone6。实际推理仍读取被选中飞机的最新状态。固定的是每个槽给谁。

原在线方法在槽到来时用实际位置选人。新在线方法允许一次例外。当另一架仍处于有证据支持的纠偏窗口，而且让出方后续门的估计余量足够，就把槽让给更需要它的一架。下一可用槽先补给让出方。六机的例子正好把第 29 槽给了 Drone6，第 30 槽补给 Drone5。三种方法共用请求预算、机载控制和同一个模型。[排表和在线实验入口](../controller_architecture_study/airsim_command_timing/run_onboard_deferral_policy.py)

### 当前结果和谁接着看什么

- **机载控制能在中央没有新命令时持续纠偏。** 早期受控中断对照验证过这条链路。最近的四机和六机试验中，任意来源控制更新的最长观测间隔约为 22–23 ms。历史忙闲只决定什么时候有槽可用，提交的所有请求都走真实 DPU。背景任务争用和独立机载硬件的成本留待实测。[机载路径验收](../controller_architecture_study/docs/Route-B两机机载闭环初验_20261124.md)
- **等预算下的选机收益在扩大时未复现。** 四机、六机共 24 场，走完 360 道门、无接触，360 条推理全部采用。固定表和原在线方法对应的 120 个槽选机相同。六机发生两次让出并补回，接手的 Drone6 最紧处提高约 0.6–0.8 mm，全队最紧处仍由 Drone4 决定。Drone4 经过此前校准的高收益位置时，几个候选槽恰好都忙。这批数据说明选机受限于有哪些机会、机会出现时哪架仍需要它。[四机六机逐机结果](../controller_architecture_study/docs/Route-B四机六机同预算对照_20261125.md)
- **六机仍有一个可独立核验的假设。** 在相同请求数下，把 Drone4 一条偏晚的命令移到第三道门前，检查全队最小净空是否随之改变。
