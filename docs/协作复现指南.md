# 路线 B 协作复现指南

先克隆 GitHub 源码，再按目标取运行包。四机、六机原型由 Windows 脚本管理额外推理。最新两机版本由 Zynq PS 采样、编码、选机和选模，直接调用真板 DPU。两版的基础纠偏都在 AirSim 里的每架飞机上完成。板端主框架也可以独立运行，由 Zynq 提供周期性外环控制。[工程框架](工程Framework.md)

## 交接时需要什么

| 要做什么 | GitHub 外还需要的文件和环境 |
| --- | --- |
| 阅读、修改调度或跑 C++ 回归 | GitHub 提供当前调度源码。C++ 回归需要 CMake、C++ 编译器和 `json.hpp`。交接包 `ps_runtime.tar.gz` 的 `build_deps/` 附有实测版本的头文件。 |
| 复现最近四机、六机机载原型 | Unreal Engine 4.27、Windows C++ 工具链、Python 3.11，以及 `blocks_ue427_onboard_source.tar.gz`、`board_package_requant18_release001.tar.gz`、`replay_frozen.tar.gz`。Blocks 包已有实验专用的机载 C++ 接口和 `FalconEmpty` 地图，需要在 Windows 构建。 |
| 复现原板端 PS 调度基线 | 同一套 UE/Blocks、同一套 release001 模型、`ps_runtime.tar.gz` 内的现成 AArch64 程序与试验配置。板子需有相容 Linux、DPU bitstream、驱动和 DNNDK 用户态库。修改 PS 程序后，还要有对应的 Ubuntu 交叉 SDK 和 DNNDK 链接库。 |
| 复现最新两机 PS 与机载对照 | 上述四个包，再取三窗口忙闲表 `ps_onboard_join_20261126_001/comparison/load_masks.json`，保存为下方命令里的 `ps_onboard_load_masks.json`。程序和校验文件在同一结果目录的 `board_build/`。自行编译时还需要对应 Ubuntu SDK、DNNDK 库和编译板端 RPC 库时使用的 rpclib 头文件。 |

发给协作者的是 **GitHub 提交号、本页和上述独立运行包**。包名与 SHA-256 见同目录的 `SHA256SUMS.txt`。Windows 端用 `Get-FileHash -Algorithm SHA256 文件` 核对。Ubuntu 或板端可在包目录用 `sha256sum -c SHA256SUMS.txt` 核对。已有网络和 DPU 驱动可以继续用。只要模型包与系统 ABI 相容，跑现成程序即可；编译、量化或重做板卡镜像属于各自独立环节。

## 先复现最近的四机、六机原型

### Windows 准备环境和 Blocks

已用 Python 3.11.9、AirSim Python 1.8.1 和 UE 4.27 运行。交接包复建使用 Visual Studio 2022 的 MSVC 14.40 与 Windows SDK。本地库有版本依赖，若链接出错，先核对 C++ 工具链版本。在 Git 根目录执行，先把 `$kit` 与 `$engine` 换成自己的路径。

```powershell
$kit = 'D:\allone_runtime'
$engine = 'C:\Program Files\Epic Games\UE_4.27\Engine'
py -3.11 -m venv .venv
$py = (Resolve-Path '.\.venv\Scripts\python.exe').Path
& $py -m pip install 'setuptools==65.5.0' wheel 'numpy==2.4.6' 'casadi==3.6.7' 'msgpack-rpc-python==0.4.1' 'opencv-contrib-python==5.0.0.93'
& $py -m pip install --no-build-isolation 'airsim==1.8.1'
& $py -c "import airsim, numpy, msgpack, casadi"
& $py -m unittest discover -s tests -p 'test_gate*.py'

$project = Join-Path $kit 'Blocks\Blocks.uproject'
& "$engine\Build\BatchFiles\Build.bat" BlocksEditor Win64 Development "-Project=$project" -WaitMutex -NoHotReload -NoXGE
if ($LASTEXITCODE -ne 0) { throw 'Blocks build failed' }
```

Blocks 包内是本实验用的项目源码、地图和构建依赖，UE 编辑器和系统工具链由同事自行安装。已有兼容的 AirSim Blocks 源工程时，也可以用 Git 中的 [prepare_onboard.py](../controller_architecture_study/airsim_command_timing/prepare_onboard.py) 生成独立副本，再用同一份 `FalconEmpty.umap` 和机数配置。机载试验需要 `falconPilotStart`、`falconPilotRates` 等自定义 RPC，直接启动普通 Blocks 时这些入口通常不存在。

### 跑闭环对照

以下命令从 Git 根目录执行，沿用前面定义的 `$kit`、`$engine`、`$project` 和 `$py`。示例板端 IP 为 `192.168.77.2`，用同事自己的网卡配置替换。四机跑完退出这一个 Blocks 实例，再换六机配置。也可先在前台开启 Blocks，使用相同地图和设置并点击 Play。

```powershell
$n = 4  # 四机结束后改成 6 再跑
$board = '192.168.77.2'
$frozen = Join-Path $kit 'replay_frozen'
$bundle = Join-Path $kit 'board_package_requant18_release001'
$cfg = Join-Path $frozen "settings_$n.json"
$editor = Join-Path $engine 'Binaries\Win64\UE4Editor-Cmd.exe'
$flags = ('"{0}" /Game/FalconEmpty -game -unattended -RenderOffscreen -nosound -ResX=640 -ResY=400 -settings="{1}"' -f $project,$cfg)
if (Get-NetTCPConnection -LocalPort 41592 -State Listen -ErrorAction SilentlyContinue) { throw '41592 已占用' }
$sim = Start-Process -FilePath $editor -ArgumentList $flags -WindowStyle Hidden -PassThru
try {
    $listen = $null
    for ($i=0; $i -lt 40; $i++) {
        $listen = Get-NetTCPConnection -LocalPort 41592 -State Listen -ErrorAction SilentlyContinue
        if ($listen) { break }
        Start-Sleep -Seconds 1
    }
    if (!$listen -or $listen.OwningProcess -ne $sim.Id) { throw '独立 Blocks 的 41592 未就绪' }
    $out = Join-Path (Get-Location) ('controller_architecture_study\results\fleet_' + $n + '_' + (Get-Date -Format 'yyyyMMdd_HHmmss'))
    & $py -u -m controller_architecture_study.airsim_command_timing.run_onboard_deferral_policy `
        --fleet $n --board $board --board-port 5240 --bundle $bundle --frozen-from $frozen --output $out
    if ($LASTEXITCODE -ne 0) { throw "保留失败结果目录 $out" }
} finally {
    Stop-Process -Id $sim.Id -ErrorAction SilentlyContinue
}
```

每个机数 12 场。检查 `summary.json` 中每架的过门数、接触、`board.requests` 与 `board.adopted`，以及 `exchange.repay_applied`。每个窗口每场应分别发 18 或 12 条请求。四机和六机合计历史结果是 24 场、360 道门、360 条命令实际采用。用随包 `reference/fleet_scale_audit.json` 对照结论。不同 Windows 运行环境可能有小幅净空和时序差异。可移植输入包已能重建原两种机数的四张静态表，无需原作者的 Windows 路径。[完整四机六机报告](../controller_architecture_study/docs/Route-B四机六机同预算对照_20261125.md)

## 再复现板端 PS 链路

这条线用 Windows 的 AirSim **TCP 41451**，让 Zynq PS 能访问。完成机载对照后，结束该对照的 IP37 服务和独立 Blocks。只在本次实验所在的以太网上允许板端访问 AirSim。

```powershell
$cfg = Join-Path $kit 'settings_ps_12.json'
$settings = Get-Content 'controller_architecture_study/configs/airsim_safety_12.json' -Raw | ConvertFrom-Json
$settings | Add-Member -NotePropertyName ApiServerPort -NotePropertyValue 41451 -Force

[System.IO.File]::WriteAllText($cfg, ($settings | ConvertTo-Json -Depth 12))
& "$engine\Binaries\Win64\UE4Editor.exe" $project /Game/FalconEmpty "-settings=$cfg"
```

在 Blocks 加载后点击 Play。板端试验期间保持 Play，直到跑完这一轮。

**修改后重编。** Ubuntu 上解压同一 `ps_runtime` 包和模型包。以包内 `source/` 作为这次验收二进制的完整源码基线，在 Git 的 [live/](../controller_architecture_study/ps_planner_repair/live/) 查找维护中的调度实现，合并时核对版本接口。工具脚本用显式路径链接包内 `local_dpu.o`、`libpsairsim.a`、`librpc.a`，把当前源码和 18 个冻结 ELF 编进新程序：

```bash
# 以下路径替换成本机对应环境。最后一个路径应是新目录。
bash "$PS_RUNTIME/build_ps.sh" "$SDK_ENV" "$DNNDK_LIB_DIR" "$MODEL_RELEASE" "$NEW_BUILD"
```

`SDK_ENV` 是对应板卡镜像的 `environment-setup-aarch64-xilinx-linux`。 `DNNDK_LIB_DIR` 是相容的 AArch64 `libn2cube`、`libhineon`、`libdpuaol` 链接库目录。它们属于交叉环境的外部前提。编译后把新程序部署到新的板端目录，先跑三个回归，再按同一试验步骤替换唯一的执行程序。已有 DPU 驱动和网线能支撑现成程序的运行，重新编译则还要有这套交叉环境。

### 路线静态表、单变量消融和三档机会对照

`study_plan.json` 在试飞前保存运行顺序、可用槽和两张路线表。原错峰是 0.90 秒，消融分别锁住 $T$、$c$、$\sigma$ 中的一项。另一组把实际错峰加到 1.20 秒，比较在线方案、按原错峰排的表、提前知道新错峰的表。三档分别开放 31、23、15 个槽，每档两架飞机。其余槽由历史掩码关闭，低、中档用固定随机种子逐步恢复部分槽。真实 DPU 运行试验所提交的推理；本轮的负载档位用可用槽表示。

### 同一真板 DPU 上的后台推理与关键窗口重叠

仍使用上面的两机 Blocks 和最新版 `ps_onboard`。Windows 用冻结回放包里的两次纯机载校准航迹生成静态表，Zynq 每 3 ms 发布一个后台模型 11 推理。每场开放全部 46 个前台时段，共用同一 DPU 并逐次串行调用 DNNDK。将二进制路径及板端、Windows 地址换成本机配置。

```powershell
$out = Join-Path (Get-Location) ('controller_architecture_study\results\ps_onboard_live_' + (Get-Date -Format 'yyyyMMdd_HHmmss'))
& $py -u -m controller_architecture_study.airsim_command_timing.run_ps_onboard_pair `
  --ssh-hop= --board root@192.168.77.2 --windows-ip 192.168.77.1 `
  --binary /home/root/allone_onboard/ps_onboard --package /home/root/board_package_requant18_release001 `
  --replay-from $frozen --contention-pair --output $out
if ($LASTEXITCODE -ne 0) { throw "保留失败结果 $out" }
```

## 接手后要解决什么

1. **机载与 PS 已接通。** 两机固定验收中逐条配对了采样、推理和实际采用。留出对照中，一段窗口的关键位置采用从每场 3 次增到 6 次，净空增加约 6.6 mm；另一段亏约 2.9 mm，DPU 调用内耗时下降。当前结果与口径见[工程框架](工程Framework.md#zynq-ps-接管额外修正)。
2. **检验联合策略是否超出静态方案。** 在同样机载控制和可用槽预算下，把按路线预排的静态表作为对照，并逐项关掉周期、选模和派发变化，查明收益出在哪。使用额外路线和更多飞机复核。
3. **量出真实存在争用时能省多少。** 历史忙闲表控制哪些槽可用，真板只执行该场提交的额外推理。后续需要实测共用 DPU 上的后台任务、PS 准备和 RPC 开销，并与纯中央控制在预定飞行质量要求下对比。将额外修正的可选任务与必须按时交付的控制任务区分清楚，再考虑复用旧义务日历。[时序与版本边界](工程Framework.md#板端主框架)

四机、六机选机对照的全队收益尚未复现。新 PS 入口的联合调节证据来自两机真板闭环与回放槽限制。
