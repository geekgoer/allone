# 状态感知的动态控制与共享加速器框架

维护日期：2026-11-02。本文是当前设计入口；进度与任务维护在[协作进度](COLLABORATION_STATUS.md)，源码与证据入口见[研究分支索引](../controller_architecture_study/docs/README.md)。

本文在用户提供的[原始Framework_latest快照](reference/Framework_latest.original.md)上整理，并纳入后续关于低开销学习建议、明确检查和真实接管的讨论。原文逐字保留，来源及哈希见[快照清单](reference/framework_source_manifest.json)。原文中的“直接查表、不使用预测模型”等是当时的设计选择；当前允许探索小评分器，但没有把整个决策层交给黑盒网络。

## 1. 一句话说明

**多架无人机共享一个计算资源。根据当前状态及正在作用的控制，判断下一条控制最晚何时必须到达、什么控制器够用，再以有限开销安排下一次计算，并检查对其他无人机的影响。**

研究重点是实时系统中的控制有效期、状态相关计算需求和共享资源决策。超网是候选实现手段，不是预先认定必须采用的结论。

## 2. 与FALCON的关系

FALCON已经把控制周期、DNN复杂度、响应时间、调度与硬件资源共同考虑；不能说它没有实时约束。其基线设计包含`D=T`的执行约束和性能建模，50ms不是不可更改的常数。

本研究关心的是：整段轨迹或多机总体J较好时，局部危险状态是否仍需要不同的更新时间与计算量。希望通过在线反馈减少这些局部失效，同时保持合理的总体控制性能和资源开销。

当前代码是FALCON思路上的研究扩展，不是完整逐项复现：主要研究分支使用237D输入、独立路径规划器、凸平移QP＋姿态反馈教师，以及Windows上的CPU分段执行原型。历史12D轨道、旧DPU轨道和论文原始条件应分别报告。

不能把“状态→动态期限→调度”本身当作已经证明的新颖贡献；还需验证状态相关计算需求、低开销决策与真实共享执行的增益。文献工作见[研究日志](../controller_architecture_study/docs/SCHEDULING_RESEARCH_LOG_20261005.md)。

## 3. 时间语义：优先使用绝对期限

| 符号 | 含义 |
|---|---|
| `r[i,k]` | 第k个控制任务的计划释放时刻 |
| `a[i,k]` | 对应控制真正生效的时刻；工程中常只能观测RPC返回代理 |
| `T[i,k]` | `r[i,k+1] - r[i,k]`，计划释放周期 |
| `R[i,k]` | `a[i,k] - r[i,k]`，包含等待、IO、前端、推理及下发的响应时间 |
| `u_held` | 此刻实际保持的、已完成接口转换和限幅的控制量 |
| `B` | 在给定状态、保持控制和模型假设下计算的剩余时间预算 |
| `c` | DNN/超网配置，成本与能力必须分别测量 |
| `sigma` | 多任务实际执行顺序；第一版使用分段EDF |

理论上，若在`a[i,k]`取得匹配状态并分析正在作用的`u[i,k]`：

\[
B_{i,k}=\mathcal B_i(x_{i,k},u_{i,k}^{actual},\Omega_i),\qquad
d_{i,k+1}^{safe}=a_{i,k}+B_{i,k}.
\]

结合基本任务跟踪需要的最大控制更新间隔：

\[
d_{i,k+1}=\min\{d_{i,k+1}^{safe},\ a_{i,k}+T_{\max,i}^{ctrl}\}.
\]

调度必须让下一条有效控制及时到达：

\[
r_{i,k+1}+R_{i,k+1}^{ub}\le d_{i,k+1}.
\]

如果分析使用的是稍后的采样状态，预算原点应是该采样时刻，扣除其年龄，并绑定当时的保持控制版本；不能把旧状态算出的相对预算从“现在”重新开始计时。

讲motivation时可以简称`T+R<=B`。但按上表的释放周期定义，精确关系是：

\[
a_{i,k+1}-a_{i,k}=T_{i,k}+R_{i,k+1}-R_{i,k}.
\]

因此不能把释放周期与命令生效间隔直接视为同一量。`T+R_next<=B`可作为相应起点下的保守充分条件，而非上述精确等式。

计划每20ms发布一次请求，不代表每20ms必有新命令生效。需要分别记录计划释放、实际发布、派发、采样、推理、命令返回与丢弃。响应时间也不等于DNN计算时间。

## 4. 模块与接口

周期丢弃试验入口采用 `period_drop`。每个已发布任务冻结 `D_job = r_planned + T_job`。前端读取原生发布时间事件后，用独立原生采样通道提交状态请求。采样可与上一任务推理或命令回执重叠，控制推理和下发仍按同机顺序执行。动态更新只改变下一未发布任务的周期长度，其释放时刻保留上一轮承诺的周期边界。

下发前按 `D_job` 丢弃来不及送达的结果。已发出的AirSim命令可能晚回执，报告单列此类超期。这个试验把物理期限用于动态准入和超期诊断，执行丢弃门使用周期期限。Windows和AirSim的实测上界与有限流水线预测均按经验值报告。

```text
状态＋当前保持控制＋时间/版本
               │
       ┌───────┴────────┐
       ▼                ▼
Safety Analyzer     控制器资格/低开销建议
动态绝对期限         哪些c在相应时序下够用
       │                │
       └───────┬────────┘
               ▼
   有限候选的释放规划＋全组准入检查
   检查所有回路、在途任务与真实开销
               │
               ▼
   原子提交尚未发布的任务安排
               │
               ▼
     分段EDF＋共享执行器
               │
               ▼
         新控制与确认反馈
```

### Safety Analyzer

输入应包含状态、当前实际保持控制、分析时刻、控制版本及动力学/扰动/估计假设。返回预算或绝对期限、适用条件，以及不可用/不可行状态。

早期`距离/速度上界`是启发式原型。当前另有基于保持控制的HOCBF时间预算与向量化分析，方向参考Yang式safe-period研究；但所用模型误差、扰动和执行器界尚未完成认证，不能称为无条件物理安全保证。具体实现见[保持控制分析](../controller_architecture_study/held_control_safety.py)和[相关研究记录](../controller_architecture_study/docs/YANG_SAFE_PERIOD_RESEARCH_20261030.md)。

使用DNN实际控制量可避免把理想MPC命令误当作真实命令，但不消除动力学、扰动、执行器和状态估计误差。独立DNN–MPC误差模块不是当前既定前置条件；若有证据表明必要，可作为明确版本的后续扩展。

### 控制器资格与建议

目标是：

\[
c^{sel}=\arg\min_{c\in\mathcal A(x,\delta,H)} C(c).
\]

`A`是对当前状态、等待/更新条件和恢复窗口已有证据的合格配置集合；不是“网络越大越安全”。恢复要求同时涉及不碰撞、位置/速度误差收敛、维持时间与任务进展，不能用悬停或倒退换取所谓恢复。

实现可以先用低维映射、少量规则或小型模型提出候选，再进行显式检查。当前探索的是486参数线性评分器＋有限候选显式优化，不是端到端神经网络控制调度；评分只是代理，尚不能认证资格，也不是原论文的全局J预测器。

离线有限延迟点测试不等于整个`0<=delta<=delta_max`区间均得到保证。未覆盖状态要保留不确定性，但当前探索试飞不因“查表没记录”就自动终止全机；采用的默认控制和继续飞行规则必须事先说明并记日志。

### 释放规划与共享准入

设计优先让`T`由有限的可行释放时间选择产生，避免在线穷举所有`T×c`组合。当前有不同探索实现：主控制路径以规则提出20/60ms等请求；小评分器分支用有限周期点与派生释放点提出方案。后者不是已经确定的最终主算法。

每次修改必须计入对其他回路的影响：在途任务、段内不可抢占阻塞、前端、IO、命令下发和调度自身开销都不能漏掉。截止时间更宽松不等于可以无限让出资源。不能各自独立选择“最晚释放”，忽略共享执行器上的相互干扰。

后台建议返回后，用最新状态、控制版本和日历重建，再做全组检查和原生原子提交。实现接口不等于每次都找到可行方案；没有通过检查不能声称方案安全，也不能修改过去的失败来制造可行性。

### 分段执行

第一版使用分段EDF：段内不抢占，段边界按绝对期限重排。当前CPU原型按最多两层全连接及其原ReLU划段。

这改变的是执行顺序，不是每次切换一种调度算法。任务发布时确定`c`，在同一任务内部只暂停/恢复，不临时更换网络深宽。不同任务可以选择不同`c`。

## 5. 超网与FPGA的定位

已有因果深宽共享超网：17个深度`1,3,...,33`，8个宽度`128,256,...,1024`，共136个配置。其同一输入上的合法增深/增宽可复用缓存；FP32与整数参考实现已验证部分直接/增量等价性。

但必须区分：

- 共享权重和增量执行能力，不等于所有配置控制输出相同。
- 同一输入的缓存续算，不等于下一次采样可以复用旧激活。
- 切换一致性训练，不等于飞行中已经减少控制跳变，更不等于零jitter。
- 执行器支持增深/增宽，不强迫第一版调度策略在任务中途改变目标配置。
- 旧DPU模型池和自定义可恢复PL执行器是两条不同部署路线。

自定义PL方向需要实测分段、DDR、上下文、量化和网络成本。当前Windows CPU时延不能代替AXU3EGB实测；Ubuntu/Vivado侧以交接包和协作者回填为准。

FP32超网导出已达到其最大配置质量目标；混合精度整数包数值一致性通过，但严格切换质量目标未全过。最新本地冻结包仍是功能原型候选，不应改写为质量全部通过。位置见[协作进度](COLLABORATION_STATUS.md)。

## 6. 当前实现与目标的差距

2026-11-02后续更新：当前试验入口已将选段放到host CPU协调进程，独立模拟XPU仅执行显式段命令；建议CPU服务改为非空闲调用，并分离新ACK期限事实刷新。此版本离线检查已通过，真实效果待用户运行，详见[实现修复与运行说明](../controller_architecture_study/docs/CPU_XPU_SERVICE_REPAIR_20261102.md)。下表的飞行收益仍描述之前的实际结果。

| 目标 | 当前事实 |
|---|---|
| 独立周期释放 | C++绝对时间日历已接入，仍有Windows发布/处理抖动 |
| 控制相关严格预算 | HOCBF原型已实现，假设未认证，实测仍有条件预算越期 |
| 最低成本合格模型 | 有采集、评分与检查代码，资格差异和额外收益未证明 |
| 低开销全组联合调整 | 有界建议、重建及原子提交已实现，可提交窗口仍很少 |
| 新学习方案真实收益 | 首轮实际安装过1组；优化复核0组，不能归功于学习选择器 |
| 当前共享执行器 | Windows C++ IO＋Python前端＋host CPU选段/独立CPU模拟XPU；未接入超网/PL |
| 完整FPGA证据 | 旧链路联通过；当前237D/超网硬件结果需独立回填与核对 |

最新阶段还发现：部分计划仍携带已结束的旧保持控制期限，出现截止时间早于任务发布。应区分已结束义务、真实历史超期和当前有效义务，而不是简单放宽所有期限。详见[阶段结果](../controller_architecture_study/docs/BOUNDARY_TAKEOVER_RESULTS_20261102.md)。

## 7. 哪些实验支撑哪些说法

| 要支撑的说法 | 所需证据 |
|---|---|
| 动态反馈减少局部危险 | 同模型池/资源/路线的离线静态与动态配对，多场景重复；保留静态也通过的结果 |
| 状态需要不同计算量 | 完全匹配初态、保持控制、参考时钟和延迟的恢复差异，另留新路线确认 |
| 建议低开销且有效 | 分开统计评分、准备、搜索、前端复核、安装和真实交付；不能只报小模型推理时间 |
| 超网优于独立池/早退 | 同位宽和资源下比较实际控制、续算、切换成本与命令跳变，不能只比较MACs |
| 满足实时/安全要求 | 与当前控制绑定的期限、适用假设、全组检查及完整超期/丢弃记录 |

J保留作评价指标；使用统一误差、权重、时间网格和窗口。控制标签MSE不是轨迹J，碰撞或缺失窗口的完整J不能补0后混算。原FALCON基线需单独对齐原条件与离线选择，不能把随便一个静态配置叫作全局最优。
