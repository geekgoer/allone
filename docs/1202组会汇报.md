# 1202组会汇报

**路线 B｜每架飞机自己维持飞行，共享 DPU 负责来得及、能凑齐的纠偏**

汇报日期 2026 年 12 月 2 日。材料整理于 11 月 28 日，主要覆盖 11 月 24–27 日。

## 1. 组会上先讲什么

以前每架飞机需要更新控制时，都要请 Zynq 读它的状态、跑 DNN、再把命令传回去。多架飞机同时更新时，普通飞行和关键纠偏都在等同一条链路。我们先给每架飞机装上一个轻量的本地控制，用它完成平时的跟踪，把共享 DPU 留给有机会改善飞行的额外纠偏。

做完这个分工后，真正值得研究的问题变了。**三次推理机会给三条命令，飞控都按时采用，为什么有时只有一架过门，有时能有两架？** 因为有的飞机需要先拉回来、过一会儿再补一把。第一条发出前，要看看第二条还有没有地方放。另一方面，只有实际腾得出 DPU 的机会，才可以拿来做这个判断。

这周最有区分度的结果有两个。**同样三次机会，三机闭环中 EDF 两轮各有一架过门，成组派发两轮各有两架过门。** 在另一个双机试验中，背景推理挡住了第二次纠偏。提前留位后，两机均过门从 **0/4 变为 4/4**，背景任务完成时间多等的中位数是 **3.49 ms**。两者都用真实 Zynq DPU，飞行在 AirSim 中进行。

## 2. 为什么要下放，以及具体下放了什么

之前十机、20 ms 起步的日志里，一条状态 RPC 往返花了 **36.66 ms**，后面构造参考、分析和打包等合计约 **2.19 ms**。另外两条任务在发布约 **3.67 ms** 时已有 DNN 输出，等到程序拿到命令确认又花了约 **38–39 ms**。后者是确认链路，单凭它无法知道飞控什么时候用上了命令。两端的等待都可能长于一个控制周期，这解释了为什么单独把选配置算得更快，能省下的时间有限。我们先改变每次基础更新必须往返的架构。[原日志与复算](../controller_architecture_study/docs/Route-B机载分工与时序初筛_20261124.md)

| 工作 | 下放前 | 现在 |
| --- | --- | --- |
| 基础航迹跟踪所需的状态读取 | Zynq PS 经 RPC 向 AirSim 读取 | AirSim 里的每架飞机直接从自己的飞控更新路径读取本机状态 |
| 基础控制目标的计算和下发 | Zynq PS 准备 237D，等 DPU 给出控制结果，再把命令发回 | 每架飞机用轻量 C++ 根据路线和当前位置计算前进速度、横向纠偏速度、航向和高度目标，直接交给本机飞控 |
| 基础控制何时切入、额外命令是否过旧 | 基础外环依赖中央按时更新 | 机载代码比较序号与采样时间，在本机飞控入口裁决哪条目标可以用 |
| 额外纠偏的选机、特征、推理和传输 | 原来每个周期都走中央链路 | Zynq PS 选择要纠偏的飞机并为它构造 237D，Zynq PL 上的真实 DPU 执行推理，PS 将角速度与油门命令发到 AirSim |
| 电机与姿态等底层控制、传感器与仿真物理 | Windows 上的 AirSim / SimpleFlight | 仍由 AirSim / SimpleFlight 执行 |

基础控制是一个轻量的航迹跟踪规则。可以把它理解成「沿路线往前走，偏左就向右拉」，输出速度、高度与航向目标。额外 DNN 命令走姿态角速度与油门接口，它获得一小段优先时间，随后由本地控制继续出目标。两条路径通过飞控裁决切换。机载基础更新的名义间隔为 **20 ms**，实验中 DNN 命令须满足 **55 ms** 的样本新鲜度限制，采用后约有 **20 ms** 优先时间。用于某些短窗对照的 **30 ms** 交付目标是另外一层时限。我们用飞控更新里的实际采用事件确认命令生效，结合飞机名、命令序号与采样戳配对。[机载控制与裁决源码](../controller_architecture_study/airsim_command_timing/onboard_pilot.hpp) · [PS 纠偏入口](../controller_architecture_study/airsim_command_timing/ps_onboard.cpp)

```text
Windows 主机上的 AirSim                                Zynq 真板
┌─ 虚拟无人机 A ─────────────────┐
│ 本机状态 → C++ 基础控制 ─┐    │    需要额外纠偏时
│                          ↓    │    状态读取 ───→ PS 选机、构造 237D
│                   机载裁决    │                        ↓
│                          ↑    │                 PL 上的 DPU 推理
│                      额外命令 │ ←── RPC 下发 ←── PS 换算命令
│                          ↓    │
│                   SimpleFlight │
└────────────────────────────────┘
虚拟无人机 B、C… 各自有本地控制状态，同时共享右侧 DPU。
```

这里的「机载」说的是功能放在每架虚拟飞机内部。代码编译进 AirSim，真实运行占用的是同一台 Windows 主机的 CPU。每架有自己的控制状态，实验还没有按真实飞行器分别测量机载 CPU 的资源和最坏运行时间。早期四机、六机试验的额外纠偏由 Windows 脚本选机并调用板端 DPU，后续原型才把选机、237D 和下发一并接到板端 PS。基础跟踪耗时和额外纠偏链路应分别计量。[分工细节及复跑](工程Framework.md#当前机载闭环试验)

原来的 $T,c,\sigma$ 仍在。现在这三个旋钮控制的是**中央额外修正**，与机载名义 20 ms 更新分开。$T$ 是同一架飞机两次中央申请的最短间隔，$c$ 是模型档位，$\sigma$ 是中央派发顺序。早期 PS 原型在关键位置用 180 ms 和模型 11（4×1024），其余位置用 720 ms 和模型 5（2×128），遇到竞争优先给快离开关键带的飞机。原义务日历、倒推预算与 A/B/C 修复在独立入口。最新成组和留位试验固定纠偏模型 11，集中回答顺序与阻塞问题，暂未把所有动作合成一次经过完整验收的在线决策。[PS 接线与静态消融](工程Framework.md#zynq-ps-接管额外修正)

## 4. 四个发现，以及它们怎样变成算法

### 发现一：同一次更新，给在转弯的哪个阶段很重要

以前的 AirSim 实验故意漏掉两次更新，验证飞行对更新时机的敏感度。50 ms 周期下，早段漏更在连续飞行里把第四门净空从约 **9 cm** 降到约 **2.5 cm**，晚段漏更只带来毫米级变动。80 ms 周期下，合计两种试验入口，早段漏更 **4/4 接触**，晚段无接触。这是人工删除更新后的飞行反应，实际在线漏更率需要另测。

本周反过来问「只给一条额外 DNN，什么时候给更有用」。在匹配的 0.18 m/s 横向速度偏差下，两架飞机较早纠偏的净空中位增益是 **6.87、7.70 mm**，较晚纠偏是 **2.25、2.48 mm**。早段及晚段的定义来自这条路线的干预位置。这个发现让我们把「飞到哪里、还有多久结束这个阶段」放进调度输入。[早晚漏更证据](../controller_architecture_study/docs/Route-B论文研究发现与证据.md) · [单次额外控制配对](工程Framework.md#一条额外命令在什么状态下有价值)

### 发现二：有时必须把两次纠偏一起考虑

在同一个临界转弯，固定路线、扰动、模型和背景推理。用四组短飞检验 Drone2，唯一改变的是两次窗口里发不发命令。

| 给 Drone2 的额外纠偏 | 无接触过门 | 第三门配对试验的估计净空中位数 |
| --- | ---: | ---: |
| 零条 | 0/4 | −9.96 mm |
| 只有早的一条 | 0/4 | −3.35 mm |
| 只有晚的一条 | 0/4 | −4.27 mm |
| 早一条，随后再补一条 | **4/4** | **+4.35 mm** |

这里的净空是根据飞行轨迹与机体外廓估计的门框几何距离，单位是毫米。接触是 AirSim 另行记录的事件，两项并排读。这个案例虽然贴近门框，主要结果是 **0/4 对 4/4 的接触与过门差别**。第二条也有时限，另一次扫间隔中 75–300 ms 档均 3/3 过门，600 ms 和 750 ms 档均 0/3。该范围由这个状态的试验得到，其他路线上的允许间隔需要另外校准。[两条命令的对照与间隔扫测](工程Framework.md#临界状态下一条早发能否顶两条)

### 发现三：逐条命令都按时，仍可能凑不齐一架飞机需要的纠偏

假设 DPU 只给三个机会。A 已拿到第一条，还需一条。B 需要两条，首条期限比 A 的补更紧。C 只需一条。A 和 B 都能用最后一个机会补更，但两架不能同时占它。

| 用法 | 三次 DPU 机会 | 可凑齐的纠偏 |
| --- | --- | --- |
| EDF，先处理眼下期限最紧的命令 | A → B → A | A，1 组 |
| 成组派发，先算后面还能凑出什么 | A → A → C | A 和 C，2 组 |

可以用一个很直接的分数表示。对眼前每种合法派发 $a$，看短窗口里最多能完成几个经校准的纠偏需求 $Q(a)$，选择 $a^*=\arg\max_a Q(a)$，同分再看动作期限。这里一组可以是一条或多条，各条必须落进对应窗口。它既解释了本例里为什么先给 A 收尾，也解释了双机四窗时为什么可以先给 B 开头。在双机案例中，单纯「先收尾」会先连发给 A，B 的首条就晚了。[双机在线结果](工程Framework.md#125-ms-场景的在线成组派发) · [三机在线结果](工程Framework.md#三个机会同时面对双条和单条纠偏)

### 发现四：把纠偏提到最高优先级，仍可能被已开始的长推理挡住

当前板端以整条推理为调度单位。后台任务一旦启动，需要等这次推理结束才能腾出设备。纯设备试验中，短、长后台模型的服务时间中位数约 **1.32、11.77 ms**。长任务在 20 ms 启动，约 31.9 ms 才结束。即使纠偏有最高优先级，也赶不上 30 ms 的交付目标。

留位的方法是先算**最晚何时要拿到 DPU**。如果纠偏的交付期限为 $d$，推理预算为 $\widehat C$，推理后面的下发和采用预算为 $\widehat O$，则最晚启动时刻是

$$
s=d-\widehat C-\widehat O.
$$

闭环用的两项合计预留是 4.5 ms，所以 30 ms 的期限下，最迟在 25.5 ms 开始。背景任务若预计能在这之前结束，让它继续跑。预计跨过这个时刻，才把它延到纠偏之后。这样给成组派发的未来机会尽量由设备真正腾出来，后台也避免白等。这里的预算来自这轮实验用的成本设定和独立测量，正式实时上界还需另做验证。[真板留位成本与时序](工程Framework.md#在真板兑现一个保留窗口要花多少)

## 6. 论文贡献准备怎么讲

1. **物理发现。** 控制更新的价值随飞行阶段变化。有些纠偏要靠前后两条一起完成，逐条按时的数量会漏掉这个区别。用早晚对照、单条和双条、实际采用到过门的因果链来证明。
2. **调度设计。** 在同一个共享 DPU 上，把有时序关系的纠偏作为一份需求，分配眼前的推理时先检查接下来还能完成几份。把 EDF、先收尾和同预算强静态表放在同一控制架构下比较。三机结果也要按飞机报告，避免把「全队多完成一组」说成每架都得益。
3. **设备实现。** 用最晚启动留位把未来的推理机会落实到真板上，量出长任务阻塞带来的错过、纠偏收益及后台延迟。机载外环提供持续运行的基础，贡献重点放在**怎样分配和兑现有限的共享纠偏机会**。

准备在汇报中用下面的顺序收尾。先展示三机会的派发反例，再展示板端 20 ms 后台阻塞和提前留位的对照。四机、六机与强静态表接近的结果也放进去，解释为什么我们从宽松路线下的毫米级优化，转向关键窗口里「有没有及时做完整次纠偏」。全套汇报的主要结果是完整纠偏数、实际过门架数和后台代价。净空用来解释飞行机制。

下一轮需要把两段机制接在一起。现在在线成组试验用预先校准的纠偏需求和已知的窗口，设备留位已经在独立真板闭环中检查过。下一步让真实运行时发布短期可兑现窗口，让成组调度原地使用它，并与同样有机载控制的强静态表、EDF 做留出路线对照。同时记录后续窗口被兑现的比例、逐机过门以及后台的尾延迟。四机与六机已有基础架构的结果，这一步用于验证**最新成组加留位**在更大规模下是否还有收益。[工程进度](协作进度.md) · [研究发现与原始证据索引](../controller_architecture_study/docs/Route-B论文研究发现与证据.md)
