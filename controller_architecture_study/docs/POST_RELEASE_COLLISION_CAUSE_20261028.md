# 释放机制修正后仍撞门：原因对照与阶段结果

后续更新：本报告是故障诊断，尚未重新优化同模型池的静态基线。完成该公平比较后，动态未显示整组优势，最终结论见[同模型池、同资源比较](FAIR_STATIC_DYNAMIC_COMPARISON_20261028.md)。下面保留本阶段原始结果。

日期：2026-10-28。分析对象为`release_calendar_repair_20261028_v1/paired_seed4_final`中的动态失败，并补做六次相同十机路线对照。

## 结论

修正释放语义后，仍存在三个不同问题：

1. **原9×1024恢复模型与当前实际更新时间的组合不适合这段连续转弯路线。** 原模型下，窗口3或10都未救回Drone1/Drone3；换为已有2×128恢复模式后，这两架在四次新试验中均没有碰撞。这里改变的是控制函数和计算成本，不能将改善全部归为平均MSE更低。
2. **端到端等待仍大，单看DNN计算负载会漏掉它。** 当前两架关键窗口内，DNN计算约1.6ms，排队却约15ms，完整R约21～22ms。扩大并发窗口只改变了等待分布，没有自动恢复原模型的通过能力；更换部分模型又可能改变其他回路的请求交错和时延。
3. **这些完整飞行是观察实验，不是已通过准入的安全调度。** 观察模式明确允许超期输出继续作用。部分任务在规划完成时期限已经过去，或最早允许释放时间已晚于期限。它们不是“满足安全约束的调度仍然撞门”的反例，更不能当成框架已经完整满足了硬约束。

本阶段找到一个实际改进候选：**Drone1/Drone3使用2×128恢复模式，允许10个任务同时在控制流水线中在途。** 同一十机路线两次零碰撞、通过全部过门及末尾跟踪检查；但两次都仍有超期，尚未通过硬期限验收。

## 修正后的原失败：时间花在哪里

固定比较参考轨迹的9.00～10.95秒窗口，位于各组Drone1/Drone3接触之前。不同配置均取同一段飞行，不拿一组的转弯阶段和另一组的终点悬停混比。

| 原动态记录，同一困难窗口的均值 | Drone1 | Drone3 |
|---|---:|---:|
| 规划选定的释放间隔T | 26.25ms | 26.27ms |
| 完整响应R：任务到达→命令确认 | 21.45ms | 21.92ms |
| 其中，已到达→开始输入服务的排队 | 14.81ms | 14.90ms |
| DNN各段计算累计 | 1.63ms | 1.65ms |
| 外层预算/预览/周期选择分析 | 0.322ms | 0.324ms |
| 纯计算需求保护判为不可行 | 0次 | 0次 |

排队约占R的七成。这里的外层分析不是单独测得的EDF排序CPU时间，不能说“排序花了15ms”。R与T也不是直接相加后等于两条命令间隔；时间语义沿用上一份修正报告。

根据任务dispatch到前端完成处理的时间戳重建，约51%的排队时间落在3个流水线名额已占用的时间段，约1%～2%与同一回路的上一任务尚未清理重叠，其余混合前端工作次序、IPC及操作系统调度。完成处理内部移除时刻未单独标记，这些是近似归因。

在这些等待区间内，执行器的DNN segment时间窗仅覆盖约25%。这不是CPU利用率测量，但说明“有任务在等”不等于“计算核一直在算DNN”。单纯增加DNN计算核不能自动消除通信与前端等待。

预算失约同样不是都发生在推理过程中：在上述窗口，Drone1的75条已施加任务中，4条在规划可用时刻已超过期限，另有部分在后续释放/等待/推理阶段超期；Drone3也有规划前就超期的任务。Drone1有5条、Drone3有2条的绝对期限早于最小允许释放时刻，即便把后续DNN计算设为零也不能使这些具体计划满足期限。

当前B仍是几何/速率启发式；“其期限失约”不能等同于真实物理碰撞必然发生，也不能以少量无碰撞结果证明B已具备严格安全含义。

## 六次预先声明的对照

所有组均使用原保存的种子4十机路线、5m/s、1.7m门宽、相同初态、237D输入与归一化参数。没有加扰动、没有缩门、没有改训练权重。共享DNN计算核始终为一个，CPU放置相同。只改变：

- `max_inflight`从3到10：同时在采样—推理—命令反馈流水线中的任务数量上限。现有I/O线程数不变，**不是增加10个计算核**。
- Drone1/Drone3在困难阶段的恢复模型：原9×1024，或已有2×128。其他回路的模型设置保留，Drone9仍使用此前已筛查的恢复模式。

首次顺序预先记录为B→A→C→D；随后反序复核D→C。过程代码哈希、模型、CPU放置、初态和仿真/墙钟检查均已核对。

| 组 | 1号/3号恢复模型 | 在途上限 | 结果 |
|---|---|---:|---|
| A | 原9×1024 | 3 | 1号、3号接触第8门 |
| B | 原9×1024 | 10 | 1号、3号仍接触第8门 |
| C | 2×128 | 3 | 1号/3号通过；2号接触第5门 |
| C反序复核 | 2×128 | 3 | 零接触，但2号第5门未达额外余量 |
| D | 2×128 | 10 | 十机零接触，全部物理检查通过 |
| D反序复核 | 2×128 | 10 | 十机零接触，全部物理检查通过 |

C复核中的2号实际没有碰撞：过门横向偏差为-0.325930m，原验收阈值为±0.325m，差约0.93mm。没有放宽阈值，也没有把这次余量不合格写成真实接触。两次C结果接近边界，不能将窗口3配置认定为稳定安全。

所有失败都只停止对应无人机，其他回路继续。因此C首次在7.24秒后仅剩9个活动回路；比较后续时延时已标记这一负载变化，不能把它当成仍有十机活动。D两次无回路退出，是真正十机持续到任务结束。

## 对照能说明什么

**只扩大窗口不够。** A→B时，原模型的排队时间确实减少，但部分时间转移到输入/通信处理，困难窗口内完整R仍约23～25ms，原模型仍碰门。不能据此宣称扩大并发就等价于获得一个更快的加速器。

**控制器的闭环适用性必须检查。** B和D首次在同一窗口下，1号的T均值约27.62ms与26.89ms、R约22.75ms与21.88ms，量级接近，但原模型失败、小模型通过。这支持“所选控制函数在该路线及该时序下是否能恢复”很重要，不能只按模型参数量或平均误差排序。

**共享影响仍存在。** C首次中未改变模型的2号出现碰撞，复核时也接近余量边界；D在较大的在途窗口下两次均通过。改变其他回路的c会改变计算成本、后续释放间隔和任务交错，所以单独回路通过不意味着共享系统也稳定通过。六次试验不足以精确分配这些影响的比例或估计长期碰撞率。

此前保存的独立低延迟对照仍适用，因为路线、权重与初态定义未变：Drone1原模型20ms两次碰门、10ms两次通过；Drone3原模型单机20ms通过。这进一步表明问题是控制器/更新时间/响应延迟的组合，而不是DNN完全没有控制能力。

## 是否存在输入实现错误或模型误差

沿本次原失败记录，将实际推理用的同一状态与参考重放给训练教师和模型：

- 模型输出与日志控制量最大差约9.54e-7，未发现该记录中的输入编码或权重错配。
- 教师参数和源文件哈希与原训练数据清单一致。
- 原9×1024的局部标准化控制MSE，Drone1从前段约0.00237增至最后两秒0.04096；Drone3约0.00263增至0.03246。横滚输出RMSE约0.154、0.137rad/s。

这是失败轨迹上的近似误差放大，不能单凭它证明训练数据缺失，或将时延与模型误差的因果份额完全拆开。小模型在相同失败状态上的MSE排名并不更好，却能沿它自己的闭环轨迹通过，故不能用这一次离线排名替代闭环资格。

## 为什么现在还不能宣布框架成功

1. D两次虽然物理通过，但分别有126、105条已施加命令超出记录的期限；各次还观察到部分平稳回路的命令更新间隔超过80ms。并非只存在日志文字上的未通过。
2. 同时，部分失约来自B已为0或释放前期限已过；当前经验B可能过于保守或与真实机身/动力学不匹配。不能为了过验收直接把这些期限删掉，应独立修正预算定义与计算。
3. 严格准入并未在本批中被宣称通过；这些组明确运行在观察模式。一个已经超过期限仍继续运行的探索试验，不是框架硬约束成立的证明。
4. 没有重新优化静态基线，也没有比较总J。动态新增的小模型需要同样交给静态选择器后再做公平比较。本次是在定位原因，不能拿D和旧静态结果直接宣称动态调度创新已获证实。

## 接下来的最小改动方向

- 将已筛查的恢复模式与其实际更新/延迟适用范围配套，先使用现有权重，不急于重新训练更大的DNN。
- 将采样/前端/通信等候纳入完整响应可行性，而不只用计算利用率决定能否加快更新。
- 把D作为明确的诊断候选，继续处理超期与B的有效含义；当前不能把它设为已认证部署配置。
- 正式比较前，对静态与动态提供相同候选池，按正确的释放语义重新离线选优。

FPGA可以降低计算与部分调度开销，但原模型扩大并发后仍碰门、计算本身仅约1.6ms，说明只迁移DNN计算不能保证解决本次问题。若硬件与软件一起使端到端响应更小、支持该模式经过验证的更短更新，仍有改善可能；本批没有FPGA测量。
