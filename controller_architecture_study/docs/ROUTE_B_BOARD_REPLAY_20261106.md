输入为 `F:/FalconReproduction/237D_data/board_237d_timing_20261106_run001`。板端交付的说明是测量证据。Windows 侧通过 [bottleneck_board_replay.py](../bottleneck_board_replay.py) 独立复算，报告在 `results/bottleneck_board_237d_20261106_v2/summary.json`，逐个期限对照在同目录 `deadline_cases.json`。原始 88 个文件的哈希与回放源码哈希随报告保存。

## 数据能用到什么程度

88 个文件哈希全部匹配。审计了 18 轮、69,600 条请求的身份、绝对发布时间、无重复顺序、各阶段时间戳、派生耗时及黄金输出容差。开放式 66,600 条均在本轮 50ms 期限内完成，另外 3,000 条是无期限的单请求测量。全部请求有效。

模型为 `main18_plain_mlp_h4_w1024_seed0`。记录为 AXU3EGB 单 B1152 DPU，应用用一个 worker 同步执行输入准备、DPU 调用和输出处理。板内入口为 raw237 向量就绪，终点为控制量就绪。用于校准的服务是完整串行 worker 占用，从准备开始到输出就绪。API 调用墙钟和 CPU 阶段已分别核对，但在这个执行结构下不能假定 CPU 前后处理和另一条 DPU 工作重叠，也无法从 API 时间中单独识别纯 PL 执行。纯硬件计时、特征构造、网络、作动、其他模型切换未测。

| 条件 | 实测软件等待 P99 | 实测响应 P99 | 以单请求服务采样重建的响应 P99 |
| --- | ---: | ---: | ---: |
| 单请求 | 0.00033ms | 1.330ms | — |
| 6 路错峰 | 0.012ms | 1.396ms | 1.389ms |
| 12 路错峰 | 0.012ms | 1.401ms | 1.389ms |
| 6 路同步 | 6.583ms | 8.014ms | 7.995ms |
| 12 路同步 | 14.476ms | 15.959ms | 15.924ms |

单请求串行服务 P50/P99 为 1.321/1.329ms，DPU API P50 为 1.301ms。12 路从错峰变成同步时，服务 P50 仍约 1.32ms，等待 P99 则增加约 14.46ms。用约 1.32ms 乘每秒 240 条，串行服务需求量约为每秒 317ms，这只是负载估算。同步请求的主要问题发生在短窗口，即使长期负载有余量，批次后部也会等待。

FIFO 校准用实测入队时间，令 `start[i] = max(enqueue[i], finish[i-1])`，再加服务时间。分别用当轮对应请求的实测服务做轨迹重建，以及仅用单请求组的服务随机采样做独立校准。两种方式都重新计算等待。后者复现了同步条件的 P99，但漏掉极端波动，例如 12 路同步的实测最大响应 17.438ms、独立校准最大 16.012ms，12 路错峰的对应值为 3.690/1.475ms。板上计时分位数和最大值均属于这次测试条件，尚无严格上界。

直接用原响应统计，12 路同步的 21,600 条中，若事后把共同期限设为 5/10/15ms，会分别有 16,200/9,000/1,801 条超期。12 路错峰 21,600 条在这三个阈值下均无超期。这个对比只换判断阈值，真实发布周期仍是 50ms。

## 换成板端成本后，A/B/C 各自能解释什么

选择 6/12 路、同步/错峰四组实测入队记录，每条件三轮各抽 20 个批次，共 240 个真实到达批次。每批试五组期限，合计 1,200 个回放案例。每条使用实测单请求串行服务 P99 1.329ms。到达时间来自板端，紧期限是离线假设。各批回放没有批前积压。使用一个模型、已锁定的发布时间和整任务边界，故这里验证诊断和调度顺序。固定 FIFO 与 EDF 按任务就绪即调度，A/B/C 计入 0.5ms 决策预留与实测 Python 决策时间的较大者。

以 12 路同步为例，数字表示所有任务都按时完成的批次数：

| 每批期限设置 | FIFO | 固定 EDF | A/B/C | A/B/C 对 FIFO 失败的诊断 |
| --- | ---: | ---: | ---: | --- |
| 全部 50ms | 60/60 | 60/60 | 60/60 | 无 |
| 1 条 10ms，其余 50ms | 36/60 | 60/60 | 60/60 | C 类 24 批 |
| 1 条 5ms，其余 50ms | 12/60 | 60/60 | 60/60 | C 类 48 批 |
| 4 条 5ms，其余 50ms | 0/60 | 0/60 | 0/60 | B 类 60 批 |
| 1 条 1ms，其余 50ms | 0/60 | 0/60 | 0/60 | A 类 60 批 |

单个紧迫任务的收益由普通 EDF 就能达到。四条同步紧迫任务在 5ms 内需要约 5.31ms 的串行服务，这份成本设定下，单纯重排解决不了容量缺口。1ms 的例子连独占整条串行服务也来不及。12 路错峰条件下，除 1ms 的独占缺口外，四组期限全部通过。

## 下一轮补哪些数据

这批数据足以校准该模型当前板内服务与同步排队。原测试在 50ms 期限内有余量，因此 A/B/C 的进一步价值应在**实际变化的控制期限**以及 EDF 处理不了的配置选择上检验。最小后续数据是：

1. **实际控制链的时间线。** 在真实集成路径或受控闭环回放中记录状态采样、237D 构造起止、任务释放、板端就绪、主机接收、控制生效和安全模块给出的绝对期限。不同机器的时钟不能直接相减，用统一主机端时间轴结合板端各阶段耗时，并记录控制版本。先核对是否真实出现窗口小于 15ms、同步到达或已有在途任务。
2. **一个成本差异明确的已验证模型。** 按本轮单请求和有限并发口径测另一个 237D 控制器，记录模型输出核对和常驻 A→B/B→B 成本。若还没建立其闭环恢复资格，先标为时序候选，实际切换决策仍只从合格模型选。
3. **保留强基线。** 实际到达和期限确定后，比较固定错峰、整任务 EDF 与 A/B/C。只在 EDF 无法修复、且资源或释放调整真实生效的样本上，归因于联合决策。
