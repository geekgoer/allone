# 慢 ping 会不会让板端改错周期？

上一轮真板十机的 31,975 条已发命令都赶上了截止，`ping()` 最慢约 7.8 ms。本轮沿用同一条路线、Zynq 程序、模型 ID 11、初始周期 20 ms 和 640×400 离屏 Blocks，只改变独立仿真进程可用的逻辑 CPU 数。没有向命令或 `ping()` 路径插入延迟。[前一轮对照](Route-B真板命令采用旁路审计_20261124.md)

## 怎样判断一次改期触发

现在程序看到两个条件同时成立才登记一次晚确认。

- 确认时刻到达或超过该条任务的截止。
- 从控制输出转换完到确认时刻，耗时超过该回路的当前周期。

登记后，还要等同一控制版本下的后续推理任务被拒绝，系统才尝试改期。尝试之后还要检查旧命令的保持期限和下一周期能否容纳预算。因此，初次触发、真正尝试和实际安装是三件事。

复算把第一步的确认时刻换成同一条命令**首次被模拟飞控采用的时间区间**，使用原日志的截止、周期和控制版本。仅有目标写入或校时误差跨过边界时单列。原始执行仍使用原 `ping()`，所以哪些改期在替代规则下会真的安装、改变之后轨迹和丢弃数如何，留给后续可执行对照。

## 四逻辑核下的实测

这轮从赛道准备开始就限制了独立 Blocks。压力过重，十机全部退出，测量从发布原点到停机约 **0.451 秒**。其中五机保持期限到期、五机输入超出模型量化范围。这个样本用于验证触发语义，无法用于比较整段飞行。

118 次任务中有 46 条发出了带序号命令，45 条匹配到模拟电机更新，1 条只观测到目标写入。8 条 `ping()` 至少等待 20 ms，最大 41.519 ms。看同一条任务自己的截止，记录了 **4 条确认判晚、飞控按时**，以及 **2 条确认判及时、飞控晚用**。

| 初次触发判据 | 数量 |
| --- | ---: |
| 两种时刻都满足 | 5 |
| 只有 `ping()` 满足 | 2 |
| 只有采用时刻满足 | 2 |
| 两种时刻均不满足 | 36 |
| 无法确认采用时刻 | 1 |

真实路径执行了 19 次改期尝试，安装了 5 次。其中两次安装可追溯到**飞控已按期采用、只有 `ping()` 判迟**的命令。

| 回路与周期 | 等待 ping | 从提交到首次采用 | 后续实际改期 |
| --- | ---: | ---: | --- |
| Drone3 第 4 周期 | 23.687 ms | 12.498～13.056 ms | 第 6 周期的尝试把未来周期从 20 改为 60 ms |
| Drone5 第 5 周期 | 25.679 ms | 8.304～8.852 ms | 第 7 周期的尝试把未来周期从 20 改为 80 ms |

另一个例子是 Drone4 第 0 周期。`ping()` 只等了 7.677 ms，飞控直到提交后 **22.191～22.780 ms** 才用上命令。晚采用的 8 条都能确认在截止前已到达 AirSim 的 RPC 回调，进一步的延迟留在了仿真器。它可能来自目标等待写入或下一次飞控更新，记录把两段分别保留。

相对钟速误差的假设分别取 100、200 和 400 ppm 重算，四核组的五类触发数量和 19 次尝试的来源判定一致。

## 八逻辑核下的实测

第一次沿用已经运行过的场景，`simListSceneObjects` 超过 3 秒，控制程序没有开始。随后重启独立 Blocks，在赛道准备与校时开始后才开启限制。第二次有 1,091 条任务，其中 1,081 条实际发出且均按期采用。`ping()` 最长 **7.665 ms**，没有触发改期。全组约 **2.378 秒**后退出，十次拒绝都在 237D 输入的第 7 号索引，即第一组参考位置与实测位置的纵向差。板端如实拒绝超出范围的输入。

从各机首末采样的 `sim_timestamp_ns` 和 PS 采样墙钟核对，八核组的仿真时间与墙钟之比中位数 **0.808**，四核组为 **0.281**，上一轮正常的允许改期组为 **1.000**。现有代码按 PS 墙钟推进参考轨迹，仿真物理却随 AirSim 时钟推进。持续给整个仿真器限核会同时减慢物理，并让参考与飞行状态拉开。这是结果解释中必须控制的因素。`ping()` 的超时和输入超出训练／量化覆盖范围可以分别出现。

## 短时加压的实测

独立 Blocks 重新启动，默认 CPU 分配下准备路线。板端进入运行后，只在三个短窗把 Blocks 限到四逻辑核，每次 153～166 ms，之后立即恢复。控制程序运行满 **32.004 s**，四机留到测量结束，六机因保持期限到期退出。运行中未记录输入量化越界。各机的仿真／墙钟速率比中位数 **0.974**，速率统计窗口随各机退出而不同。

- 4,618 条发布中，4,551 条发出带序号的命令，67 条在下发前丢弃。7 条 `ping()` 等待超过 20 ms，均出现在约 4.07～4.16 秒的发布阶段附近。最长 **61.309 ms**。
- 在同一份日志上，两种时刻都满足初次触发条件 2 次，只有 `ping()` 满足 4 次，只有采用时刻满足 1 次，两种都不满足 4,541 次，另有 2 次不确定、1 次仅有目标写入。100～400 ppm 钟差敏感性下，三类触发的确定数量一致。
- 真实系统尝试改期 20 次，装上 4 次。其中 18 次尝试追溯到按采用时刻不满足初次触发的命令，包括 Drone3、Drone8 已装上的两次 20→40 ms。对这两条命令，采用时间区间跨过了任务截止，但可以确定「输出转换到采用耗时超过 20 ms」这一条件不成立。

Drone10 最清楚。第 204 周期的 `ping()` 等了 **57.223 ms**，飞控在命令提交后 **9.316～13.300 ms** 就已用上，确定赶在任务截止前。板端仍按慢 `ping()` 把下一次的下发预留抬到 **57.283 ms**，原周期只有 **20 ms**。后续 8 次改期尝试均未安装，其中 7 条对应任务的派发日志明确记录了这笔预留造成的预算不足。这台飞机最终到期退出。这里已经观测到晚确认影响后续调度的链条。即使改正触发条件，工作线程等待返回的时间仍须单独处理。

同一轮也有真正晚用的命令。Drone2 的第 203 周期，`ping()` 等了 **25.714 ms**，飞控却在提交后 **52.470～56.451 ms** 才用上。它在任务截止前到达 AirSim，但在目标写入和固件更新之间又等了较久。这种情况需要缩短实际采用链路。两个例子都发生在有意施加 Windows 压力的对照中，历史自然长尾的具体原因依然未知。

下一轮应先把「命令采用」与「收到回话」分开接入 \(T,c,\sigma\) 日历，用相同压力验证改期触发和后续预算是否更合理。采用确认要按序号配对，未获得采用证据时继续保留现有期限保护。采用仍频繁迟到的样本可以用来设计机载轻量控制对照。

## 复算和边界

本轮原始记录在 `controller_architecture_study/results/ps_trace_pressure_20261124_001/`。`*_audit.json` 对应原始板端时钟和带序号的模拟固件记录，`*_comparison.json` 是在同一条已运行时间线上复算的两个触发条件。[复算源码](../airsim_command_timing/replay_retime_trigger.py)

```powershell
$out = 'controller_architecture_study/results/ps_trace_pressure_20261124_001'
python -m controller_architecture_study.airsim_command_timing.replay_retime_trigger --trial "$out/run_pressure4/trial" `
  --audit "$out/run_pressure4_audit.json" --output "$out/run_pressure4_comparison_recheck.json"
```

短时加压用 [PowerShell 入口](../airsim_command_timing/run_ps_trace_pulses.ps1)，传入独立 Blocks 的进程 ID 和本线板端套件位置。记录在 `run_pulse4.json`、`run_pulse4_audit.json` 与 `run_pulse4_comparison.json`。
