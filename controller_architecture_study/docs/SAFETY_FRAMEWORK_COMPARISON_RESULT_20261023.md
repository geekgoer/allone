# 2026-10-23 多机框架对比：阶段结果与下一步

## 结论先行

**尚未得到“FALCON-style 基线撞门而新框架安全完成”的有效证据。** 当前已完成启动配置修复、分段推理实现和一次 8 机静态候选校准；新方法在同一选定配置的名义工况下仍有截止时间中止，因此没有启动预先规定的 16 组扰动配对发现，也没有做确认实验。

这是当前实现/时延模型未通过，不是“超网训练失败”，也不能据此断言整个研究方向不可行。不能把“新方法零碰撞但中止”当安全完成，更不能把 T25/T50 超载时的静态碰撞当作有效 FALCON 安全性反例。

实验协议见 `SAFETY_FRAMEWORK_COMPARISON_PROTOCOL_20261023.md`。以下均为 Windows/AirSim/CPU 先导实验，不是 FPGA、DPU、严格 CBF 或完整原文 FALCON 的验收。

## 1. 已完成的实际工作

- 通过独立 `-settings=` 配置启动 12 架真实 AirSim 无人机；已查询启动 settings 和 listVehicles 双重确认。未覆盖 Documents 下的原三机配置。
- 用户要求仅运行命令后，没有再进行屏幕操作。
- 实验从 12 机 T50 过载诊断收敛到 **8 架实际参与飞行的无人机**；其余启动 pawn 未作为活跃控制回路或成功样本计数。
- 现有三个 237D 网络可以按最多两个 FC 的层段运行、暂停、恢复；不改模型权重、不训练。层段用 TorchScript 编译，两种策略完全相同。
- 共享推理是一个独立 CPU 进程中的 worker，不是每架一份并行推理；IPC 计入响应时间。
- 修复了整批采样阻塞 ready-output 的处理方式；采样和特征生成现在属于释放后的 control job，不再叠加无关的每机高频轮询。
- 发现在 `plain_mlp_h9_w512_seed0` 的 2225156 个参数中，有 462873 个非零 float32 次正规值。显式开启 CPU flush-denormal 后，离线小模型耗时由约 1.3 ms 降到约 0.26 ms。三个模型各 32 个相同随机输入的开/关对照，物理输出最大绝对差均为 0。权重文件未写回。
- 分段/独立上下文/分段抢占/启动保护/失败计分等 7 项单元测试通过。真实三模型的编译分段与 eager 整网所检查输入逐位一致。

这些是有限数值检查，不是全输入一致性或闭环安全证明。现有环境的 pynvml FutureWarning、pytest 退出时的 pyreadline 析构异常未造成测试失败。

## 2. 门洞与任务规模

“1 m / 0.75 m”已确认是门洞**净宽**。早期 1 m 三机无扰动试飞本身就碰撞，不能解释为调度策略缺陷。当前使用净宽 2 m、净高 4 m，立柱厚度 0.15 m；没有缩小原 Pawn 的碰撞模型。

固定任务取 environment 48 / route 1 的既有参考，从相位约 5.9355 s 开始，持续 3 s；每架预期通过 gate 3 和 gate 4。8 机成功应为 16 次有效穿越，不是 8 架各飞五门。

## 4. 同配置的新方法：为什么尚未通过

`calibration/framework_nominal/report.json`：

- 请求 229 次，施加 221 次，6 个输出过期未施加；另有 2 个 ready 结果在任务结束/关闭时没有用于飞行。
- 4 次命令 RPC 返回越过承诺截止时间。
- 碰撞 0，但 6 架因截止时间过期中止；仅 Drone3、Drone5 完整通过两个门。
- worker 累计计算约 235.39 ms / 3 s。
- 释放选择最大 overhead 约 **0.0671 ms**，不是搜索开销巨大导致失败。
- 规划器记录的预测不可行次数为 **0**，与实际多次超期不一致。

失败集中在约 2.40–2.47 s、接近第四门时：

| 无人机 / 请求 | DNN 计算 ms | 实际提交晚于计划 ms | 提交时剩余预算 ms | 算完后等前端处理 ms | 处理时超期 ms |

| Drone7:25 | 1.29 | 45.53 | 9.89 | 9.96 | 1.73 |
| Drone1:26 | 0.75 | 43.04 | 12.39 | 31.15 | 19.75 |
| Drone2:26 | 0.77 | 41.72 | 13.71 | 25.97 | 13.30 |

**可直接支持的诊断**：DNN 计算不是这些请求的主要耗时；计划释放到真正开始处理、以及 ready 输出到命令发送的前端等待，比 DNN 计算大得多。当前释放可行性检查主要模拟计算 worker 的已承诺任务，再加一个固定前端预留，未正确反映共享串行前端和后续释放的拥塞。不能用 `estimated_feasible=True` 代替真实可调度性。

**源码审计还发现**：处理 ready 输出时，`now` 在命令 RPC 之前读取，RPC 返回后直接用于下一次规划，可能用旧时刻模拟未来可行性；下一版本需要改为 RPC 返回后的新时刻。它是应修复的时间记账问题，但不能在未复测前断言是全部失败的唯一原因。

预算的保守程度也可能影响请求密度，但目前不能为了得到成功就放宽物理截止时间。若替换预算模型，必须明确新的动力学/扰动假设、另起版本，不能在发现挑战结果后偷偷调阈值。

## 5. 下一步：只修时间/调度实现，不重新训练 DNN

本轮 v1 的源码身份已冻结；后续改动应另建 v2 结果目录，不能覆盖或与 v1 混跑。

1. 修复命令返回之后的时间记账，使下一次释放规划使用最新时刻；继续保留原始物理截止时间，不允许过期后重新计时。
2. 将端到端响应模型落实为：新状态采集 + 特征构建 + IPC + 共享推理排队/执行 + 命令发送/返回 + 前端调度等待。不能仅用 DNN 服务时间推断资源可行性。
3. 先用保守的完整-job 成本做小规模、有明确上限的可行性检查；只有能够对应真实日志的模型才用于最新释放选择。无需增加 RL、能耗模块、训练新超网或立刻扩展 Vivado。
4. 先让同配置的新方法通过 8 机名义任务；若无法满足，应报告不可行或采取明确的任务接纳策略，不能用悬停/中止伪装穿门成功。
5. 通过后再跑完整预声明 16 个场景×2 个方法，保留所有负结果；若发现差异，再增加新重复、邻近初值和最快静态对照。
6. 正面结果若只依赖候选网格缺少中间周期，要扩展静态局部搜索；若只依赖 Windows 桥接瓶颈，不得外推为 FPGA 的调度优势。

不要缩短 AirSim 持续控制命令来强行释放 RPC worker，除非先验证控制语义。本机 SimpleFlight 的 `api_goal_timeout` 默认仅 60 ms；短命令结束后长期未刷新可能自动转入悬停，形成隐式 fallback，破坏对比。
