## 在同步过载时一次算出至少要换多少

限定同一同步批次、任务均已就绪、一个整任务串行执行器。模型资格由外部给出。对任务按绝对期限排序。在第 (k) 个期限之前，要求：

```text
开始时刻 + k × 大模型成本 − 已降档数量 × 每次节省时间 ≤ 第 k 个期限
```

这个不等式给出每个前缀至少要换多少条任务。每遇到一个新缺口，从当前前缀中尚未降档且合格的任务中补足所需数量。每次换模型的节省相同，因此在这组条件下总降档次数等于所有前缀要求的最大值。若某个前缀的合格任务不足，该组在这个串行执行模型中不可行。对少量任务的穷举与该规则的可行性和最少降档次数一致。

回放使用双常驻连续与交替各自完整响应 P99 的较大值，ID 11 为 1.334864ms，ID 6 为 11.788443ms。该成本已包含模型分派和交替场景样本。采用首批板端实测同步到达记录，等所有本批请求就绪且至少留 0.5ms 决策时间后启动，实测抽取的各批均在 0.5ms 内到齐。三种策略使用相同启动时刻。请求原周期是 50ms，附加短期限及模型资格为对照假设。无批前在途任务，共 840 案例。通用 A/B/C 采用原有八次局部修改预算。

| 12 路同步场景 | 固定大模型 EDF | 通用 A/B/C | 前缀分配 | 前缀分配最少换为小模型 |
| --- | ---: | ---: | ---: | ---: |
| 都是 50ms 期限，小模型均合格 | 0/60 | 0/60 | 60/60 | 9 |
| 都是 50ms，3 条必须保留大模型 | 0/60 | 0/60 | 60/60 | 9 |
| 都是 50ms，4 条必须保留大模型 | 0/60 | 0/60 | 0/60 | — |
| 1 条限期 5ms，其余 50ms，小模型均合格 | 0/60 | 0/60 | 60/60 | 9 |
| 4 条限期 5ms，小模型均合格 | 0/60 | 0/60 | 0/60 | — |

12 路全大模型需约 141.46ms 串行工作。9 小 3 大加预留约 47.88ms，8 小 4 大约 58.33ms。原通用规则最多改八次，所以在这组高负载场景连最少需要的九次修改都无法完成。前缀分配一次构造完整配置。全部切到最快合格模型可以达到相同的时序通过数，前缀规则的额外作用是保留最多的大模型调用。这一目标是本轮选型取舍，未假定大模型具有更好的实际控制表现。对于非同步释放、部分工作在途、执行时间跨状态变化或多执行器，需使用相应时序检查。

## Windows 到板端的 UDP 状态

Windows 有线口 `192.168.77.1/24`，板子 `192.168.77.2` 两次 ICMP 回应 1–3ms。使用交付的原版 IP37/1 客户端，两种模型在 UDP 5237 的首个黄金请求都超时，见 `results/ip37_windows_20261106_attempt2/`。交付记录明确临时验证服务随后停止。当前 Windows 的 SSH 批处理没有可用认证，无法直接从此端确认进程或启动服务。已有 Ubuntu → 板端黄金结果继续作为独立证据。

在板端 SSH 或串口终端运行以下命令，若已有 237D 服务在 5237 运行则先核对它的模型池和 READY 信息：

```bash
cd /home/root/board_package_quant_v2_main18_v1
out_dir=$(mktemp -d /home/root/ip37_windows_XXXXXX)
./pool237_runner serve \
  --pool 'main18_plain_mlp_h4_w1024_seed0,main18_plain_mlp_h33_w1024_seed0' \
  --inputs inputs_raw.txt --warmup 100 --port 5237 --out "$out_dir/service"
```

出现 `READY family=independent237 protocol=IP37/1 port=5237` 后，保持该终端运行。接下来先从 Windows 分别发 32 条黄金请求并记录网络往返，随后在现有 237D 控制链上做只读影子推理。实际期限和控制资格核对通过后，再判断是否适合闭环接管。
