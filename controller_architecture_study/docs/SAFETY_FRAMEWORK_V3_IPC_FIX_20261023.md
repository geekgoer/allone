# v3：Windows IPC 人为等待的修复

v2 的源码和结果已保留在 `results/safety_framework_comparison_v2/n8_net2`，其中 `frozen_source` 与该轮 setup 中三个源码哈希一致。

## 已重现的错误

主机独立测量空 Pipe 的轮询等待：

| 调用 | 实际等待中位数 | p95 | 最大值 |
|---|---:|---:|---:|
| `Pipe.poll()`（非阻塞） | 0.0122 ms | 0.0194 ms | 0.0714 ms |
| `Pipe.poll(0.0005)` | 15.4691 ms | 16.0661 ms | 16.1022 ms |

此前子进程收到任务、交给推理线程后，又用第二行等待下一条消息，等轮询结束才收取已有推理结果。因此“设置了 0.5 ms 超时”实际给控制链加入了约一个 Windows timer tick 的等待。v2 的静态 T150 完整-job 日志中，DNN 约 1 ms，却出现约 10–22 ms 的常见完整 job 时长及更大尾部。

## 唯一的 v2→v3 运行逻辑改动

子进程控制路径改为：非阻塞排空输入 → 排空 ready 输出 → 高分辨率 `time.sleep(0.0005)`。本机该 sleep 的独立测量约 1 ms；不再把有超时的 Pipe 等待插在结果交付之前。

启动等待、结束清理中的长 poll 不在试飞计时控制路径内，不需要无关重构。没有修改门、无人机碰撞体、DNN 权重、B、安全期限或成功条件。

已加入回归测试，要求控制路径只能非阻塞轮询：旧代码复现失败，改后与全部其他测试一起通过（10 项）。

## 连续批次

v3 使用 v2 已声明的完整-job 成本模型和单在途任务限制。顺序脚本自动完成：三模型×六周期及邻域静态校准 → 同配置动态名义验收 → 通过后才进行全部 16 组配对扰动 → 有干净差异才做新重复确认。任何阶段未通过即停止，清理并保留数据。

结果另存 `results/safety_framework_comparison_v3`，不能与 v1/v2 的时延数据混算。测得的成本仍是预测估计而非 WCET，有限飞行成功也不等于形式化安全或 FPGA 验证。
