# 七机动态未救回：时序开销量化

2026-10-26。只分析已有记录，并对保存的状态做离线函数计时；没有新试飞，没有修改控制逻辑、模型、门或扰动。

## 核心判断

**当前最明确的问题是：动态原型要求短周期，但执行流水线没有兑现这一要求；同时，释放规划低估了完整响应成本。DNN计算不是主要耗时。**

在已证实低负载可以恢复的Drone1对应场景中，七机动态在收到危险观测后，还要等待旧任务的命令、命令后状态回读、完成通知和主线程处理，之后才释放新任务。监测进程已有的新状态没有直接作为这次DNN输入，新任务又重新采样。首个新鲜控制直到扰动后57.22ms才返回，低负载两次成功约16.56/16.97ms。

这是已确定的时序障碍，尚不是“删掉某一项开销就必定救回”的因果证明。低负载与七机也存在资源负载、空间放置及闭环历史差别，不能把约17ms当作数学安全阈值。

另有一处原型假设需要纠正：响应预留约7.19ms，实际七机响应明显更长。不能用这个偏乐观的原型来否定framework本身。

## 分析对象与计时口径

详细拆分17次既有飞行：七机持续反馈批次9次，低负载诊断8次。原始59次试验全部保留，未重写。

- 当前DNN是CPU上的冻结237D、9×1024模型，推理线程位于逻辑CPU14；前端12、命令I/O8、观测10，分别属于不同物理核。不是GPU或FPGA推理。
- `R`：父进程请求控制输入采样，至命令RPC加顺序ping返回。它不是纯网络时间，也没有独立测到执行器真正生效的时刻。
- CPU DNN时间：完整FC/ReLU段的时间之和；段间停顿与首次排队单列，避免把等待算进DNN。
- 命令更新间隔：相邻两次命令RPC返回之差。不能直接用命令行的T替代。
- 主对照窗口为扰动后0.4秒：七机动态有11个新鲜输入任务，单回路20ms两次成功各20个。该窗口结束时尚未观察到本例碰撞，避免用碰撞后的运行解释碰撞原因。
- 全程均值、危险窗口均值、首个关键任务的数值分别报告，不能混用。对应七机动态的三项R分别为22.91ms、18.03ms、20.31ms。

## 1. 响应时间到底花在哪里

下表为上述危险窗口的平均值；低负载列按两次成功任务数加权。所有分段无重叠，逐任务相加与实际R闭合，误差检查容限1微秒。

| 部分 | 七机动态失败 | 低负载20ms成功 | 七机增加 |
|---|---:|---:|---:|
| 输入请求分发、线程等待、状态/碰撞查询 | 2.90ms | 1.55ms | 1.36ms |
| 采样完成后的通知、回传、前端等待及状态处理 | **7.91ms** | **1.62ms** | **6.29ms** |
| 237D特征生成及提交间隙 | 0.65ms | 0.43ms | 0.22ms |
| 推理输入传递、任务建立及首次排队 | 0.49ms | 0.42ms | 0.07ms |
| **CPU DNN计算** | **2.42ms** | **1.69ms** | **0.73ms** |
| 段间停顿 | 0.38ms | 0.16ms | 0.22ms |
| 推理完成到命令开始发送的处理/分发 | 2.58ms | 1.03ms | 1.55ms |
| 命令RPC与顺序确认 | 0.71ms | 0.53ms | 0.19ms |
| **合计R** | **18.03ms** | **7.41ms** | **10.62ms** |

七机多出的10.62ms中，采样结果完成后的交付与前端处理贡献约59.2%，CPU DNN计算增加只贡献约6.9%。这不是说其余成本都与硬件无关，而是不能把完整R全部当作DNN执行时间。

危险窗口内推理器首次排队平均约0.14ms。整个七机动态任务中，FC段累计执行时间约占物理窗口41%；这不含工作进程IPC、归一化和调度，也不是操作系统CPU利用率。结合短排队来看，目前不像是“FC计算把推理核完全占满”导致主要失败。

## 2. 一个关键控制为什么直到57ms才到

下列均以扰动写入RPC返回为0，来自`Drone1:34`及其前序任务：

| 事件 | 扰动后时刻 |
|---|---:|
| 监测服务开始获取该条危险状态 | 7.85ms |
| 该观测消息已被父进程接收 | **11.88ms** |
| 前一个任务的命令RPC返回 | 15.18ms |
| 前一个任务的命令后状态回读结束 | 16.27ms |
| 父进程拿到前任务完整结束通知 | **25.44ms** |
| 将危险事件落实到下一任务计划 | 27.30ms |
| 下一任务实际释放 | **36.90ms** |
| 新控制输入的采样调用开始 | 38.40ms |
| 输入采样完成 | 39.69ms |
| 输入结果被父进程接收 | 45.46ms |
| 特征处理开始/完成 | 49.50/50.11ms |
| DNN开始/完成服务 | 50.49/54.19ms |
| 控制命令RPC返回 | **57.22ms** |

11.88ms是观测消息接收时刻，不是独立记录的风险计算完成或调度生效时刻；该条检测函数自身约0.53ms。不能把“收到危险状态”写成“此刻已经成功释放紧急任务”。

前一个任务使用的是扰动前约1.64ms获取的状态，直到扰动后15.18ms才下发其控制。这里的“旧输入”指扰动前状态，不自动等于违反某个输入年龄限制。

程序直到收到**完整命令后状态包**才从`pending`中移除前任务。于是新的任务被以下等待串起来：

1. 从危险观测接收到前任务完整完成通知，约13.57ms；其中包含剩余旧任务工作、命令后回读和通知等待，不能全部称为纯调度开销。
2. 从完整完成通知到安装事件，约1.86ms。
3. 从事件安装到实际释放，约9.59ms。
4. 新任务请求采样至命令RPC返回，约20.31ms。

最后20.31ms里，CPU DNN计算仅3.26ms，首次排队0.13ms、段间停顿0.44ms。采样结束至父进程接收已花5.77ms，再到特征开始又花4.04ms。

**危险已经有观测了，DNN却没有立即得到这条状态，新的控制工作也没有立即开始。** 目前已有的EDF作用于各队列的选择；事件循环仍把新任务释放放在命令、监测和输入处理之后，跨处理类别的优先级并没有完全贯穿整个流水线。

## 3. 为什么请求20ms，实际仍约40ms

本例危险后0.4秒的相邻命令返回间隔平均约34.30ms；成功的低负载两次约19.98/20.02ms。

一个具体间隔，从前条命令返回57.22ms到下条返回99.10ms，合计41.87ms：

| 组成 | 时间 |
|---|---:|
| 前条命令之后再读状态/碰撞 | 1.71ms |
| 该状态完成到父进程获得完整通知 | 6.85ms |
| 已满足计划时刻及前任务完成条件后，到下一任务释放 | 11.48ms |
| 实际释放到发起采样 | 0.01ms |
| 下一任务采样至命令返回 | 21.83ms |
| **合计** | **41.87ms** |

这一条下一任务请求周期确实是20ms，没有主动要求等待40ms；但循环必须先收齐前一任务反馈，再处理队列，实际已经做不到20ms。

固定20ms诊断对照则还会因旧周期来不及执行而跳过旧释放、等待下一个日历位置。两种现象不同：一个受串行完成和释放延迟限制，一个还包含固定日历跳过的等待。CSV将两者分开，未将正常等待一律称为浪费。

## 4. 释放规划的成本预留确实偏低

此批原型的预留方式是：

`response_reserve = DNN各段经验估计之和 + 固定4ms`

Drone1七机动态这次为7.187ms，实际全程平均R为22.910ms，危险窗口平均R为18.032ms。固定4ms没有覆盖七机观测、采样交付、前端等待和命令处理。

在碰撞前的0.4秒内：11个新鲜输入任务全部超过这项预留，**6个任务实际释放时期限已过**，11个命令均晚于其原有期限返回。首个关键任务释放时已比原期限晚13.56ms。

全程2009/2009个已应用任务超过预留，175个释放时期限已过；这些全程计数包含碰撞后的运行，不能用来扩大对首次碰撞的解释。超过启发式响应预留也不等于违反D=T，二者统计口径不同。

这里没有完整的端到端可行性准入证明，只是持续周期原型的释放提前量。为了完整观察，过期工作仍执行并记录，程序没有暗中把期限延后。因此当前结果暴露的是**原型的执行成本模型与实际运行脱节**，不是framework已经证明不可行。

## 5. 其他开销也已量化

**观测并不免费。** 本例12.27秒内，检测函数累计墙钟约2.695秒，相当于物理窗口的21.96%；单次约0.636ms。周期/预算规划本身累计约占2.66%，单次约0.162ms。这里是记录到的累计函数墙钟，不是CPU利用率，不能把等待区间和函数时间再次相加。

**重复RPC很多。** 按代码和任务窗内日志推算，本例约1682次AirSim API调用/秒，正常七机约1715–1723次/秒，低负载20ms约399次/秒。控制任务一次先读状态和碰撞、发送命令加ping、随后又读状态和碰撞；监测进程另读状态和碰撞。该计数排除初始化及注入器临时调用，是API调用估算，不是网络抓包，也不能等同于板端UDP频率。

**风险判断重复算了较重的参考姿态。** 使用128条保存状态、相同CPU核、无RPC的离线计时发现：

| 函数 | 每次平均墙钟 |
|---|---:|
| 完整单点参考，含姿态计算 | 0.238ms |
| 给定缓存参考后的风险计算 | 0.025ms |
| 原参考生成＋风险判断 | 0.284ms |
| 只算所需p/v/a，悬停时保持原姿态回退的候选 | 0.188ms |
| 原状态评价与日志构建 | 0.333ms |
| 原237D特征生成 | 0.368ms |
| 状态消息编码＋解码，不含IPC传输 | 0.030ms |

候选在这128条状态上h、ḣ、转弯压力和边界选择一致，数值差为0；包含悬停回退时平均减少约34%。它**尚未部署到控制程序**。离线微基准没有复现七机并发负载，不能直接用这些值替换实测R或声称节省了多少端到端时延。

编码解码的离线量级远小于关键任务5.77ms完成交付等待，故不能简单把整段都归因于JSON。当前日志没有“助手准备发送/发送结束”的完整时间戳，无法将这5.77ms进一步严格分成助手轮询、IPC和父进程调度，更不能全部叫网络慢或GIL慢。

## 6. 换成FPGA会怎样

当前CPU计算在危险窗口R中约占13.4%。FPGA可以改变DNN执行成本、权重访存和执行器调度行为，但不会自动修正以下软件依赖：

- 等命令后状态包完整回传，才允许下一任务进入；
- 已有监测状态只用于判断风险，DNN又重新请求采样；
- 主事件循环迟迟没有释放已具备执行条件的紧急任务；
- 用DNN估计加固定4ms替代完整响应预留。

从首个关键任务的当前账本机械扣掉3.26ms新DNN计算，命令仍约在扰动后53.96ms返回；这只是说明这一个直接加速项的量级，**不是预测全系统替换成FPGA后的真实结果**。硬件改变会同时改变其他任务与排队，最终必须实测。

## 7. 下一步按什么顺序修

1. **先校准完整响应与更新间隔成本。** 区分输入采样→命令返回的R，以及命令之后还会阻塞下次任务的反馈路径；不再只预留DNN＋4ms。不要通过延后旧期限来掩盖不可行。
2. **解除不必要的串行门槛并复用新鲜观测。** 区分命令确认和后续状态回传，避免等完整反馈才安排下一轮；评估用公共观测提供DNN输入，保留状态年龄、命令时间和碰撞记录，避免重复查询。当前任务的模型/输入仍固定，不需要加新模块或改成段内抢占。
3. **让紧急程度贯穿前端和命令路径。** 不能只保证DNN段队列顺序，却让紧急任务释放排在大量监测/记录处理之后。把纯记录工作移出关键路径，并复用参考计算。
4. **仅补必要时间戳。** 记录助手状态包准备发送/发出，以及父进程开始处理输入的时刻；用它区分现有完成交付间隙，不先铺新一轮大网格。
5. **修复后只复核已确认可恢复的Drone1场景。** 双方使用相同优化后的基础设施和核心数，正常静态候选需重新校准，再做固定周期、仅段EDF、动态周期/优先级的完整配对。

暂不重训DNN、不增加超网训练、不扩大扰动强度。原Drone7较强场景在低负载20ms下也失败，不能将其直接当作“只要调度够好就该救回”的案例；本次没有快速MPC对照，不能声称它物理上不可恢复。

当前B仍是距离/速率原型，关键计划中的B约147ms，并非已验证的安全时间。20ms要求来自另外的紧迫度规则；不能把这些结果解释为严格CBF安全保证，也不是原始FALCON完整最优配置的复现胜负。
