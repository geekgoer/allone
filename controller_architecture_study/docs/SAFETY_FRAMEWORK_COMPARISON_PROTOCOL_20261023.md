# 多机状态感知框架对比：实验协议与边界

日期：2026-10-23。研究重点已从“超网是否必要”转为“平均控制性能最优的静态配置，是否会忽略个别回路的瞬时物理风险”。本文件是实验协议，不是成功结果声明。

## 1. 这轮要回答什么

在同一组真实 AirSim 无人机、同一批 DNN、同一路径、同一门洞和相同共享计算资源下：

1. 离线按总体控制性能选择、且名义工况调度可行的静态配置，面对个别无人机的初始横向速度偏差，是否发生碰撞？
2. 状态预算驱动的下一任务释放与分段 EDF，能否完成同一任务而不碰撞、不靠中止或悬停冒充成功？
3. 若有差异，静态方法能否通过一直使用更短周期解决？为此确认阶段加入“名义工况中最快的已测可行静态配置”。

不预先保证存在所希望的差异。没有发现差异、双方都失败、只有 RPC 超期导致的差异，都必须保留。

## 2. 基线是什么，不是什么

原始依据：本机 `E:/BaiduNetdiskDownload/vitis-ai6.1/tmp/pdfs/FALCON.pdf`。关注 Eq. (4) 的状态跟踪性能、总体性能优化及 `R <= D <= T` 约束。

本轮使用 **FALCON-style 受限近似基线**：

- 无 SVM/SVR 性能代理；实际飞行测量性能，并在有限候选中搜索。
- 离线选择网络、周期、相位、固定优先级；运行时不根据瞬时风险改变这些配置。
- 同一 CPU worker 依次执行真实 DNN 的层段，层段之间按固定优先级选择任务。
- `D = T`，校准候选必须在完整名义任务中无超期输出、无 RPC 返回越过截止时间、无碰撞且仿真时钟有效。
- 候选集合受限、硬件固定、没有复现完整原文设计空间，因此不称为“FALCON 全局最优”或“完整 FALCON 复现”。

性能采用 Eq. (4) **形式**：状态为位置 3D、速度 3D、四元数 4D；四元数先同号对齐。对共同 20 ms 网格上的 K=20（21 个状态点）窗口计算加权误差和，再对窗口成本取平均后求倒数。各回路等权求和。

原文完整数值权重不明，本轮明确使用 `Wx = I10`；额外的跨窗口聚合方式也是本轮定义。因此不能声称数值 J 与原文直接可比。早撞/中止的任务 J 记为缺失，不能因累计误差较少而得到更高奖励。

## 3. 新方法的最小实现

保持每架无人机所选 DNN 与静态基线一致，先隔离**时间与调度链**的贡献：

`当前状态 → 门附近的预算 B → 下一任务绝对截止时间 → 至多3个释放候选 → 层段 EDF → 新控制输出`

- 预算是门附近的距离/速度包络原型，包含机体包络和额外间隙；不是 Yang-style CBF、不是严格安全证书。
- 预算以观测时刻锚定，不因决策晚了而重新计时；截止时间不能在过期后自行延长。
- 最大控制更新约束使用 150 ms 原型上限；这里不是已证明的全状态控制安全上限。
- 释放规划只模拟已承诺的单次任务，不包含无限未来任务的可调度性证明。
- 服务时间来自实测包络加保护量，不称 WCET；预留共同前端/RPC 时间。
- 任务内网络配置不变，只能在层段边界暂停/恢复；不同任务的激活和输入互相隔离。
- 没有 MPC fallback；动态任务过期触发中止，明确算失败，不算“安全完成”。

发现阶段前的 n8 名义 pilot 测得旧轮询前端 enqueue 到命令 RPC 返回最高约 42.2 ms，原 31 ms 预留不足；75 ms 预留曾使控制提交过于密集，也未全部通过。移除无关轮询后，当前原型固定 50 ms 前端经验预留（另加 DNN 服务包络和释放保护量），并只为单点跟踪指标生成 1 点参考、为真正 DNN 请求生成完整 21 点参考，避免重复工作。释放预留不是全局时延上界，**绝对截止时间仍不延长**。所有调试 pilot 只能用于运行时校准，不计作挑战场景的确认结果；这些失败必须保留，不能挑一次偶然成功作为证书。

这是整个框架中时间/调度部分的组件级先导实验。尚未验证完整 State-to-Mode Map、超网、FPGA 加速器或严格 Safety Analyzer，不可把单次成功表述为整个框架已证明。

## 4. 公平资源与实际规模

使用 12 架**实际参与飞行的 AirSim 无人机**，不是给 3 架飞机加 9 个空客户端。出生/门组横向间隔 12 m。

三种已有 237D plain MLP：

- `plain_mlp_h9_w512_seed0`
- `plain_mlp_h21_w512_seed0`
- `plain_mlp_h9_w1024_seed0`

模型来自 `results/decision_convex_recovery_scenic_falcon18_v1/runs`；不修改权重，不重新训练，不读取 test split。

两种方法都使用一个真实 CPU worker、同样的每段最多 2 个 FC（及其 ReLU）。worker 位于单独的 Python 进程中，与 AirSim/RPC 前端隔离 GIL；不是每架一份并行推理。IPC 延迟计入端到端响应时间。不能只给新方法分段能力而把基线强行当整网不可抢占。已有整网/分段逐项一致性检查与独立上下文、层段抢占单元测试。

每个层段用 TorchScript 编译执行，减少逐算子进出 Python 的干扰；不改变已有权重和网络结构。与 eager 整网输出的一致性须独立核对，两种调度方法使用同样的编译层段。

Windows 原型将当前 Python 进程的 GIL 切换间隔统一设为 0.5 ms，并在实际推理线程预热；这不是修改操作系统、不是实时保证，也不是给某个方法专用的优化。纯推理与并发前端下的执行时间差异需区别，不把 Python 调度伪影解释成 DNN 本身的 MAC 成本。

小模型发现 462873 个非零 float32 次正规权重（2225156 个参数中）；CPU 的次正规数处理会显著影响耗时。当前主线程和实际 worker 都显式采用 `torch.set_flush_denormal(True)`，不写回权重文件；部署身份中记录该数值运行方式，另以同输入对照检查输出差异。不得把 CPU 数值慢路径解释为 FPGA 计算成本。

这是 CPU/Windows/AirSim 的框架试验，不将结果解释为 FPGA 的容量、DPU 切换成本或 PL WCET。场景没有人工 sleep 注入的加速器负载。

## 5. 门洞尺寸与参考任务

用户所说的 1 m / 0.75 m 是**净宽**。旧门框生成器接收的 width 是立柱中心间距；因此传入 `净宽 + 0.15 m`，立柱厚度 0.15 m，净高 4 m。

1 m 净宽在三机无扰动 pilot 中也碰撞。碰撞接触点表明当前 Pawn 的横向碰撞包络约为 0.48 m 半宽；现用 0.50 m 原型包络及 0.025 m 额外间隙。这不是全姿态严格几何证书。不能继续用旧 0.2 m 假设将几何不可行伪装成基线失败。

所以先测试净宽 2 m。若有必要再独立测试 1.5 m，且必须重新通过名义工况、重新校准静态配置。当前包络下 1 m / 0.75 m 不适合作为控制方法公平比较，不能擅自缩小机体碰撞模型。

参考取已验证的 environment 48、route 1 的已保存轨迹，参考相位约 5.9355 s，任务窗口 3 s，巡航约 5 m/s；每架预期穿过 gate 3 和 gate 4。成功是 12 架共 24 次有效穿越，**不是每架飞完五门全程**。

任务从同一物理状态开始（仅指定目标无人机施加协议中的初始偏差），不是中途 teleport 的飞行。初始放置在计时前、暂停仿真时完成，并检查位置/速度/姿态读回。

## 6. 预先规定的流程

### A. 名义工况检查

可选的固定小模型 T150 smoke 只用于排查基础设施，不假定它就是合适的工作点，也不假定 50 ms 是固定或必需的周期。正式流程先做静态候选校准，再要求**选定配置**的新方法名义工况也完整成功、时钟有效、没有超期输出；否则不能进入挑战结果的安全优势解释。

### B. 静态受限搜索

先测最小候选网络的共同周期 25/50/100/150 ms，再测另外两个网络的共同 T150。选有效候选的最高总 J，继续测相位翻转、优先级反转、末位回路改网络及相邻周期。

这是单轮有限邻域，不是假装穷举。最终也要求选定配置对应的新方法名义工况通过，才冻结进入挑战阶段。

### C. 配对发现

预先固定 16 个初始偏差场景：

- 目标无人机：最高/最低固定优先级两端（Drone1、Drone12）；
- 横向方向：正/负；
- 初始横向速度偏差：0.6/1.0/1.4/1.8 m/s；
- 同方向初始位置偏差 0.05 m。

每个场景两种方法都运行，交替顺序，32 次任务全部保留。不能只报告碰巧赢的场景。

“干净的差异”要求：基线实际碰撞、新方法完整成功；双方仿真时钟有效、无执行异常、无超期未施加输出、无命令 RPC 返回越过各自截止时间。普通碰撞、调度失败、状态保护中止分别记录。

### D. 冻结确认

完成全部发现后，若存在干净差异，固定第一个场景，额外做 3 组新试验，初始位置在原值附近 -1/0/+1 cm；顺序平衡。若名义工况最快静态候选与总 J 最优候选不同，再加入该静态对照。

3 组只是阶段性复核，不构成高可靠性或普遍性证明。若无差异，输出负结果，不捏造确认试验。

## 7. 数据与解释边界

每次保存初始状态、配置、每架轨迹、采样时刻、请求、队列/层段执行、释放决策、物理碰撞对象、完整任务判定和 J。

注意：单前端逐任务交错执行 ready-output 收取、释放时的新状态采样和下一请求构建，不能把 ready output 压在整个 N 机采样批次之后。**状态采集是 control job 的一部分，不再另外为每架飞机维持无关的 100 Hz 轮询负载**；前端的任务提交顺序也分别遵循固定优先级/EDF。末尾额外采样直到覆盖统一任务窗口。碰撞标志在这些采样时检查，事件标志会锁存，但碰撞发现延迟随采样间隔变化，不能据此声称首次触碰的精确时刻。状态采集不是零成本，日志记录 dispatch 时样本年龄。控制命令是 AirSim 异步命令加 ping 返回，属于 RPC 时间代理，**不是精确的物理执行时间戳**。实机安全时间证明还需要真正执行确认或相应不确定性界。

记录 worker 实际占用、任务数及规划 overhead。不能仅以新方法较少 miss 声称更优，还要同时看完整穿越、碰撞、任务进度、状态跟踪及计算开销。若更快静态对照也能安全完成，结论应收敛到动态方法的资源/性能折中，而非“静态必然不安全”。

12 架飞在同一仿真进程，共享机器噪声；不能把同一次任务的 12 架当成 12 次独立系统重复。校准只覆盖名义分布，本轮挑战是初始偏差泛化；尚不能声称优于对扰动分布充分优化的强鲁棒 FALCON-style 基线。

## 8. 启动与恢复

已提供 `controller_architecture_study/configs/airsim_safety_12.json`。通过 UE4 的 `-settings=` 参数加载，不覆盖用户 Documents 下原三机配置。

不要使用 `simAddVehicle` 把已启动的三机 Play 扩成 12 机：本机 AirSim 按启动 pawn 数加 4 创建 RPC worker；运行时新增不会扩容。暂停时发送多个持续控制任务可占满 worker，使解除暂停也无法执行。此外，运行时 pawn 不进入旧 scene-object 位姿缓存。

脚本现在读取启动 settings 验证，缺少 startup vehicles 时在 reset/新增前拒绝，不再盲目补建；异常输出与清理失败单独留存，不计入控制方法优劣。任何 RPC 失效后先检查，不循环重试。

用户已明确要求后续只运行命令，不操作电脑屏幕。
