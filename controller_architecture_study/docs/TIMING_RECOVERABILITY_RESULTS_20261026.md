# 完整航程时序实验：已经找到“及时更新能救回”的场景

日期：2026-10-26。

结论：固定同一个DNN、同一初态、同一参考路径与门宽，已经复现了较长等待下撞门、较短等待下完整通过并恢复的情况。这证明这些状态并非控制器本身无法恢复。它是时序机制的实验证据，尚不是完整动态框架战胜FALCON离线最优配置的证据。

## 结果

下面是确认批次的全部18次飞行，不含前面的筛选批次。

| 条件 | 完整恢复成功 | 发生碰撞 | 实测平均R |
|---|---:|---:|---:|
| DNN，T=20ms，初始剩余等待为6T/7 | 4/4 | 0/4 | 3.90ms |
| DNN，T=80ms，初始剩余等待为6T/7 | 0/4 | 4/4 | 3.99ms |
| DNN，T=20ms，初始立即采样 | 2/2 | 0/2 | 3.98ms |
| DNN，T=80ms，初始立即采样 | 2/2 | 0/2 | 3.82ms |
| DNN，T=40ms，自然响应，初始等待6T/7 | 1/1 | 0/1 | 3.81ms |
| DNN，T=40ms，加入响应等待，初始等待6T/7 | 0/1 | 1/1 | 20.97ms |
| 原MPC教师，T=10ms，初始立即采样 | 2/2 | 0/2 | 3.59ms |
| 原MPC教师，T=20ms，初始立即采样 | 2/2 | 0/2 | 3.84ms |

20/80ms主要对比使用两种困难状态，每种各做两次交替顺序复核，四个配对的初态完全一致。碰撞来自AirSim专用碰撞API及新事件时间戳，实际对象为第2或第3门的侧框。所有18次都执行到预定航程结束，包括发生碰撞的组；没有用查表缺记录或迟到提前结束。

固定T=40ms的R对比只是一个确认配对。较慢R通过显式等待构造，模拟额外通信/排队时间；它不是本轮实际测得的多机争用或FPGA时延，不能这样引用。

## 这个结果说明什么

1. **确实存在时序敏感、能够被及时更新救回的状态。** 原MPC与固定DNN在较短周期下都能完成，不能把这些状态笼统归为“教师也救不回来”。
2. **首次更新相位很重要。** 在6T/7的初始等待下，20ms组约21ms就收到首次命令返回，80ms组约73ms才收到。若初始立即更新，80ms也能通过。因此不能声称“80ms一定会撞”；更准确的问题是危险出现后，还允许保持旧控制多久。
3. **满足普通截止期并不等于物理安全。** 确认批次的四个80ms碰撞组，以及40ms/约21ms响应的碰撞组，都没有各自的名义截止期超时。反过来，少数快速组出现了偶发迟到，继续运行仍完成了任务。这正是本次保留迟到、让飞机飞完的价值。
4. 仍然不能断言现有B计算已经足够准确，也不能断言当前动态调度已完成救回。本轮没有使用B决定更新或用状态表选择模型。

性能函数也有保留：使用现有同口径的Eq4形式、Wx=I和20ms公共评估网格。两个“初始立即更新、双方均安全”的配对，T20/T80的J分别为0.140740/0.133046、0.163548/0.154100（该J越高越好）。这是各一次飞行的观察，而且较短T使用了更多计算资源，不能称为资源公平的整体框架优势。碰撞组的J保持缺失，没有拿碰撞后的残缺任务补算漂亮分数。

## 实验范围与公平性

- AirSim保持12机启动配置，但本轮每次只有一架执行试飞，其余未参与共享推理负载。**这不是七机/十二机竞争实验。**
- 固定模型：`plain_mlp_h9_w1024_seed0`，原237D输入与配套归一化。模型及全部六个模型库的SHA256复核一致，没有训练或修改权重。
- 参考轨迹：已有environment 48、route 1的连续C2曲线，参考巡航约5m/s；不重规划或改变参考时钟。
- 两种初态来自已有困难状态，横向位置偏差±0.05m、横向速度偏差±1.1m/s，原有姿态与held control保留。分别从航路中段开始，执行全部剩余3/4个门，再观察终点3秒；不是从起飞点开始的五门任务。
- 门洞净宽2m、高4m，未为本轮缩小门洞。沿用无人机半径0.5m与0.025m余量判据，并同时保留实际网格碰撞。
- 正式运动阶段不暂停物理，不中途重新放置无人机。初始化和预热在暂停状态完成。
- 完整恢复要求：飞完整个规定窗口、无碰撞/飞行异常、全部目标门有效穿越、向前推进，最后250ms位置误差≤0.3m且速度误差≤0.6m/s；未降低判据。
- 首轮筛选给终点1秒观察，所有组仍在减速，恢复判据未通过；原结果完整保留。确认批次统一给双方3秒观察，没有把首轮未通过改成通过。
- R从状态请求开始计到控制RPC返回，包含采样、碰撞查询、特征、推理、等待和发命令，是生效时间的可观测代理；没有硬件上的精确控制生效时间戳。
- 主要快速组平均R=3.90ms、p99=5.30ms，但最大R=34.04ms，并出现1次名义截止期迟到。CPU和Windows不是硬实时环境，不能用平均R充当安全上界。
- CPU亲和性使控制线程与Unreal使用不同物理核；不是操作系统独占核或FPGA等价时延。结束后已恢复亲和性、删除临时门框，AirSim保持Play且未暂停。

## 对框架的直接建议

**不必继续以“补齐硬编码格子”作为实验前提。** 先固定c已经得到清楚的时序因果证据。之后若要选c，可用连续状态评分/回归替代严格分箱，对覆盖不足的状态采用事先指定的基准模型并标记为探索；换成连续模型仍需验证，不能自然变成安全证明。

**T不必局限40/80ms。** 40/80ms原先是经验适用范围。本轮已经运行20/40/60/80ms。现有时间接口可以接受更细粒度的周期或直接指定下一次release时间，没必要再增加一张离散T表。

**B是上限，用户的理解是对的。** B=120ms时在80ms内更新完全允许；B=30ms时要限制的是等待加响应，不能仅让T≤30ms。例如从同一时间原点计算，若预留R上界8ms，采样前最多还能等22ms；若预算已经消耗了一部分，还必须扣除已过去的时间。当前distance/rate原型不能作为严格安全证书。

下一步只接回一个必要环节：用本轮确定的两个困难状态做同资源七机配对。静态基线应先在独立正常开发场景中搜索并冻结(T,c)，不能直接把本轮故意选的80ms叫作“FALCON最优”。动态侧保持同一DNN或同一候选库，允许提前下一次更新、在FC分段边界调度，查不到模式时使用预声明默认分支继续观察。记录完整安全结果、实际R/首次等待、B是否真正约束决策和同口径J。先验证危险回路获得及时更新是否有用，不新增训练或复杂选模器。
