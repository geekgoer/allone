# 最新动态撞门：模型、周期与软件等待的区分

日期：2026-10-28。对象是上一阶段 `physical_deadline_observe_seed4` 中的 Drone1、Drone3。它们仍使用 `plain_mlp_h9_w1024_seed0`，不是已为 Drone9 筛查的小模型。

## 结论

不是一个原因，也不是“排序算法计算了几十毫秒”。现有证据支持：

1. **十机软件流程没有落实请求的20ms更新。** 撞前两秒，两个回路的新命令实际平均隔31ms才返回，最长间隔74ms/67ms。即使提前进入快速模式，飞机也没有获得所请求的更新频率。
2. **控制器与更新时间的组合不合适。** Drone1原模型在单机、低响应延迟下，20ms两次都碰门；同模型改为10ms，两次通过。因此不能说它完全不能飞，但20ms不是这条路线下足够稳妥的已验证选择。
3. **Drone3的共享流水线等待是一个重要影响因素。** 它在十机中碰门，原模型单机20ms通过。这排除了“这个模型在这条路线必然无法通过”的说法，但一次通过不构成普遍安全证明。
4. **原型没有把每个模式经过验证的更新时间范围落实为调度约束。** 提前预警已生效，1/3号在约0.53秒就请求20ms，后续没有过早降频；但原模型不变，最小请求周期固定20ms。通用80ms更新上限及几何B不能替代该模式在困难路线下所需的更紧控制更新要求。

所以主问题是：**选了一个对更新时间较敏感的控制器组合，软件运行又进一步拉长了实际更新时间。** 局部模型误差会参与轨迹偏移，但不能将这两次失败全部归因于“训练没训练好”。

## 现有十机日志的时间账

以下窗口仅取各自碰撞前两秒，不把碰撞后的悬停或工作量下降计入：

| 指标 | Drone1 | Drone3 |
|---|---:|---:|
| 请求的周期 | 20ms | 20ms |
| 实际命令更新间隔，平均 | 31.00ms | 31.23ms |
| 实际命令更新间隔，最大 | 74.08ms | 66.59ms |
| 输入采样开始到命令确认，平均 | 10.58ms | 10.70ms |
| 分段DNN计算，平均 | 1.81ms | 1.83ms |
| 策略分析，平均 | 0.387ms | 0.400ms |
| 命令在已承诺期限之后确认 | 9次 | 8次 |
| 计算需求保护判为不可行 | 0次 | 0次 |

策略分析包括预算、路线预览与模式/周期决策，不是独立测量的EDF排序CPU时间。不能把其余等待统称为“排序耗时”。

将连续两条命令之间的间隔按真实时间戳拆开，平均值可以准确相加：

| 上条命令返回 → 下条命令返回 | Drone1 | Drone3 |
|---|---:|---:|
| 上条命令后的采样、回传及前端处理 | 3.43ms | 3.50ms |
| 反馈处理完后，按计划主动等待 | 8.80ms | 7.95ms |
| 已到计划时间、反馈也已处理完，仍等到任务真正释放 | 10.25ms | 10.65ms |
| 新任务释放到命令确认 | 8.45ms | 9.05ms |
| 合计 | 30.93ms | 31.14ms |

此表纳入窗口中第一条命令与其窗口外前驱的完整间隔，和上表仅在窗口内取相邻命令的均值有轻微差异。每个单独间隔的拆分误差为0。

“主动等待”本身不是代码耗时，也不应全部删除。额外问题在于：到该运行的时候，前端还没释放任务。代码最多允许3个任务同时在整条采样—计算—命令反馈流水线中在途；只有前一个任务的命令后反馈完成处理，才释放该回路的下一个任务。即使DNN计算核暂时不忙，采样、回传、前端待处理项目仍可占住名额。

根据在途任务的释放与完成处理起止时间重建，上述额外释放等待中，Drone1约42%～58%、Drone3约44%～60%落在三个名额已占用的时间段。范围来自完成处理内部实际移除时刻未单独记录；它是近似占用重建，不是严格CPU竞争归因。其余部分还混合前端工作次序、IPC和操作系统调度，现有日志不能进一步精确分配，更不能断言全是EDF排序计算。

这说明纯DNN利用率未超100%，并不代表完整控制通路能及时给出下一条命令。

## 新补的隔离试飞

保存同一份种子4路线、速度5m/s、门洞净宽1.7m、全状态初值与全局参考时钟。每次只启用一个闭环，以去掉其他回路的排队；几何仅随独立测试场地平移。没有外加扰动、没有人为插入延迟、没有修改权重、没有把碰撞后的状态计作正常飞行。

| Drone1 | 原9×1024 | 10ms | 3.35 / 3.39ms | 两次均完成8门与末尾跟踪 |

| Drone3 | 2×128 | 20ms | 2.15ms | 完成8门与末尾跟踪 |
| Drone3 | 3×256 | 20ms | 2.21ms | 完成8门与末尾跟踪 |
| 两条路线 | 教师MPC | 10ms | 3.07～3.42ms | 各次对照均完成 |

共14次独立重置试验，包含5次教师对照；Drone1另做10ms→20ms反序复核。所有保存的仿真/墙钟比通过原有检查。原模型10ms的两次实际命令平均间隔约10.08/10.05ms，20ms约20.00/20.04ms，不是只改了打印参数。

这不是严格控制每一个响应时间样本的数学单因素实验；Windows抖动及模型计算耗时仍存在。因此：

- 能说原模型的周期/实际更新时序确实影响通过结果；不能宣称精确安全分界必然就是10ms或20ms。
- 换小模型同时改变了控制函数与计算耗时，不能把改善百分之百归到精度或速度之一。
- 教师与DNN使用相同训练教师定义。不能只凭教师10ms通过，就说教师20ms也通过；本次没有做这个推断。
- 这些是两条保存路线的有限经验，不是十机新策略已经验收。

此外，Drone1原模型20ms在第8门中心平面瞬间的偏差仍满足原有几何阈值，但约0.115秒后仍接触门框。无人机有体积，穿过中心平面不等于整个机身已离开门框厚度区域。这也是保留真实碰撞API、不能只看“8/8平面穿越”的原因。

## 精度是不是也有问题

将失败十机轨迹中**实际用于推理的同一状态、同一参考**重放给训练教师与三个模型：

- 原模型预测和日志控制输出最大差约9.54e-7，说明这批记录没有发现输入编码或checkpoint不一致。
- 训练教师参数及源文件哈希与数据清单一致。
- Drone1原模型标准化控制MSE从前段约0.00234上升至撞前两秒约0.03519；Drone3约0.00261上升至0.03156。后段横滚角速度输出RMSE约0.142 / 0.135rad/s。

因此确实有局部控制近似误差，且随失败轨迹进入困难状态放大。但**这是沿失败轨迹的对照，不能证明训练数据缺失，也不能把误差放大与时延造成的状态偏离完全拆开**。

在这些相同失败状态上，两个小模型的平均MSE反而更大，尽管它们从共同初态独立闭环飞行可以通过。它们形成了不同的后续状态轨迹。这个结果直接说明：不能用一条失败轨迹上的平均MSE排名替代恢复/闭环资格，也不能说通过的小模型必然更准确。

## B与FPGA分别能解决什么

当前B仍是几何/速率启发式，不用实际held control和完整动力学推导。以Drone1为例，记录中10.58秒附近B仍为150ms，10.78秒附近约80ms，接触时已降到0。当前规则没有证明飞机能在剩余时间内刹住横向运动，也没有证明该DNN在允许更新间隔下可恢复。

“命令及时返回”与“返回的控制足以安全穿门”是两个条件。可以不增加显式DNN误差界，但至少需要给所选c配套已验证的更新/延迟适用范围，不能对所有模型统一假定80ms以内就够。

FPGA有改善希望：原DNN在现实CPU的10ms请求、约3.4ms平均响应下能通过，证明并非只能依靠不现实的零延迟才能飞。但不能保证只加速DNN就能救回：

- 原十机中DNN计算均值仅约1.8ms，采样、反馈回读、前端待处理与任务释放等待仍在。
- 若仍固定20ms最小请求间隔，不能保证通过Drone1这条对更新时间敏感的路线。
- 硬件也可能通过降低在途占用连带改善排队，所以不能简单“减掉1.8ms”预测最终收益；必须测迁移后的完整通路。
- FPGA不会自动修正B的动力学含义、模式适用域或当前控制函数。

## 后续只需聚焦的改动

1. 将c与已经通过的实际更新/延迟范围配套；不盲目加大DNN，也不先重新训练。
2. 针对上述约10ms额外释放等待处理整条流水线的名额占用及反馈依赖；20ms/10ms是否落实要看真实命令间隔，不能只看请求参数。
3. 若要让原9×1024在该Drone1路线继续使用，应让10ms成为经资源检查的候选，而不是全机一律降到10ms；也可选已通过20ms的模式。
4. 模式变化后重新检查共享任务集，再做同模型候选池的静态/动态配对。当前没有新增一次完整十机救回成功的结论。
