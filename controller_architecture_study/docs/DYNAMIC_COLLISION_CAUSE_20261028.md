# 当前动态撞门：原因、时间预算与硬件加速的作用

后续实现、模型筛查与期限检查结果见[本阶段处理报告](ANTICIPATORY_REPAIR_AND_DEADLINE_STATUS_20261028.md)。本文保留修复前的诊断证据。

本诊断针对2026-10-28最近的十机异质路线试验，不将结论自动推广到此前所有七机／十二机试验。本次读取既有轨迹、配置与时延记录，并做相同状态下的离线控制输出对比；没有启动新飞行、训练或修改运行规则。

## 结论

周期调整、完整两层FC之间的有限抢占、静态优先级／EDF执行、独立核心与采样／命令通道已经实现。**不能称整个调度框架已完成验证**：本批没有随状态切换c，没有逐job保证完整流水线的截止时间可行，也没有严格的动力学安全时间分析。

近期失败不能全部归因于“DNN没选好”，也不能全部归因于Windows开销。已有证据分别支持：

1. 现有动态规则识别部分转弯偏晚，且在同一组连续转弯中多次过早降频。
2. 当前9×1024 DNN在特定末门路线存在局部控制偏差；取消多机争用、周期缩短到10ms仍发生接触。
3. 计算利用率筛选不等于满足逐job响应时间上界；本批为了观察完整飞行允许迟到输出继续施加，故不能说“已经满足T+R≤B却仍然撞门”。

不能从这些观察分配各因素的因果百分比，也不能断言任意更早预警或任意FPGA一定能／不能救回。

## 1. 预警与周期变化：确实有实现问题

三个几何种子中，Drone9均有以下时间线：

| 时刻 | 事件 |
|---|---|
| 约5.14s起 | 第一弯即将进入DNN已有的未来2s参考窗口 |
| 7.14s | 保存的参考轨迹实际开始第一弯 |
| 约8.10～8.13s | 动态策略首次为该机请求20ms周期；此前一直请求60ms |
| 约8.47～8.49s | 已经处于转弯段，策略再次请求60ms |
| 约9.17～9.18s | 再次请求60ms |
| 约10.47～10.49s | 末门前又请求60ms，随后才回到20ms |
| 种子2约10.986s、种子3约10.947s | 动态Drone9实际接触第8门左框 |

规划时刻由既有观测时间线插值对齐，精度受约20ms观测采样及RPC时间影响；轨迹段起点7.14s来自保存的多项式定义。

原因在`probe_seven_continuous_timing.py`：

- `mode_is_difficult`检查当前路径管道余量及0.4s后**单个点**的参考加速度；阈值为2.5m/s²。
- 种子3第一弯参考加速度峰值约1.990m/s²，因此单靠该加速度规则不会对第一弯提前触发，约8.1s才由第二弯预览触发。
- `desired_periods[v]=target if difficult else .060`会在该布尔条件解除时直接请求60ms。当前连续风险公式原本得到的较短周期，可能被这个分支覆盖。
- 同一机的cruise和recovery都被设为`plain_mlp_h9_w1024_seed0`；名称切换没有产生不同控制器。

种子3该机的计算需求筛选从未因超载放宽周期；最高估计负载约0.748，低于0.95上限。几次放宽时负载约0.567，`relaxed=[]`。因此这里不能解释成“硬件忙不过来，被迫降低危险无人机频率”：是当前启发式规则主动放宽。

这是当前实现的不足，不是T+R≤B这个公式强迫出现的结果。它支持改进提前识别和保持恢复模式；但不能单凭时间线证明提前改T就能避免所有碰撞，因为单机始终10ms的同模型也会碰撞。

## 2. 控制器能力：确有证据，但不能归因于所有DNN

既有低延迟检查使用同一路线、门尺寸和初态，无其他回路争用、无人工延迟，仿真与墙钟比约0.999：

| 控制器 | 请求周期 | 平均采样至命令RPC确认R | 实际命令间隔p99 | 结果 |
|---|---:|---:|---:|---|
| 凸QP MPC教师 | 10ms | 3.006ms | 12.260ms | 8门通过、末尾跟踪通过 |
| 9×1024 DNN | 20ms | 3.374ms | 22.657ms | 第8门左框接触 |
| 同一DNN | 10ms | 3.129ms | 12.110ms | 第8门左框接触 |

MPC和DNN的10ms组更新时序接近，MPC能通过，说明此路线并非物理上完全无法通过。现有证据不支持把DNN触门完全归因于共享计算排队。也不能由10ms失败推断R更小或5ms更新一定仍失败：这些尚未测试，几毫米到几厘米的裕量变化就可能改变接触结果。

进一步将该DNN失败轨迹中的一组状态交给六个既有网络与训练教师，在**相同状态、相同未来参考**下离线计算输出，避免只比较不同闭环轨迹上的控制量：

| 路段时间 | 选定9×1024相对教师的标准化输出MSE |
|---|---:|
| 5～7.14s | 0.000208 |
| 7.14～8.4s | 0.001344 |
| 8.4～9.66s | 0.007002 |
| 9.66～10.9s | 0.042353 |

末段body_rate_x的物理RMSE约0.160rad/s，平均有符号偏差约−0.107rad/s。训练教师的代码SHA256和规范化后的参数签名均与当前离线教师匹配，未用不同教师设置制造误差。

这证明存在局部控制函数偏差，不只是“同一输出来晚了”。但误差上升也可能与进入较难状态互相影响，尚不能据此单独断言训练数据缺失、结构不够或某个实现环节就是唯一原因。六个网络在末段均有偏差，21×1024在这些记录状态上较好（MSE约0.035911），但**离线MSE更好不能证明它接管后会安全**。

这次没有为框架加入DNN误差界，也无需为了诊断而增加一个新的误差建模模块。

## 3. 时序机制跑通，不等于约束已得到保证

本批动态结果存在502／492／421次截止时间失约。为了完整观察撞门与恢复，本批运行启用了`allow_late=True`，迟到输出仍会作用；碰撞只退出对应回路。

当前实际实现是“按B和风险规划时间，并记录是否满足”，不是“所有请求均已证明并执行T+R≤B”。静态／动态均保存失约记录，没有把超期删除后报成功。

计算需求筛选主要检查`sum(C_i/T_i)≤0.95`。它没有保证每个job的采样、前端、段间阻塞、通信和命令确认均在自己的截止时间前完成。

种子3的Drone9末门接近段（9.66～10.92s）中：

- 平均采样至命令RPC确认约7.092ms；
- 纯DNN分段计算累计平均约1.520ms；
- 该区间实际命令更新间隔p99约61.123ms，最大约62.235ms；
- 单机该策略分析平均约0.284ms，配置分析并没有消耗几十毫秒。

命令间隔大的一部分来自策略自己选择60ms，并非把7ms的R全部归为加速器运算。将观测到的计算时间从R账面扣除，剩余约5.572ms，涉及采样、IPC、前端、队列及命令通道；这只是固定其他记录分段的记账比较，不能当作实际FPGA的R下界，因为硬件迁移后队列、重叠与通信也会改变。

## 4. T+R≤B是更新期限，不应承担整个未来轨迹预测

若B_k表示从当前控制u_k生效时起，其在当前状态下还能安全保持的时间，则应首先核对：

```
下一控制实际生效时间 a_(k+1) − 当前控制生效时间 a_k ≤ B_k
```

当T_k定义为从a_k到下一job释放的等待时间、R_(k+1)为从该释放到下一控制生效的完整响应时间时，才直接对应：

```
T_k + R_(k+1)^ub ≤ B_k
```

若T采用常见的“释放到释放周期”，则实际生效间隔为`T_k + R_(k+1) − R_k`；不能混用时间原点。本项目以命令RPC返回作生效代理，尚未观测真实执行器生效时刻。

窗口短并不是逻辑错误：可以每次保证下一次更新前的安全，连续执行。前提是B确有相关动力学／保持输入下的安全含义、约束确实被执行、后续控制能够维持安全且后续更新仍有可行解。当前距离／速率原型不具备这些完整条件。

反过来，及时运行一个无效控制器也不会自动安全。B作为更新期限，不会自动告诉系统哪一个DNN足以恢复，也不会自动把整个后续路线规划好。

Yang–Belta–Tron 2019的safe period针对已知动力学与当前保持不变的实际控制输入；本文Definition 4及Section III.C可作为以后改进B的依据，不能把当前经验速率B直接等同于该论文保证：

https://calinbelta.com/wp-content/uploads/2024/01/Self-triggered_Control_for_Safety_Critical_Systems_Using_Control_Barrier_Functions.pdf

“约束太苛刻”和“发现危险太晚”应区分：前者意味着把本来可安全等待的情况判成不可行，后者意味着错过了提前调整控制／资源的机会。当前原型在不同状态可能同时有这两种问题，不能通过统一放宽B解决。

## 5. 不增模块的改进方向

保留B作为短期更新约束，在已有状态／模式判断中复用DNN已经读取的未来2s参考：检查一段即将到来的连续转弯，而不是只检查0.4s后的一个点。进入恢复配置后，依据已有跟踪误差和运动趋势判断是否恢复，再放宽周期，避免一次加速度低于阈值就降频。

提前识别可以为T、c和段间优先级的调整留出时间，但不是保证。当前同一模型单机10ms仍失败，故下一步还需确认有哪些现有c在该类状态下可用，再把它们作为动态候选。同时把端到端响应预测与已承诺job的截止时间对账；不需要重新加入大规模(T,c)搜索或显式DNN误差界。

## 6. 迁移FPGA后的判断

| 因素 | 仅加速DNN是否直接解决 |
|---|---|
| 神经网络计算与由其引起的排队／段阻塞 | 有望改善，取决于真实加速器与调度粒度 |
| 0.4s单点预览、2.5阈值、转弯中重新60ms | 规则不改就仍存在 |
| 同输入下神经网络控制函数的局部偏差 | 精确执行同一函数不会直接消除偏差；更快更新可能间接改变轨迹 |
| Windows采样、进程通信、AirSim RPC及网络传输 | 不会因为替换计算核心自动消失，需要重新测完整R |
| 姿态响应和已有控制恢复能力 | 不由纯计算加速自动保证 |

所以FPGA上仍**可能**发生当前类型的碰撞。也不能反向声称FPGA一定会撞，因为更短R、较小抖动和更高更新频率可能改变临界场景的轨迹。本批不是硬件反事实试验，不能从CPU轨迹直接预测最终FPGA成功率；不得套用早期12D／25D模型的板端时延当作当前237D时延。
