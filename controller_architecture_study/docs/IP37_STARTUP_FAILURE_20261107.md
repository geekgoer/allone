## 结论和证据

首轮多机入口在 `origin = 当前时刻 + 0.5秒` 预留初始化时间，却提前解除物理暂停。日历要等到origin才释放第一条任务，飞机已经开始运动。原 `hoverAsync` 在本轮没有维持预设悬停。两组第一次真实采样时，飞机已经下坠1.01–1.29m、向下速度3.92–4.62m/s。

板端在正常响应；status=3是它主动拒绝越界输入，不是通信超时。失败向量中的237D索引9/19/29对应前几个参考点的相对高度分量，本轮达到约2m以上，量化码超过127。Windows本地按原归一化和实际input scale=8计算，也复现相同越界。拒绝保护本身不能删除或改成静默裁剪。

三机各自的“初始暂停样本→第一次飞行样本”都多出约0.490–0.495秒模拟时间。扣除这段启动空窗，实际飞行样本之间的模拟/墙钟比为0.992–1.007；原汇总2.39–3.27的异常比值不能理解成模拟器整体加速了三倍。

成功输出的释放到返回P99分别约10.53和14.99ms，均低于本轮50ms周期。动态组30次建议均为 `already_feasible`，没有周期改变，不能用这一短暂、起点已失配的失败判断动态算法收益。

## 修复

1. 初始化仍在暂停期间进行，并显式提交经现有标定转换的悬停推力/零角速度命令，ping确认提交；不依赖 `hoverAsync` 作为保持控制证据。
2. 预留的0.5秒在物理暂停状态下等待，到了日历起点才解除暂停并开始释放。若初始化耗尽预留，保持暂停并报告启动失败，不带错误起点开始飞行。
3. 保存实际解除暂停的请求、返回时间；初始状态、轨迹时钟和日历使用同一个起点。
4. 单机退出原因直接打印，并把非碰撞错误纳入顶层errors。脚本遇到输入/运行异常会保存汇总、打印原因并停止后续组，不再让两组失败却只显示空errors。
5. 全部飞机均退出时结束该组，避免无意义等待剩余20秒。
