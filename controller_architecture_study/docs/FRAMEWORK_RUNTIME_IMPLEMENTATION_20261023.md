# Framework 的 Windows 实现与验收边界

## 目标与不变项

按 `D:/Chrome下载/Framework_latest.md` 实现状态到 controller mode、动态绝对 deadline、有限次全局释放检查、分段 EDF。先在 CPU/AirSim 上落实逻辑；不把它称为已经部署的共享 FPGA，也不声称已有 CBF 安全证明。

不重新训练、不改写现有模型，不引入 DNN–MPC 误差变量、RL 或新的在线全局 J 优化器。旧 v1–v5 结果全部保留。

## 已实现的在线链路

当前入口输出到 `results/framework_runtime_v5`。v3为异步流水线/完成余量一致性修正版，v4把已知固定初态的第一批时间表移到暂停初始化，v5进一步在同一最多5次检查内加入错峰释放；旧版本不覆盖、不混作同一组验证。

1. 每条控制回路保存其上一条实际发送的限幅控制、发送/通信返回代理时刻及下一条已承诺 deadline。
2. 发送新控制后请求新状态，Safety Analyzer 接口接收该状态和 held control。当前仍使用距离/速率原型；接口明确标注 `uses_control_in_bound=false`，以便之后替换控制相关 safe-period。没有偷偷将当前简单预算说成严格控制相关分析。
3. 从新观测起点得到预算，生成 `min(观测时刻+B, 上条命令代理时刻+80ms)`；80ms 是本轮离线恢复协议中实际测试的控制间隔/允许等待上限。原 deadline 不因处理过慢而重置。
4. 两维 `h, hdot` 是相对保存参考轨迹的 moving-tube 特征；不同于门框真实网格距离。模型表采用合格、不合格、未知三种状态，只从经验合格集合中选实测计算成本最低者。不默认大模型更安全，不把未知当合格。
5. 模型只在下一任务选择。已释放任务保存 `frozen_model` 和 `frozen_deadline_s`，返回时再检查，禁止中途增深、增宽或修改 deadline。
6. 一个独立进程加载六个冻结 237D 模型，每任务保留独立 activation/cursor。最多两个 FC+原 ReLU 为一段，段内不可抢占，段边界按 absolute deadline 选择下一 ready job。
7. 共享 CPU 特征/分析前端、唯一分段推理进程、每条回路独立的异步采样/命令通信通道分别建模。在途上限等于本次活动回路数，每条回路最多一条未完成任务；没有让多个 DNN 同时占用推理资源。Tornado 客户端不能跨线程共享，每个通信线程独占客户端。所有策略使用相同采样与命令路径。
8. 前端顺序为：计算完毕的控制交接 → 已承诺到时释放的异步采样 → 在途任务特征计算 → 下一任务观测分析。不同在途任务之间使用同一 static/EDF 排序。新的非抢占特征计算和分析如果会挡住即将到期的输出，就暂缓；已经完成的旧任务不能因为其旧 deadline 较早，就让其下一任务分析无限阻塞仍未完成的任务。有限次释放检查采用相同资源与顺序，包含并行采样、前端、层段、IPC、命令交接、通信、一个层段阻塞和在途上限；未收到进度的 pending job 保守计完整计算量。最多五个候选，不枚举 T×c。没有预测可行安排就显式拒绝，不 best-effort fall-through。
9. 当前规划预留1ms；前端特征3ms、采样通信20ms、分析1.5ms、交接1ms、IPC收/发各1.5ms、命令返回25ms、完整通信通道占用40ms、预测完成保护1ms，释放启发式额外提前20ms。这不是WCET表：有墙钟特征/分析成本超过表值的记录，额外提前不能替代成本证明。命令返回与随后新状态读取是不同事件：只有前者受当前控制生效 deadline 约束，后者仍占通信资源并影响下一轮分析。25ms来自新协议286条命令的最大实测12.91ms并留余量；完整40ms占用没有删掉。后续停GC的135条采样里采样最大17.51ms，因此将采样预测从10ms提高到20ms，特征从1ms提高到3ms，并将提前量从5ms提高到20ms；没有改B或80ms控制上限。1ms规划预留来自失败实例重放100次测量（均值0.34ms、最大0.74ms）；超过预留时，将所有未确认完成和未来释放整体推迟相同超额量，仅在原 deadline 剩余余量能支付时提交，否则拒绝，不延长 deadline。实际各阶段超估计次数、规划耗时、命令返回超期与保守拒绝分别记录。
10. 两种策略统一处理失败：过期结果不发送，deadline/命令返回超期或碰撞就中止本次实验。悬停不是任务成功。
11. 两种策略的首批相对时间表在已固定初态/held-control的初始暂停期间准备，物理时钟启动后仅平移时间原点；首次DNN推理仍在运行窗口执行。初始化规划不冒充稳态免费计算，后续每次观测/选择/释放规划都计实际开销。物理时钟尚未启动的预测拒绝不记成实际过期。
12. v5优先尝试按EDF顺序、以输入/交接和模型成本确定间距的错峰释放，同时保留共同释放候选，总共不超过5个完整预测；不能把所有未来任务无条件重新同步到同一时刻。每个候选仍检查全局已知任务与在途任务，原deadline/c不变。该启发式不是最优release定理。

## 当前模型库

六个已有 plain MLP：hidden depth=9/21/33 × width=512/1024。来自同一237D数据与归一化合同，不修改任何检查点。

框架的模型库接口不依赖“越大越好”，也不要求一次任务中增量扩展网络。共享权重超网/PL执行器之后替换执行与配置接口；本阶段先落实任务边界选 c 和任务内有限抢占。

## 标定已经做什么

`results/framework_runtime_calibration_v2` 已完成240次恢复标定：10个 h/hdot 代表状态 × 2种路径阶段 × 2种初始等待（0/80ms）× 6模型。

连续物理时钟，所有模型使用相同控制送达目标（推理预留30ms）、80ms命令间隔。预热在初始暂停期间；第一条0ms命令也在暂停期间预计算，其他命令不能靠暂停获得实时性。

恢复需要完整窗口、无碰撞/声明的 tube 越界、有效穿门、至少80%任务进度，以及最后250ms位置误差≤0.3m、速度误差≤0.6m/s。送达偏差超过4ms会另外标为时序不可比，不能当作模型能力差。

这是有限代表点和两个等待端点，不是整个格子、所有中间等待或任意 held control 的证明。地图中的 `empirical_admissible` 只能理解为经验合格。旧逐帧暂停 v1 约慢30倍，已停止并保留部分数据，没有混入 v2。

结果：239/240 次时序可比，60个“格子×模型”条目中36个经验合格、24个有观察失败。**六个模型在本轮的合格/不合格分布相同；没有观察到“危险越高需要越大模型”的稳定结构。** 不应为制造 c 的动态切换而任意改标签。

## 必要回归与实际抢占

- 回归覆盖独立上下文、函数一致性、启动保护、真实分段调度、pipeline资源、在途上限、未知状态、仅选合格模型、deadline起点、有界拒绝等。
- 新的前端阻塞回归：紧急任务在计算即将完成时，若继续启动另一次输入采样，会挡住其输出。模拟与事件循环同时修复，不只让模拟器变得乐观。
- 实际工作线程三次抢占检查均观察到低优先级大模型暂停、小模型紧急任务先完成、再恢复；六模型分段与原 eager 输出检查通过。
- 这证明执行器确实可抢占，不保证每一次飞行都必然产生抢占。逐次报告必须记录真实 `segment_resumptions`，不能把支持抢占等同于已发生收益。

## 当前集成检查与下一步

`results/framework_runtime_v1` 保留原串行通信集成检查。最终三机正常工况曾完成，但八机出现预测拒绝，因此不能宣称已完成八机安全验收。该八机运行目录已保留 `frozen_source`，后续异步实现另开 v2，不把两个版本拼在一起作比较。

地图局部问题已完成48次新增恢复检查，保存在 `results/framework_runtime_refinement_v1`：实际达到的 h≈0.2455、hdot≈−0.2455，在固定位置/速度/路径时钟下，实际姿态与 held control 对比名义值，共24次均通过；局部代表点 h=0.225、hdot=−0.35，在两路径、两等待端点、六模型下另外24次均通过。仅新增 h∈[0.225,0.25]、hdot∈[−0.35,−0.2] 的小格子，不覆盖原 h=0.15、hdot=−0.5 的失败标签，也不扩充状态维度。开发中用过的状态不作独立最终验证。

`results/framework_runtime_v2` 单独保存异步通信版本的全部集成检查。对尾时延的 TCP_NODELAY 配对诊断没有观察到明确收益，结果在 `results/framework_rpc_nodelay_probe_v1.json`，因此没有启用此选项或改系统/依赖包。直接237D预处理省略未使用的体角速度和参考对象构造，检查结果与原特征逐位一致；两种策略均使用该优化。

`results/framework_runtime_v3` 单独保存异步采样版本；每个运行目录自动冻结10个关键源文件并校验哈希。三机试验只激活3条回路，不能因为启动列表有12架就称为12机负载。2026-10-24重启后曾恢复为3机默认启动，已获用户同意正常关闭并用独立12机配置重开，原用户 settings 没有覆盖。

曾观察到一次约53ms规划墙钟停顿，其原因未能确定。后来 `n3_net2/smoke_20261023T221426_841834Z/adaptive` 捕获到独立、明确的证据：第2代GC从1157.3627043持续到1157.4041482（约41.44ms），三条采样RPC在这个区间同时阻塞至约50ms，随后两条结果过期。这次有时间戳对应，不能把它倒推成此前53ms停顿也一定由GC造成。该真实闭环还观察到8次分段恢复。

因此新增局部执行措施：预热与显式GC在初始暂停期间完成；只在有限试飞窗口及私有推理进程的有限生命周期暂停自动GC，引用计数仍有效；主试飞进程清理后恢复原GC启用状态并记录。不是永久禁用系统GC，也没有更改驱动。线程CPU时间受Windows分辨率影响，低于一个tick可能显示0，不能解释为算法不占CPU。

额外的并发只读状态RPC配对诊断在 `results/framework_transport_probe_v2/20261023T221809_234870Z.json`：三线程、480条请求、TCP_NODELAY关闭/开启各240条。关闭时均值4.76ms、p99 6.55ms；开启时均值4.99ms、p99 6.86ms，没有启用依据。它是空闲Play下的通信诊断，不是实际飞行时延；运行中采样更慢这一事实仍保留，不能用空闲数据替换运行成本。

仿真墙钟到达3秒时，AirSim返回的状态可能仍是上一物理帧。收尾只补采首次覆盖固定窗口的状态（最多100ms），不延长待执行任务的 deadline；评分仍使用原3秒窗口。未取得窗口覆盖就保留未完成状态，不通过修改报告强行补齐。

必要集成通过后连续执行：三机 → 八机正常集成 → 新pipeline下重新搜索静态六模型/六周期及邻域 → 全部16个预声明扰动双策略配对 → 若有有效差异，再做新重复及 deadline-only 消融。不复用旧pipeline的静态最佳配置。

## 关键限制

- 预测成本来自有限实测和余量，不是 WCET；Windows及RPC没有硬实时保证。预测可行与实际按时要分别记录。
- 发送加 ping 返回只是控制生效时刻的代理，发送后状态请求也不是板载硬件确认。真实FPGA部署必须保留这一接口并测出真实链路时延。
- 现在的 B 不是严格 safe period；更新 deadline 或换更宽松 B 的假设必须另开版本，不能为通过测试改线。
- 三秒固定任务用于组件集成，不代表全五门任务、所有状态或12机容量均已验收。
- CPU代码实现完成、经验模型表存在、GPU/FPGA实时性、物理安全保证，是四个不同结论，不可混称。
