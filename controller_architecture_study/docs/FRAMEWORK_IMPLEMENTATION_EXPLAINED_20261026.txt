当前framework到底做了什么，以及为什么还没有找到安全胜例
日期：2026年10月26日

一、先澄清一个最重要的概念

FALCON式“离线方案”仍然是闭环控制。它不是离线算好一串动作，然后不看无人机状态地飞行。

这里的“离线”，是指在运行前选好DNN、控制周期和资源配置；飞行时仍然不断读取状态，由控制器计算纠偏动作。因此，静态方案本身也能纠正偏差，不是天然遇到危险就会撞门。

你的改进，是把状态反馈进一步用于“怎样分配计算”：当前情况还能等多久、这次用哪个模型、谁先计算、下一次何时更新。控制器原本就有的纠偏能力，要通过这些计算决策及时发挥出来。

第一阶段确实应该聚焦于：相同场景和资源下，静态配置来不及纠正，而动态方式及时送达控制，最终完成同一任务。这应当是一个公平、可复现的案例，而不是先把所有模块都做成最终版本。

二、当前原型的整体工作流程

AirSim状态
  → 估计当前等待预算、查询合格模型
  → 安排下一次计算任务的释放时间
  → 多架无人机共享一个分段推理执行器
  → 将DNN控制输出送回AirSim
  → 获取新状态，再进行下一轮决策。

具体对应如下。

1. 飞行与控制器

AirSim启动配置有12架无人机，主要在线实验实际使用7架。各机航道分开，研究它们竞争同一推理资源，不研究机间避碰。

沿用六个237维输入的独立DNN，输出推力和三个机体角速度。对应总深度10/22/34、宽度512/1024；代码按隐藏层计数，所以名字里是9/21/33。这几天没有重新训练或修改它们。

两种方法使用相同的保存路线。动态方案目前没有因为危险而重新规划路径，改变的是模型选择、计算顺序和更新时机。

2. Safety Analyzer：决定最迟何时需要新控制

目标接口是：根据当前状态、正在施加的控制和不确定性，给出还能安全保持多久的预算B。

在这条预算时间线里，T是下一任务释放前的等待，R是释放后到新控制生效的响应时间。你的要求是T+R不超过B；R越大，留给等待的空间就越少。单纯满足计算任务的R<T，并不等于任何飞行状态都安全。

当前只实现了距离/速率估算。虽然记录了实际控制量，但它还没有真正进入动力学安全时间推导，也没有实现Yang式CBF。因此，这部分是原型，不是安全证书。

实际期限还受已测试的等待/更新上限约束，常见为40或80毫秒，并限制输入不能过老。目前这些上限比物理B更严格；最新实验中B没有成为主导约束，所以还不能说已经验证了“动态物理安全预算”的收益。

3. State-to-Mode Map：决定这次用什么DNN

用“偏离参考轨迹的余量、正在接近边界的速度、转弯上下文”查询一张经验表，从已有合格记录的模型中选择估计计算成本最低者。

不会直接假设越危险就必须用最大模型。一次任务开始后模型固定，只在下一次任务时改变。

当前最大的不足是：表主要由有限恢复试验和成功轨迹经过的点构成，还没有充分标定成连续的恢复区域。“未知格子”只是我对“这类状态没有对应的已验证模型记录”的代码称呼，不表示飞机已经不安全，也不是你额外要求的物理机制。

遇到这种情况就中止，是我这版原型选择的保守处理，并非framework必然要求。它会截断本来可能通过的飞行，因此不能据此认定动态方法救不回来。探索阶段可以预先规定默认模型和更新规则，未知时打标并继续观察；其结果要与经过覆盖验证的运行区分记录。

4. Release Planner：决定下一次什么时候开始算

模型确定后，规划器只尝试少数释放排法，并检查采样、预处理、排队、推理和命令传输能否在期限内完成；不是每一帧穷举全部模型与周期组合。

它最多检查5个候选。当前包含错峰释放、先并行采样两路再错峰等排法。由下一任务的释放时间间接调节更新节奏，而不是一直固定50毫秒。

已承诺的截止时间不会因为排队或规划变慢而向后顺延。

5. Inner Scheduler：决定多机谁先计算

共享推理执行器采用EDF，即截止时间更早的任务优先。每个DNN按约两层全连接层切成一段，只能在完整段结束后暂停、换任务和恢复；不是随时任意抢占。

当前共享执行器由CPU模拟，前端和通信放到其他物理核心，Unreal避开这些核心。这有助于减少干扰，但Windows并没有提供独占核心或硬实时保证。

6. 控制反馈

控制输出经过检查后送回AirSim。下一轮根据新状态重新选择和安排任务。

当前没有额外的高频危险监视器。动态方式也不能凭空知道两次采样之间发生的变化，更不能保证任何危险状态都救得回来。

三、静态对照具体是什么

我没有故意选择一个很慢的模型或周期来制造失败，而是在有限候选中，按正常工况的总体J做搜索和重复复核。此前搜索了52个候选，选出的静态配置是9×1024、40毫秒周期、错峰启动和固定优先级。

这代表一个有限的FALCON式静态对照，不是原论文的完整复现：没有接上SVM，也没有完成全部硬件设计空间搜索，更不能声称它是所有静态方法中的全局最优。

四、这三天主要做了什么

首先，把模型选择、下一任务释放、分段执行和实际多机飞行接起来，补上状态、命令、碰撞及时间记录。

其次，修正了会把实验做错的问题：原碰撞读取方式会漏报；某些时延把同一段前端等待算了两遍；命令已经到达通信助手后又重复预留上游时间；部分释放候选漏掉了本来可行的排法。

然后，检查控制器是否真的有机会救回。已经找到及时接管能恢复、延后接管会失败的状态；也发现一些更强扰动在已测协议下未恢复。教师对照请求了20/40毫秒更新，计算时暂停仿真，使计算等待在仿真时间上接近零；尚不能据此断言更低周期、更低响应时间下一定救不回来。

还检查了“状态看起来相同，但当前控制已经改变”的区别，避免拿命令前的恢复结果替代命令后的验证。

当前117项代码回归通过。它们不是117个飞行安全场景，也不能当作控制安全证明。

五、当前结果能说明什么

正常七机：静态和动态都完成，J分别约4.8916和4.7770。J越大越好，动态这次约低2.34%，没有证明控制性能更好。

局部恢复：两种DNN、两种输入延迟协议、命令前后两组控制组合，共8次检查都恢复成功。但这是局部控制能力证据，不是整个在线框架通过，也没有显示大模型在这个目标点更强。

最新三个扰动配对：动态都因进入其他未知格子中止。静态两次完整通过，另一次穿门完成但末段恢复不达标。双方都没有实际碰撞，因此没有产生你要的安全胜例。

以前确实记录到过静态撞门，但对应动态也没有在同一对试验中完整达标。不能把不同场景的“静态撞门”和“动态成功”拼成一次胜利。

最近在线实验使用包含预定穿门的3秒挑战窗口，不是每次完整飞五个门。

六、为什么不是简单地找一个场景就结束

你的目标本身没有问题。第一阶段找到一个可靠案例，就足以说明值得继续研究，不需要先完成全部状态覆盖、超网和FPGA。

但这个案例至少要同时满足三件事：
  第一，静态方案自身已经会反馈纠偏，不能故意把它配置差。
  第二，危险状态确实可恢复，否则两种方法都会失败。
  第三，动态方法要实际完成任务，不能把提前停机、悬停或一次幸运结果算成救回。

真实多机里，还必须把控制及时送到。暂停仿真后证明“立即计算能救回”，并不等于共享资源排队时也来得及。

把门缩小也不必然产生合适案例，可能只是让两种方法都过不去。例如当前无人机包络直径按1米计算，还需要净空，直接设0.75米门洞就不符合这套假设。

七、哪些复杂性是我过早引入的

确实有一部分工作是必要排错，但我也过早把“找首个有效案例”和“完整六模型查表、释放规划、分段运行时、严格边界验收”绑在一起。结果是状态稍微走出已有样本，就被未知格子挡住，主问题迟迟没有形成清楚的对比。这使推进不够聚焦。

不是所有已写的工程代码都是学术创新，也不是所有验证都必须在第一阶段完成。当前成功轨迹拼格子的做法，还不足以支撑“一个区域内都合格”的判断，需要纠正，而不是继续无限补点。

更短的验证路径应当是：先限定一个很小、已验证可恢复的场景；固定同一个DNN，隔离比较固定更新与状态相关的更新/调度；得到公平、可重复的救回案例后，再打开模型选择，验证完整framework和它的额外收益。

这不是取消你的框架，而是先隔离验证动态时序这一核心作用。超网、更多模型和更大并发规模放到后续阶段，不作为首个案例的前置条件。

八、现在到底进行到哪一步

已经有：能跑的多机CPU原型、固定静态对照、动态模式选择、有限释放规划、段级EDF，以及可追溯的实验记录。

仍缺少：覆盖有效的局部恢复区域、物理B真正发挥作用的证据，以及“静态碰撞而动态完整完成”的公平配对案例。

还没有做：把这套运行时接到超网和FPGA、实现严格CBF安全时间界，或完整复现原始FALCON全部环节。

所以当前准确的结论是：原型和部分前提已验证，但你的核心实验结论尚未得到；既不能说idea已经失败，也不能说已经证明它优于FALCON。
