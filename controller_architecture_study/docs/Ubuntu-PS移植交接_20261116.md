## 4. 新模型和控制契约：这几项不能改错

| 配置 | 值 |
| --- | --- |
| 板端地址/当前UDP服务 | `192.168.77.2:5239` |
| 协议/身份 | `IP37/1`，`9253dd1fc87f8d7f` |
| 模型 | ID1～18；ID11为4×1024，当前候选示例5/10/13/8/11/6 |
| 硬件运行时 | 本包既有DNNDK/N2Cube、B1152整任务；不是VART/xmodel路径 |
| 外部输入 | RAW float32，237维；只在板端归一化一次 |
| DPU输入 | 归一化后的237维再补3个零到240维 |
| 输出 | 4个物理量 `[推力加速度, wx, wy, wz]`；m/s²及rad/s |
| 输入/输出比例 | 当前实测16/0.0625；必须读getter再次记录，不能套5238单模型比例8 |

RAW237为：当前姿态四元数4 + 当前速度3 + 21个参考状态各10维 + 20个参考推力标量。每个参考状态10维是相对位置3、姿态4、相对速度3。当前加速度虽然从状态中读取，但不在本237D特征里。不能改成273维，也不能混入12D、25D、300D旧契约。

AirSim原始状态采用每机局部NED坐标，四元数 `[w,x,y,z]`，角速度为机体坐标。237D编码进行约定的坐标符号变换和四元数符号连续处理：以 `fast_convex_preprocess.encode()` 及数值fixture为准，不能凭印象重写。参考窗口21点、间隔0.1 s，特征推力计算中的重力常数为9.8066，与某些动力学配置9.80665不同，迁移时不要“顺手统一”。

控制下发使用角速度和油门接口。**以下符号是AirSim Python API层**：roll=`u[1]`，pitch=`-u[2]`，yaw=`-u[3]`；该Python客户端内部还会取负pitch/yaw。**改用AirLib C++直接调用时应传 `u[1],u[2],u[3]`**，使最终RPC一致，不能照搬Python层参数。已有 `native_io.cpp` 正是这样处理。见 [C++复用与接口补充](C++代码复用与API契约_20261116.md)。油门为：

\[
\mathrm{throttle}=\mathrm{clip}\left(0.6+\frac{u_0-9.81}{19.62},0,1\right).
\]

控制命令异步提交，**不能等待命令duration结束才释放控制线程**。RPC返回/随后ping只作为接收返回代理，不能称为精确物理生效时刻。碰撞后只让该机退出，其他机继续，记录退出后负载变化。

## 7. 第二阶段：迁移调度器，保持算法一致

完成下列语义，再做双机固定/动态对照。先实现等价性，之后再单独研究优化。

### 7.1 时间和任务生命周期

- 全部实时绝对时间使用板端单调时钟；AirSim的仿真timestamp单独保存。不能相减板端与PC的绝对时钟来算单向时延。
- 周期由日历确定：`r[k+1]=r[k]+T[k]`，不是上一次完成后再等T。到点即发布并尝试采样。
- 当前每机一个在途槽。发布时若旧槽未完成，记录 `dropped_busy_io`；对于已过期旧任务取消尚未执行的工作，不能排队补做过期任务，也不能悄悄移动释放时间。
- 已在DPU执行的整任务不能软件撤回；超期只能禁止其迟到结果下发，等待硬件返回后释放设备。原命令已发送后才发现返回超期，也不能伪称它未曾施加。
- 分开记录计划跳过与意外丢弃；后者不能计入“启发式主动节约资源”。

### 7.2 期限与成本

已采样任务的控制返回期限：

\[
d^{act}=\min\{r+T,\ d^{hold},\ s+F,\ d^{recovery}\}.
\]

`r+T`为发布时冻结的周期期限；`s`为采样开始；`F`默认80 ms；补更项仅在欠补更时存在。

保持分析使用当前观测及**实际施加后的**控制，不使用未执行的DNN输出。现有分析的基本绝对界是 `min(sample+B, last_actuation+maximum_update)`，不能把响应时间重复扣除，也不能用旧控制的版本安排已换控制后的义务。

未来任务的采样就绪、前/后处理、不可抢占服务都需显式计入。倒推预算只是候选筛选；批准必须用全组前推和同机复用检查。只看利用率或只检查最危险一架不够。

板端重新测成本。当前每档服务时间来自历史串行板端验证，Windows在线还加3 ms网络余量；改成本地DPU后不要继续把这3 ms当作硬件时间，也不要直接全部置零。给出本地服务、采样网络、PS处理、下发网络和调度开销的新分项包络。报告观测最大值，不能把它直接改名为WCET。

### 7.3 保持当前启发式

1. EDF尾序列＋当前模型全组检查。
2. 失败时考虑允许集合中的最快模型。
3. C类再试至多两个替代队首及确定尾序列。
4. 仍失败才尝试合法的未来释放修改，后继槽同步改期；已发布槽不可重写。新采样时刻改变时，输入有效期同步改变；当前控制保持期限不延长。
5. 最后才考虑有资格的单次跳过及紧邻后继补更。
6. 可行后，按尾序列预算对下一派发任务尝试一次质量升级，再做全组检查。

最多8次完整检查、12个候选。A/B/C为启发式修复依据，不是对全部物理失败的完备分类。按TRAIN512评分选质量，不能用共同480条或后续测试集重新选最优模型；模型资格目前仍是探索池，尚非已证明的状态恢复集合。

快照带revision及提交截止时刻；**取得提交锁后重新读时钟**。提交时检查版本、当前控制和未发布槽，整组安装或整组拒绝，不能部分生效。到期仍无方案时保留原配置并记录原因，不把旧配置称为安全。发布/命令事件不能被无界求解或日志写入阻塞。

### 7.4 跳过和补更先关闭

它是撤回一个未发布任务，周期不变。后继原有任务成为必须补更的义务，不额外凭空增加一条任务；欠补更时禁止再次跳过。可以重选其DNN，但不能放宽补更期限。只有按期控制交付才清账，失败/迟到仍保留。

开发版资格是小误差、低参考速度变化和保持分析覆盖，尚未经新INT8充分实飞验证。迁移第一、二阶段默认关闭。第三阶段才做保护早弯/可保持阶段及补更期限的配对，不得把参考fixture当成物理资格证据。

## 8. PS多核与实时执行怎么处理

先做可复现的单执行器模型，不引入多DPU并行假设。可将发布/关键事件与管理规划分离，让阻塞网络、写文件、可变长日志离开发布路径。初版先明确每个线程、锁和队列的职责，再配置可用PS核；不能靠“用了多线程”就认为没有串行等待。

CPU绑核应使用Linux线程/进程亲和接口。特别注意：现有runner的 `--affinity` 调用的是 **`dpuSetTaskAffinity`，是DPU核选择，不是PS CPU绑核**；`--priority` 是DPU任务优先级，也不是Linux `SCHED_FIFO` 优先级。不能混用这两层术语。
