## 1. 先明确“完备”的范围

裁剪后的控制/调度内核可以独立导入和做数值核对，没有CPU DNN、训练、教师求解或Windows DLL依赖。此次复核发现并补回两项必要支撑：

1. `trajectory.from_layout()`：校验冻结的多项式及连续时刻，构造实际使用的参考窗口。此前这项组织逻辑主要在验证脚本里。
2. `profile.read_profile()`：核对冻结身份、部署内容和原始CSV，再读取18档成本与训练内评分。可通过 `deployment=` 显式绑定已有模型包，避免复制二进制或破坏原哈希检查。

**它仍不是一个已经完成的PS应用。** 本地DPU适配、ARM端AirSim RPC、PS事件/释放/下发循环和ARM构建尚未实现。那些职责不是冗余，也不能因为测试通过就省略。交付包中的 `COMPLETENESS.json` 将“已提供、待实现、尚未证明”分别列出。

本次的完备性是：迁移所需计算内核、接口要求、数值样例、冻结部署身份及代表证据齐备，剩余实现任务明确；不是宣称解压后即可在板端飞行。

## 2. 黄金、原始日志和CSV应该加回来

它们属于验收材料，不属于控制循环。整理如下：

| 材料 | 为什么需要 | 放在哪里 |
| --- | --- | --- |
| 18档各32条黄金输入及定点输出 | 验证接口、归一化、符号和真实DPU输出，共576条 | `reference_assets/deployment/golden/` |
| 共同480条各模型参考输出 | 重新核对模型误差和板端一致性；不是运行时输入流 | `reference_assets/deployment/validation/` |
| 8640条原始板端请求CSV及原汇总 | 追溯每档服务成本、P99/max和精度；不能只传手工抄的数字 | `evidence/release001/results/release001_board480/` |
| 黄金运行及getter原日志 | 证明实际张量比例和模型身份，与汇总哈希配对 | `evidence/release001/results/release001_board_goldens/` |
| 代表性Windows成功与失败完整日志 | 比较迁移前后的发布、输入、队列、推理、下发与丢弃位置 | `evidence/windows_reference/` |
| 三条量程拒绝RAW237 | 复现当前输入覆盖问题 | `verification_inputs/range_rejections.json` |
| 原始归一化、registry、freeze和SHA清单 | 避免使用错模型或错参数 | `reference_assets/`、`evidence/`及依赖锁 |

不带全部历史实验、训练集、旧量化模型或旧Windows执行源码。代表日志选择五轮：静止起飞拒绝、飞行中拒绝、单机真实换模成功、双机动态有一条丢弃、相同双机固定成功。目录中的原始文件按字节保留，没有改写报告或删除失败行。

黄金TXT每行实际是245列：前237列RAW输入，接4列本版INT8物理输出，再接4列同源FP32物理输出。最后8列都是参考答案，不可送入DPU；本版DPU应与第237～240列（从0计数）比较，不能误用末尾FP32四列来做定点一致性判定。

重算正式标准化MSE时，原验收程序先将 `u_std` 按float32取值，以匹配C++嵌入常量。新核对器沿用这一口径；直接拿JSON中的双精度值计算会出现约1e-10量级差异，这不代表板端预测发生变化。

原格式中各模型重复保存部分输入，是冻结参考文件的格式；为保持校验和与原始证据，这里不重排去重。它们不应被编译或常驻加载到正式PS循环。

## 6. 必须补齐的执行职责与事件契约

不要把裁掉旧Windows入口理解成可以不实现这些步骤：

1. **绝对日历**：以PS单调时钟到点发布；记录计划/实际释放。已发布任务的周期期限固定。超期任务禁止继续使用旧结果；整任务DPU运行中无法软件撤回，返回后丢弃过期输出。
2. **采样与配对**：RPC读状态，记录采样开始/返回；四元数wxyz、局部NED坐标。观测必须绑定当前实际已施加控制及版本，不能把监测旧缓存默认为最新。
3. **输入与期限**：按 `sample-origin+reference_start` 读取冻结参考，构造RAW237；计算保持界。控制返回界为 `min(release+T, hold_deadline, sample+freshness, recovery_due)`，不是只看DPU推理时间。
4. **队列与本地推理**：就绪行交给 `runtime.take()`，使用所选配置调用真实DNNDK `Pool::infer()`；归一化一次，保留饱和检查。将真实返回交给 `board_done()`。不能用CPU预测、sleep或UDP回环计时冒充本地DPU。
5. **控制下发**：再次核对控制版本和期限，按现有物理输出符号及油门转换发角速度/油门命令。异步提交，不等待duration；ACK/ping仍只是返回代理。
6. **完成与新观测**：记录命令返回，推进控制版本，使旧证据失效；重新采样绑定新控制，再归还工作槽。必须分别统计控制返回时间和后续归还开销。
7. **规划与安装**：有明确服务机会的管理任务建立有限日历，全组检查；提交锁内重读时钟/版本，整组提交。不能因规划阻塞到点发布，也不能提前松开后仍按旧快照写入。
8. **补更**：默认关闭计划跳过；启用前完成等时延资格。只有按期补更才清账；连续跳过、放宽欠账期限或把意外drop计作主动跳过均不可。
9. **记录与评价**：逐槽状态、各阶段时刻、配置、版本、拒绝原因、碰撞与身体余量。只有单机碰撞退出，不让其他机无故同时停；退出后负载要标注。

本包提供1～8中计算/状态转移的参考，硬件与OS实际编排仍待实现。当前每机单在途槽导致的忙丢弃是参考原型行为，不代表已经实现“每周期必有新控制”；移植后应测量并说明。不得通过悄悄推迟release解决它。

详细控制契约、模型身份、CPU/DPU优先级区别、真实计时和验收阶段沿用 `docs/Ubuntu-PS移植交接_20261116.md`。其中“旧入口文件路径”是追溯参考，不是新运行源码必需依赖。
