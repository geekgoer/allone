# 七机框架验证：阶段结论与下一步

> **2026-10-24后续更正：本页“实际碰撞为0”不能作为有效结论。** 低速实体接触实验证实，当前AirSim的`getMultirotorState().collision`为空，而专用`simGetCollisionInfo()`正确报告撞击。旧快照使用前者，漏报风险影响本页历史碰撞统计、模式表和安全验收；旧数据保留，但必须以修复后的专用接口重采。零记录不等于零碰撞。最新源码已使用专用接口及事件时间戳，并拒绝加载未按此接口校准的模式表。本文其余内容为发现该问题之前的阶段记录。

日期：2026-10-24。本文汇总实际执行的完整发现集、诊断消融和一次撤回的实现改动。所有失败保留；没有修改已有模型、模式表标签、门洞尺寸或绝对截止时间来制造优势。

## 先回答研究问题

**当前还没有得到“FALCON式静态配置实际撞门，而本框架安全完成”的有效证据。**

现有实现已经能够运行真正的多机闭环、固定任务配置、分段有限抢占、状态查表和有限候选全局接纳。正常七机配对曾完整通过。但本次完整扰动集里，静态方法通过的场景更多；不能把动态中止称为更安全，也不能把零碰撞当成完成任务。

这不是整个idea不可能的证明。它说明当前的模式适用域和安全时间近似还不足以支持希望得到的结论。应先修正这两个实验假设，继续增加场景数量并不能解决它们。

## 16对完整框架实验为什么失败

动态14次未通过全部为`no_admissible_mode`：12次在物理时间开始前拒绝，2次飞行中进入无合格模式格子后中止。它们不是14次碰撞，也不是14次成功避免碰撞。

静态另外8次未完整通过：4次违反配置的球形包络/额外净空穿门判据，4次任务穿越完成但末尾跟踪恢复判据未通过。AirSim均没有报告真实碰撞。三种失败必须分别记录。

完整16对的动态运行中，物理B先于80ms控制更新上限约束下一命令的次数为0。正常复核也是0/456。因此这批完整框架实验主要检验查表、更新上限和运行时集成，尚未实际检验物理B能否带来安全优势。

12对期限消融中，B实际约束了48/581次分析，危险回路的预算逐渐缩短，随后下一任务无法及时接纳而中止。这说明该机制确实能触发，但“触发并拒绝工作”仍然不是安全完成。

## 已确认的关键问题

### 1. 模式表目前不能解释成整个状态格子的适用保证

六个模型的合格/失败格子分布完全相同。没有观察到可靠的“这个状态需要更多神经计算”结构；不能强制切换大模型来补出这个结论。

现有校准采用少量代表状态、两种路线、初始等待0和80ms，然后按固定80ms节奏控制。它没有覆盖格子内所有状态、所有中间等待时间、所有实际held control，或任意变化的后续更新序列。

所以以下推理不成立：

> 两个等待端点通过 ⇒ 该格子在0～80ms任意等待与后续更新时刻下都合格。

`h`和`hdot`相同也未必意味着姿态、未来路线、当前施加控制等条件相同。第一版不必立刻加查表维度，但必须先检查当前两维表在这些变化下是否还可靠，不能把未知/已有失败的格子自动改成合格。

### 2. 预算不是控制恢复能力

当前B是门附近的距离/速率近似，虽然接口记录实际发送的控制u，计算并没有使用u预测动力学。它也不是严格CBF safe period。

按时算完不自动表示新控制能把飞机拉回来；反过来，预测拒绝也不说明物理上不可恢复。期限消融在约0.27～0.29s中止的记录属于这种区别，不能解释为FALCON已经撞而本框架避免了碰撞。

用户不希望另加DNN误差预算，本阶段没有加入。下一步先检验实际控制输出下的恢复域与允许更新时间，不需要增加新的误差模块。

### 3. 校准的安全谓词与正式验收不同，必须先统一

`framework_runtime_calibrate.rollout`在任意时刻参考管道`h<0`就提前终止，并使用`enforce_tube=True`判断合格；正式`fly`调用的`physical_report`默认`enforce_tube=False`，主要检查门平面净空、实际碰撞、任务进度与末尾恢复。

参考管道边界不等于门框实体边界，尤其是两门之间的空旷区域。因此当前模式表和最终宣称的任务成功使用了不同标准。这能解释部分“表说没有合格模式，但固定周期能完成”的现象。

这不是说应直接放宽模式表。若Framework的安全集合确实包含全程管道约束，正式运行也必须满足它；若研究目标是避开门框并完成任务，模式校准就应采用与该目标一致的几何及恢复标准。应先统一定义，再重新采集。旧试验在`h<0`后已停止，不能靠事后重命名把它们改成成功。

核对旧校准还发现两类直线代表状态存在等待敏感性：`(h,hdot)=(0.15,-0.5)`及`(0.375,1.5)`，六个模型都是立即接管通过、等待80ms未通过，共12组模型/状态记录。两端均时序可比，但80ms轮是参考管道越界后提前停止，未观察到真实碰撞。它们是后续统一判据后做等待扫描的候选，不能当成七机安全优势或“80ms一定撞门”的证据。

### 4. 运行时开销存在，但不能把所有负结果归因于Windows

已修复：完成命令的旧期限错误阻塞输入、传输过多上下文、后端重复线程、普通超时等待导致的较长释放延误。相关回归79项通过。独立推理核、前端核、通信进程、Unreal试验期间避让这些核的设置均有记录，试验后恢复。

额外尝试把多份反馈合并后只做一次全局接纳：候选代码80项测试通过，但实际正常七机动态在1.102s进入`h0_v1`，没有合格模式而中止。该次没有接纳延后，不能把失败都说成规划过慢。控制更新节奏改变会影响后续状态；只减少规划次数并不足以修复模式域问题。

候选改动已完整撤回。当前15个核心运行时文件的SHA256均与冻结v23一致；v24源码快照、失败日志、测试记录应保留以供追溯。不要将v24结果混入v23。

## 几何和实验公平性

当前净宽2m、净高4m。采用半径0.5m加0.025m净空的球形包络；不能把这种保守判据的违反直接写成真实撞门。

只读查询Quadrotor1的实际BodySetup得到单个32顶点凸包；BodyMesh相对缩放为1。按常用100 Unreal单位/米换算，其资产横向极值约±0.503m，竖向明显小于0.5m球半径。资产凸包仍不等于所有姿态下的世界包络；尚未完成完整物理尺寸/姿态标定。

在当前假设下，把净宽直接改为1m或0.75m会与声明的球形包络冲突，不能这样制造更难场景。后续若核实几何并调整包络，应为双方同时采用，并建立新的独立实验版本。

J使用原式形式的p/v/q状态跟踪误差、Wx=I和公共20ms采样网格，并非离线控制输出MSE。论文具体权重未获得，不能声称绝对数值与原论文一致；撞毁或中止的部分轨迹J不能与完整任务J比较。

## 下一步：只做决定性的一小组工作

1. **已做可恢复性诊断。** 单回路实时20ms试验仍出现两次时序中止，故补充暂停步进，仅隔离控制器行为。1m/s初态在两种更新间隔均通过；1.45m/s初态均未满足配置穿门净空，门3横向偏差约-0.513m和-0.507m，均无实际碰撞。实际最大保持间隔约21ms、51ms，已经逐次记录；不能将其写成精确20/50ms硬实时运行。此结果不支持靠缩短该组状态的周期就能逆转成败，但也不是所有状态都对周期不敏感的证明。
2. **先统一安全谓词，再修补经验模式表。** 沿用同一门框/净空、任务进度与恢复定义，明确是否要求全程参考管道约束。对可恢复且等待敏感的状态，结合真实闭环姿态、held control和参考阶段，检验少量中间等待与变化更新间隔。保留原表，新建有来源的局部表；不能靠失败重命名成合格。
3. **验证物理期限确实会触发且任务仍可恢复。** 比较相同模型、相同初态、相同资源下的固定周期与状态期限，确认B激活、任务完成和真实碰撞分别如何变化。若更频繁更新也救不回来，应先改控制任务或控制器，而非要求调度器创造恢复能力。
4. **最后恢复多机公平比较。** 在新实现下用完整正常窗口重新验证静态候选可行性，冻结选择后运行独立扰动与重复。只有真实碰撞对无中止完成才能称安全优势；双方完成的公共场景再比较J。

以上不新增RL、能耗预测、DNN误差预算或复杂在线搜索，也不先扩展到136配置或FPGA。先判断状态→合格控制模式→可行更新这条主线是否成立，再部署硬件。
