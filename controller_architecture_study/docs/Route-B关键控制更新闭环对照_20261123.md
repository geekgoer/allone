# 路线 B · 哪一条控制更新值得优先保住？

想象两架飞机同时等 DPU。一架刚开始转弯，需要改变动作。另一架正在平稳飞行。如果两条命令不能同时算完，我们希望先保住错过后果更重的那条，还要让另一架有足够时间。要验证这个想法，第一步是确认**漏掉哪一条，飞机真的会飞得更差**。

## 已做完的历史筛查

用同一路线、20 ms 周期的四轮十二机真板日志。每道转弯门按参考时间往前看两个窗口。早段是 **0.80～1.10 秒**，晚段是 **0.075～0.225 秒**。这些只是候选窗口，延续早晚漏更实验的提问方式。

| 窗口 | 已记录的发布 | 按时发出并收到确认 | 推理没启动，输入已被入队阶段接收 | 推理启动后仍未按时交付 |
| --- | ---: | ---: | ---: | ---: |
| 早段 | 690 | 674 | 6 | 10 |
| 晚段 | 345 | 341 | 3 | 1 |

表里只数日志中留有发布记录的任务。已经退出的飞机不再发布，故退役后的空白没有算进来。四轮用了不同的 CPU 线程设置，表的用途是找问题出现在哪，不能用来估计某个设置的漏更率。

Drone2 第 8 门恰好有两条适合先测的更新。任务 729 在参考过门前约 **1.034 秒**，任务 774 在前约 **0.134 秒**。各自在四轮里按时三次，有一次入队后未派发。

- 早段任务 729 入队后等了 **11.72 ms** 才被派发检查拒绝。按拒绝时使用的模型耗时和下发预留倒算，约在入队后 **10.71 ms** 前要开始推理。这段等待中，已经运行的任务结束后，DPU 又启动了另外三架飞机的任务。所以早段有机会在正式试验中检查排序的作用，仍要重算被挪动任务的期限。
- 晚段任务 774 入队时，DPU 正被 Drone4 占用。那次占用约在入队后 **1.34 ms** 结束，距估算的最晚开工只剩约 **0.21 ms**。即使优先级能调整，已经运行的整条推理也不能中断。这里的耗时和预留都是对应日志中的估计。

## 第一次新试飞只回答一件事

在原十二机路线、第 8 门前，把目标任务分别放在 729 和 774。每个时刻做两对，每对包含一次正常飞行和一次刻意漏掉目标更新，共八轮。每轮使用固定 **20 ms** 和模型 **ID 11**。漏更时照常取样，只在专用试验程序里停止目标任务进入 DPU，飞机继续使用上一条命令。另一条命令仍按原日历更新。其余飞机照常飞。实验在 AirSim 中进行，DPU 是真板。

复跑时脚本先核对输入哈希，每次从同一冻结路线重置。正对照和漏更轮交换先后顺序。分析要求两次飞行干预前的位置、速度、姿态、旧命令和采样迟滞接近，目标前后相邻两条都已交付，并能读出目标门净空或确认接触。实际接触和没有读到过门数据分开记录。净空按现有机体包络和采样位置估算，接触读 AirSim 的碰撞报告。

如果正常飞行有正净空且无接触，两对有效试验都显示漏更导致了接触或**至少 2 cm** 的净空损失，就把该窗口列为下一轮独立确认候选。2 cm 是这次筛查预先使用的门槛。一次出现、配对状态差异太大、目标旁边又漏了别的更新，都不算稳定效果。两对都没有足够差异也要记录。

## 运行一次配对试验

试验入口调用此前已用过的 `prepare_case_v2` 和板端 DPU 独占脚本。先打开 Windows 的 12 机 Blocks 配置，点击 Play，保持视口可见。板上使用 `board_package_requant18_release001`。现有控制程序和原模型包不需要覆盖。

板端包放在[本轮结果目录](../results/ps_critical_update_20261123_001/critical_update_board.tar.gz)，已在 Vitis Ubuntu 交叉编译。离线调度回归共通过 254 项。生成的二进制、冻结的输入和运行脚本在包内。本轮仍待实际跑这八轮。

在 Windows 的 PowerShell 上传并登录板子。这块板的 SSH 服务只提供旧的 `ssh-rsa` 主机签名，Windows OpenSSH 默认不会选它。用 `-o HostKeyAlgorithms=+ssh-rsa` 给这两条连接加上兼容选项，然后按提示输入板子的登录密码。出现 `no matching host key type found` 时，连接还没走到登录验证。

```powershell
Set-Location -LiteralPath 'F:\FalconReproduction\airsim_control'
$package = 'controller_architecture_study\results\ps_critical_update_20261123_001\critical_update_board.tar.gz'
scp -o 'HostKeyAlgorithms=+ssh-rsa' $package 'root@192.168.77.2:/home/root/critical_update_board_20261123_001.tar.gz'
if ($LASTEXITCODE -ne 0) { throw '试验包上传失败' }
ssh -o 'HostKeyAlgorithms=+ssh-rsa' root@192.168.77.2
```

如果输入密码后 `scp` 报 `subsystem request failed`，在 `scp` 后加大写 `-O` 重试，使用板子支持的旧版文件传输协议。登录用的 `ssh` 保持上面的写法。

在已登录的板端终端，解包到新目录再启动。真实计算窗口是八轮各 32 秒，另有每轮场景准备和日志时间。

## 先通过这一步，再比较三种调度

**简单理解。** 第一阶段先问“漏这一下有多疼”。第二阶段才问“调度能不能保住这一下”。如果该门两条单次漏更的影响都很小，就先复查其他候选或延迟区间，避免把现有的两次漏更结果硬套成单次关键更新。

| 正式组 | 做什么 |
| --- | --- |
| 离线固定配置 | 只在开发路线上选择每机固定周期和模型，冻结后跑其他路线。给它相同的 DPU 和模型池。 |
| 最早期限优先 | 就绪后先算期限最近的任务。与下一组使用相同的周期、模型选择规则及计算、通信预留。 |
| 关键更新保护 | 给已独立验证的危险窗口优先机会。若其他受影响任务据当前预算赶不上期限，保留原派发。记录尝试、成功、失败及原因。 |

三组交错复跑，锁定独立路线与配置；开发用第 8 门只用于形成规则。比较已标记的更新是否按时到达、最小净空及接触、其他飞机的超期和调度耗时。第一轮正式实验不需要同时改周期、分段和跳更。只有关键更新真的从未到变成及时到，且物理结果变好，才能把收益归到保护策略。自然负载下若没有可区分的样本，可以另做固定的受控压力实验，并分别报告。

本轮完成的是历史筛查、一次漏更专用试验和配对分析入口。三组正式比较要等物理筛查和独立确认提供可用目标。[此前的论文发现与证据](Route-B论文研究发现与证据.md)
