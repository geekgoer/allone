# 为什么有时救回、有时失败：后续复核结论

## 给使用者的简短说明

**成功案例是真的，也能再现；目前还没有稳定到每次都成功。**

本轮完成了正常工况的静态配置筛选、两轮机制消融，以及冻结旧源码和当前源码的原序列复跑，共33次完整飞行窗口。DNN权重、输入归一化、门宽、航线和扰动强度没有改变。

最明确的前后差别是：**成功时更早采到扰动后的状态，并较早开始连续纠偏；失败时可能刚采完旧状态就发生扰动，下一份新状态来得太晚。** 磁盘缺页、线程竞争和I/O等待会进一步放大这个问题，但不能把每次失败都归结为DNN推理慢。

## 一、成功与失败必须一起保留

| 运行组 | 动态物理通过 | 固定静态物理通过 | 动态首个新控制 |
|---|---:|---:|---|
| 上一批原序列，固定40ms对照 | 2/2 | 0/2 | 15.84、12.03ms |
| 本轮批量消融中的完整配置 | 0/2 | — | 32.34、26.98ms |
| 加载上一批冻结源码，复跑原序列 | 2/2 | 0/2 | 19.10、10.43ms |
| 当前源码，复跑同一原序列 | 2/2 | 0/2 | 18.49、6.53ms |

批量消融中选出的固定60ms候选也两次碰撞，首个新控制约55.74、56.90ms。

不能把这些开发运行合并成一个可靠成功概率。尤其不能只引用成功的几组而省略批量消融的失败。原序列与批量序列的初始化次数、此前执行条件和实际释放时机没有独立随机化隔离。

旧源码与当前源码都能在原序列复现救回，因此没有发现新增开关必然破坏救回的证据；但也没有通过这个对照彻底分离代码微小时序影响、运行上下文和操作系统干扰。

## 二、一个失败案例说明了什么

以批量消融`r1_full`为例，以下时间相对于扰动写入RPC返回，都是实际记录：

| 事情 | 相对时间 |
|---|---:|
| 采到旧状态，横向速度约-0.878m/s | -1.15ms |
| 扰动写入完成 | 0ms |
| 根据旧状态计算的控制返回 | +6.87ms |
| 传感器新状态被控制前端收到并触发事件 | +10.36ms |
| 下一控制请求实际释放 | +20.73ms |
| 该请求采到新状态，横向速度约+1.141m/s | +25.14ms |
| 根据新状态计算的控制返回 | +32.34ms |

这次第一份有效新反馈里的DNN执行区间约1.8ms。问题主要不在这个1.8ms：事件出现时，当前原型仍受20ms最小请求间隔约束，再加上释放抖动、I/O等待和后续处理，纠偏起点被推迟了。

另一个失败`r2_full`也在扰动前0.51ms采到旧状态，新状态直到+19.64ms才采到，控制在+26.98ms返回。输入记录中的横向速度确认它们确实是扰动前后的不同状态，不只是墙钟标签分类造成的假象。

当前源码原序列的两个成功运行，分别在扰动后约12.73ms、1.06ms采到新状态，约18.49ms、6.53ms返回新控制。

因此，**单看“DNN只算了几毫秒”或“每20ms有一次命令”并不能回答有没有及时纠偏。** 一条在扰动之后返回的命令，仍可能根据扰动前的旧状态计算。

“首个新控制”是便于比较的观测量，不是充分安全条件。本轮还出现首个新控制约17.88ms或19.87ms、随后仍碰撞的情况，连续控制时序和控制器恢复余量同样需要考虑。现有记录不能推出统一的“20ms内必安全”阈值。

## 三、为什么以前更容易失败

### 已有证据支持的解释

1. **以前动态计划经常没能及时落实。** 历史失败候选中，首次新反馈约28.32、52.99ms；扰动后550ms窗口内，Drone1命令之间的最大间隔约56.49、94.49ms。此前成功组的最大间隔约27.51、28.48ms。
2. **存在已经证实的执行链路阻塞。** 先前内核采样确实发现Torch运行库硬缺页约44ms，以及推理线程就绪后被同核其他应用拖延约28ms。驻留和私有进程优先级措施针对的是这些风险。
3. **近期成功窗口中，新反馈更早、更连续。** 固定40ms等待下一次采样，再加响应时间，往往约37～43ms后才根据扰动后的状态控制；动态在部分运行中将关键回路维持在约20ms间隔，实际首次新控制降到约7～19ms。

### 仍不能确定的归因

- 本轮没有独立证明“驻留措施就是全部成功的原因”。关闭驻留的两个消融都失败，但同期完整配置也两次失败，不能据此作单因素因果判断。
- 成功也依赖扰动落在两次采样之间的什么位置，以及随后执行链路是否及时。不能只解释成“Windows随机抖动”，也不能声称新增开关没有任何时序影响。
- 模型权重相同，没有发生一次新的训练提升。控制器的恢复余量是否足以覆盖所有允许的采样等待与响应组合，尚未验证。

## 四、静态配置确实重新选了，未拿指定40ms冒充最优

只使用无扰动正常飞行，在两个既有网络和20/30/40ms候选上筛选；如果没有零违规候选，按预定规则补60ms。所有缺失周期和迟到更新都计入违规。

这里“9层”指9个隐藏层，另有输出层。

| 隐藏层×宽度 | 固定周期 | 正常总J | 缺失＋迟到更新 |
|---|---:|---:|---:|
| 9×512 | 20ms | 1.600162 | 163 |
| 9×512 | 30ms | 1.595126 | 34 |
| 9×512 | 40ms | 1.580078 | 19 |
| 9×512 | 60ms | 1.533939 | 0 |
| 9×1024 | 20ms | 1.665148 | 296 |
| 9×1024 | 30ms | 1.657953 | 26 |
| 9×1024 | 40ms | 1.643774 | 58 |
| 9×1024 | 60ms | 1.594487 | 0 |

正常数据因此选出9×1024、60ms，并在扰动前冻结。随后正常复核又出现2次失约，不能称作稳定的严格可行配置。稍后原序列中40ms正常窗口也有过零违规，说明当前机器的时序域还不够稳定，不能由这次筛选推断“7机只能用60ms”。

选出的60ms配置在两次扰动中都碰撞，其中一次全程无名义期限迟返。这继续说明：**满足一个固定的执行期限，并不自动意味着物理状态变化后仍来得及恢复。**

这是有限候选的正常工况搜索，不是完整FALCON的SVM、所有模型和全局参数优化。动态也尚未稳定满足自身期限，不能把物理救回直接写成严格实时可行性优于FALCON。

## 五、B、EDF和预留量的独立贡献还没有证明

本轮消融结果如下，每种两次、顺序正反排列：

| 变体 | 物理通过 |
|---|---:|
| 完整动态配置 | 0/2 |
| 关闭物理B约束，保留状态相关周期与80ms更新上限 | 1/2 |
| 以固定任务优先级替代EDF，保留动态周期与B | 1/2 |
| 用新正常数据重标定响应预留 | 1/2 |
| 关闭推理驻留/优先级措施 | 0/2 |

结果受时序变化影响，样本也很少，不能由此推断B有害、EDF有害，或某个消融更优。目前没有证据说它们各自不可缺少。

旧响应预留约45.19ms，新标定值约47.46ms，差别很小；这也不是一个强度充分的预留量消融。

原型在扰动前就可能以约20ms间隔运行：这是风险相关周期公式、旧响应预留和最小间隔共同作用的结果。部分成功的第一条纠偏输出甚至早于传感事件处理。因此不能把首次救回全归功于事后事件、B或EDF。

## 六、代码、验证和数据边界

- 增加`probe_recovery_mechanisms.py`，实验条件与顺序在试飞前写入`plan.json`。
- `flight`增加可选模型、调度器和物理B消融参数；默认语义保留原配置。关闭B仍保留控制更新上限，没有暗中放宽所有期限。
- 新增`probe_frozen_feedback_control.py`，实际从上一批保存的源码目录加载运行器和飞行代码，并记录加载路径。
- 20项相关检查通过。涉及推理执行器、I/O、输入编码、动力学/评分、核心放置和驻留措施的八个核心文件，与上一批冻结源码的SHA256一致。
- 除了原先的目标初态匹配，还核对了33次窗口中全部7机的实际初始位置、速度、四元数和角速度，均与原始成功案例一致。
- 所有运行均保留；失败没有自动重试或剔除。三组运行的清理与CPU affinity恢复均通过。
- 仍使用RPC返回作为控制生效代理。没有测到真实电机/飞控的精确生效时间，没有FPGA验证，没有安全证书。

## 七、下一步应聚焦什么

**优先把“已检测到危险，却仍需等到下一次有效新反馈”的盲区测清并收敛。**

具体沿用现有模块即可：

1. 固定当前案例和DNN，覆盖少量预先规定的扰动相对采样时机，判断当前20ms下限与真实响应延迟组合是否留有恢复余量。
2. 把采样等待、事件接收、最小间隔等待和实际响应分别计时，使用已有原始状态确认反馈是否确实包含变化。
3. 再决定在现有B和释放规划中如何处理这个等待；如果当前最小间隔不能及时恢复，应明确记录不可行，或验证能否在真实资源允许时提前补一次新反馈。不能通过假设零延迟获得成功。

本轮不支持扩大训练、增加更多模块或继续宣称某一调度器必然更优。它支持的研究问题是：**共享执行资源下，怎样让基于新鲜状态的有效反馈在恢复窗口内到达，并让这种能力对采样时机和执行波动具有余量。**
