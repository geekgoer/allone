## B50-01 把原生前端等待从共享 CPU 需求中分开

`--split-native-prep` 保留每机响应路径中的采样与交接等待，同时允许不同回路在预测中并行等待。完整预测仍检查所有回路期限和每机复用，已发布任务期限不变。新增回放测试覆盖等待与规划重叠、等待保留在响应路径、等待不计共享 CPU 需求，以及命令后收尾仍占该回路。

首组实验 `results/ip37_native_prep_split_20261109_120115/` 中发现 Windows Python 线程 CPU 计时的粒度问题。两臂在 1662 条可用准备记录中只有 0 和 15.625 ms 两种读数。因此这组原型使用的“线程 CPU 计时”不能作为毫秒级输入计算成本。旧臂 Drone4 cycle484 在 0.91 ms 时完成原生采样，Python 到 46.58 ms 才接手，输入在 53.92 ms 就绪。新臂虽实际安装 9 次周期修改并全部按期交付，缩短周期的 4 次仍均早于 2.5 s，第 4 门约 5.0–5.3 s 仍有条件 B 超期。两臂各 24/24 门、零碰撞。同一旧臂 232 条拒绝快照仅替换为该拆分模型重算，通过 0→0。首组不用于单独归因或作为最终成本实现。

反序复测 `results/ip37_native_prep_split_reverse_20261109_120242/` 仍是同一线程 CPU 计时版本。两臂均 24/24 门、零碰撞、无周期超期。合并成本组实际修改 6 次，拆分组 10 次，分别有 2/3 次缩短周期，均早于第 4 门窗口。另一组 308 条同快照重算仍为 0→0。旧组安装数随运行变化，不能将单次安装差异归因于拆分。

## B50-02 使用控制线程接手至输入就绪的实测经过时间

修正：拆分组将计划释放到 Python 控制线程开始的时间作为每机路径等待，将线程接手至 237D 输入就绪的经过时间作为保守的共享服务估计。这一段仍可能包含线程暂停。原生 RPC、结果到轮询及线程接手分别记录，粗粒度线程 CPU 计时只用于诊断。两段估计仍各取已观测最大值，命令与收尾成本和时序保护保留。82 项相关测试通过。

## B44-01 命令返回后的工作被计入本次命令期限

状态：代码已修复，回归通过，待板端复核。

## B44-02 已返回命令的在途任务可能重新背上旧期限

状态：代码已修复，回归通过，待板端复核。

证据：`JointRuntime.snapshot()` 将收尾中的任务作为旧任务带入预测，以旧任务的命令期限约束它。在命令已经返回、旧期限已过且工作线程仍忙时，快照还会直接拒绝，无法检查已经公布的下一次未来释放是否能避开剩余占用。
