# 真板日志怎样认出飞控用上的那条命令

AirSim 收到 `ping()` 并回复，只能说明这次 RPC 有回应。上一轮在独立 Blocks 中已经看见，回复早和飞控用上命令早是两件事。这次把板端的任务截止、`ping()`、以及模拟飞控首次采用的记录连起来。[独立 Blocks 证据](Route-B完整仿真命令采用计时_20261124.md)

## 接入方式

板端沿用上轮十机的控制器、模型池与任务日历。每条实际尝试发送的控制命令获得唯一序号，并用带序号的 RPC 调用同一个角速度和油门接口。命令原有的 1 秒最长持续参数保留，后续正常更新可以覆盖旧命令。原有 `ping()`、版本、保持期限、派发与改期规则继续运行。诊断记录供试验结束后核对。

1. 开始和结束时各做 32 次时钟 RPC。Windows 时钟值落在板端发送和返回之间。分析允许两端相对钟速误差 200 ppm，按事件距离校时的时间放宽区间。200 ppm 是分析假设，结果中保留这个参数以及原始时钟样本。区间盖住截止时，结果记为不确定。
2. 运行中只添加命令序号，读取飞控记录在结束后进行。Blocks 记录 RPC 进入、目标写入、第一次在该目标有效时写出模拟电机值的固件更新。
3. 用命令序号配对，分别判断采用早于或晚于 `ping()` 和任务截止。若缺了飞控记录或只有目标写入，单独计数。命令未采用与日志未观测到都保留各自的证据范围。

板端源码由 [生成工具](../airsim_command_timing/prepare_ps_trace.py) 从冻结快照生成。32 秒试验由 [独立运行脚本](../airsim_command_timing/run_ps_trace.sh) 执行。运行脚本只采用单独的 `/home/root/tcs_command_trace_*` 目录。它读取原校准、场景准备工具及 18 模型基线。遇到 DPU 已有打开的设备描述符就停止，不会杀掉占用者。独立 Blocks 只绑定直连网卡 `192.168.77.1:41591`。原实验用的 41451 不参与。

## 证据位置

真板 ARM 回归通过 298 项，分别是调度 43、日历 208 和复核 47 项。Windows 工程的 `controller_architecture_study/results/ps_trace_20261124_001/` 留存生成的源码、原始请求、校时、模拟固件记录及分析。模拟固件记录必须在独立 Blocks 退出前取回，每轮用互不重叠的命令编号，且应在下一轮运行前取出这一轮的记录。[旁路分析入口](../airsim_command_timing/audit_ps_trace.py)

## 十机实测结果

两轮各 32 秒，都是原十机路线、真实 DPU、模型 ID 11、初始周期 20 ms。采用离屏 Blocks，分辨率为 640×400。两轮配置分别取历史的 `natural_fixed20` 与 `natural_retime20`。

| 条件 | 总发布 | 下发前丢弃 | 按期采用／下发 | 最慢 ping | 实际改期 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 固定 20 ms | 16,000 | 14 | 15,986／15,986 | 7.801 ms | 0 |
| 初始 20 ms，允许改期 | 16,000 | 11 | 15,989／15,989 | 6.147 ms | 0 |

固定组最慢的一条 `ping()` 是 Drone11 第 1514 周期，提交后 0.523～1.679 ms 已进入首次固件更新。两轮共 31,975 条命令找到匹配的固件采用记录。有 **3,989 条**的固件更新确定晚于 `ping()`，**283 条**确定早于 `ping()`，剩余 **27,703 条**先后落在跨设备钟差区间内。每条已下发命令的采用均能确认早于其任务截止。固定组在 100～400 ppm 的相对钟速误差假设下复核，截止判定一致。25 条丢弃均由板端记为 `dropped_inference`，没有发出控制命令。

历史 38～39 ms 的 `ping()` 两轮均未重现，允许改期组没有产生改期触发。单次对照的丢弃数差异无法说明允许改期能改善交付。旁路已经能在真板运行时指出当前究竟是「命令已发但未采用」还是「采用早于确认」。下一次应在相同十机路线上改变 Windows 仿真负载，先让长尾复现，再比较按 `ping()` 和按采用时刻所得的改期触发。这里核对的是时序，原始归因和过门质量需要后续重复与飞行审计。
