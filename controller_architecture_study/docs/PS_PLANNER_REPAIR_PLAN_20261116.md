# PS Planner Repair and Closed-Loop Validation Plan

2026-11-16。基于[PS交付复核](PS_MIGRATION_DELIVERY_REVIEW_20261116.md)，规划下一阶段由当前Windows Agent直接访问Ubuntu构建机及Zynq实施。本文是执行计划，本次只做只读连通/版本核对，没有修改板端程序或启动飞行。

## 1. 先解决什么

**先让配置调整能够及时、正确地落地，再研究它能否改善飞行。**

主控制链已经上PS，18004条请求在现有单/双机试验里按期交付。现在的主要障碍是：规划使用约10 ms的CPU时间，算完后其他任务已经向前执行；整份快照版本不一致，候选就不能提交。

下一步不把“89个候选全部安装”设为目标。其中一些在最新状态下可能确实不再合适。成功标准是：仍有效的修改能及时安装；失效修改继续被拒绝；其他飞机的更新和补更义务保持完整。

研究主线仍是[新版Framework](OBLIGATION_PROTECTED_BUDGET_FRAMEWORK_20261116.md)中的“义务保护→连续预算→预算内选模→全组复核”。本阶段修复执行基础，不增加黑盒优化器，也不同时加入超网和分段调度。

## 4. 第一步：测出规划内部的实际成本

### 4.1 固定输入和输出

先冻结三类输入：已有89个真实skip快照；最长24.987 ms的keep_current快照；普通成功keep、无资格/无解等代表快照。使用原记录的模式成本、期限、permission和候选上限，不更改成本来制造失败或触发。

逐个预热后重复回放，保存输入SHA、输出、线程CPU和墙钟分布。解析输入、生成日志、写文件单独计时，避免把它们混入核心规划时间。ARM独立回放测的是无飞行竞争的成本；后续live计时才测真实竞争，二者分开。

### 4.2 新计时点

| 阶段 | 要区分的工作 |
| --- | --- |
| 取得快照 | 等日历锁、锁内复制/建模、释放锁 |
| 预处理 | JSON解析、字段校验、模式表转换、排序 |
| 诊断 | 路径和窗口需求计算 |
| 每个候选 | 生成、倒推、完整PS/DPU前推、组装通过结果 |
| 质量升级 | 是否真的需要第二次检查、用了多少预算 |
| 提交 | 等锁、检查版本/时间、复制或安装变更 |
| 记录 | 日志入队、序列化和写盘 |

各计时区间保持互斥或明确包含关系；报告计时探针本身的开销。不能把“1次完整检查”理解为此前诊断、复制、排序都没花时间，也不预设JSON一定是主因。

此阶段只加观测，不改变策略。保留v5和原数据，新版本单独命名。输入相同情况下，重要的动作、模式、顺序、补更和可行性结果应相同；新增计时字段不参与等价比较。

## 5. 第二步：根据热点选择最小改动

按测量结果选择，不一开始重写全部源码：

- 若诊断在原计划已可行时占主导，把不影响选择的详细诊断延后到确需修复时；不能延后实际保持/期限检查。
- 若反复解析/复制占主导，在一次决策内复用模式/任务表示，减少重复JSON转换；日志仍可保持原JSON格式。
- 若完整前推占主导，优化小型事件管理及重复查询，缓存固定尾序列；必须对相同输入和异常状态做差分。
- 若管理频繁启动占主导，合并事件并沿用仍有效承诺。少做无意义搜索，不减少采样和已承诺控制交付。
- 若锁等待占主导，缩短锁内复制/安装，算法在锁外；不把整个10 ms规划搬进日历锁。

初始工程目标：普通keep路径P99约1 ms以内，代表性完整修复P99约3 ms以内，观测最大尽量控制到5 ms以内。这些是**待测优化目标，不是现有性能或WCET承诺**。若达不到，报告实际瓶颈，并据真实可修改窗口决定是否缩小问题规模或限制在线功能，不伪称已满足。

除平均/P99/最大外，直接记录“从触发到安装”的响应及安装前剩余提前量。仅把算法函数变快而仍无提交机会，不算解决问题。

## 6. 第三步：让计划能够适应执行进度，而不接受过时条件

### 6.1 基本做法

候选保存的是对未来槽的小变更，例如“某个未发布任务换模型/提前”“某个未来槽撤回，原下一槽承担补更”。不把旧快照里的已完成任务重新装回当前日历。

```text
快照S0 → 生成候选变更Δ
                   ↓
             获取最新快照S1
                   ↓
     核对目标仍可编辑、控制证据和期限仍适用
                   ↓
  把Δ应用到S1的副本，保留所有实际在途工作与补更
                   ↓
         有界全组检查（最多重验证一次）
                   ↓
      短锁内核对S1版本与实际提交时间
             通过安装 / 变化则拒绝
```

原快照版本一致时保留原快速提交路径。版本变化时新增的是重验证路径，不能直接忽略版本不一致，也不能无限循环重试。没有足够重验证预算时继续拒绝。

把“计划/义务结构版本”与“观测/进度版本”区分开可以减少不必要重建，但本身不构成批准依据。先实现清楚的有界重验证，再决定是否值得增加细分版本优化。

### 6.2 哪些必须重新检查

| 新变化 | 处理原则 |
| --- | --- |
| 其他任务已经完成 | 移除已完成工作，按实际结果更新剩余需求；不能沿用旧时刻 |
| 其他任务刚发布 | 加入实际状态、固定槽期限及剩余处理，检查对其影响 |
| 有任务正在DPU运行 | 保留真实不可抢占剩余占用；不当作可撤回任务 |
| 供方控制版本变化 | 原跳更资格不能自动复用；需要匹配新held的观测，否则拒绝 |
| command_pending/不确定发送 | 不能用旧控制证据为其跳更背书 |
| 保持期限缩短或成本增大 | 用较新、较紧条件重新验证，不可保留旧宽松条件 |
| 目标已release | 不再撤回目标槽；改期/跳更候选失效 |
| 补更已欠账 | 保留冻结期限，禁止再次跳过，不因重规划清零 |

完整检查继续覆盖其他UAV，不只看被跳飞机。临界区时长和重验证计算本身也计入响应时间；不能通过锁住发布器10 ms来保证“版本稳定”。

### 6.3 验证范围

建立可控制事件时刻的生命周期回放：复现“搜索时其他UAV发布/下发”，另加入期限收紧、服务超包络、目标过期、控制版本变化和原下一槽超测量窗口等反例。

通过要求：在明确有效的测试中修改能安装；确实失效的修改仍拒绝；每机release、在途所有权、DPU不可抢占及补更记录不被破坏。原89份输入只含快照，不能独自证明并发重验证正确，需要新的事件序列和新运行日志。

## 7. 第四步：先验收执行，再评价收益

### 7.1 双机、不跳更

沿用同一模型池、冻结路线/初态和成本生成口径，T50做固定与修复动态配对，先各一轮20 s。检查无输入拒绝、无意外drop/迟到、完整窗口、实际模型/周期、输出符号、保持版本和控制链。通过后再做三组配对；首轮失败先定位，不机械追加轮数。

没有必要修改配置时允许keep；不能为了看到变化强制降档或缩周期。若场景确实没有可用机会，离线机制验收和闭环收益测试分别记录。

### 7.2 独立跳更验收

先使用原T30独立工况与相同资格门槛，不把门变宽、成本变大或阈值放松作为触发手段；开/关各一轮20 s。重新记录每条候选是否进入新状态复核、为何拒绝、是否安装。

如果自然批准一次跳更，必须完整看到：

1. 未发布槽实际出现 `planned_skip`，没有对应DPU调用；
2. 原紧邻下一槽按原身份release；
3. 补更走真实DPU、命令下发及返回；
4. 在冻结的有效期限内清债；
5. 其他保留任务仍按期，测量窗口结束没有未清债务。

这只证明机制能执行，保持资格当前仍是条件假设。没有触发时允许结果为0；必须说明是没有必要、无物理资格、时序不可行、还是仍被提交活性阻断，不能混记为已验收。

## 8. 第五步：回到真正的研究问题

工程阶段稳定以后，才继续以下实验：

- 一次跳更/不同补更时刻的实际控制损失，覆盖自然飞行的转弯进入、中段、退出和直线；旧两次漏更实验不能直接代替。
- 固定义务下的EDF、受保护派发、倒推预算选模；观察模型与顺序调整是否改善关键交付。
- 保留全部更新已经可行时，是否有“供方少一次反馈、受益方获得更好模型”的净质量收益。缺配对损失数据时保持质量型主动跳更关闭。
- 公平优化的静态配置与动态对照；先双机，证据支持后再扩大4机，不直接重跑12机大矩阵。

分段DPU和超网另外开展固定小样的硬件能力验证，不阻塞当前提交问题的修复，也不写成已经迁移的能力。

## 9. 版本、记录与停止条件

现有实测v5保持只读基线。建议在Ubuntu建立独立修复目录、板端另建新目录，先命名 `profile001`，优化和提交修复各留独立版本；不覆盖旧二进制或原始日志。Windows保存修改源、补丁、构建身份、原始回放和派生分析，不只回收一句PASS。

每阶段交付一份记录：发现什么、修改什么、测量和回归结果、仍未解决什么。涉及真实控制时先核对DPU和飞机占用；不用停止未知进程来获得独占。

若测量说明现有宽松工况不需要修改，接受这个结论；若资格不足则先补证据；若在可控的小规模里仍无法有界重验证，缩小在线允许动作，不关掉时序/控制守卫。**最终以有效修改及其他回路不受损为准，不以跳更次数越多越好为准。**
