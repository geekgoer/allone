# 真实碰撞漏报修复与后续实验

日期：2026-10-24。用户已手动点击Play，12机RPC正常；Agent没有操作屏幕。

## 关键更正

之前的“静态实际碰撞0次”不能作为有效结论。低速接触实验在同一`1M_Cube`实体障碍物上复现了：`simGetCollisionInfo()`给出真实撞击对象和时间戳，但`getMultirotorState().collision`依旧为False、空对象名和0时间戳。旧框架快照使用了后者。

本地AirSim主源码也支持这个定位：`AirLib/include/vehicles/multirotor/api/MultirotorApiBase.hpp`的`getMultirotorState()`填入运动状态、GPS和时间戳等字段，没有填入collision。`PawnSimApi.cpp`单独维护碰撞信息，其`getCollisionInfoAndReset()`会清除短暂的has_collided标志而保留事件时间戳。

因此，不能只替换API后仍仅检查has_collided；两次轮询之间标志可能已经被清除。

## 已实施的修复

1. 统一快照分别读取运动状态和专用碰撞API。
2. 以大于启动基线的非零新碰撞时间戳识别碰撞，记录对象、事件时间戳及原瞬时标志。启动前已有碰撞不重复计入。
3. 模式表必须带有`simGetCollisionInfo_changed_nonzero_stamp_v1`来源标记；旧表被明确拒绝加载。
4. 读取碰撞增加了一次真实RPC，时延契约升级为`parent_visible_state_and_direct_collision_v3`。旧经验成本表不能直接用于新运行，需重新测量。
5. 校准与正式试验统一为门框净空、真实碰撞、任务进度、末尾跟踪恢复判据。参考管道h<0继续记录，但不再自动代替实际撞门并提前终止。

85项相关回归通过，覆盖空状态包collision、专用接口、标志清除后新事件、忽略启动旧事件、完整窗口校准、实际碰撞终止、拒绝旧模式表与模式专属等待上限。

修复后的低速接触复核通过：专用API与统一快照均捕获同一障碍物事件，临时障碍物已清理。这个诊断使用AirSim自带低速控制，仅验证碰撞采集，不是DNN或调度性能对比。

## 新发现及其含义

修复后，在原有2m净宽门洞就已经记录到真实碰撞，例如`turn_c00_delay000_plain_mlp_h9_w512_seed0`约0.291s撞到`FalconSafetyGate_Drone1_3_right`。

另一个代表状态的立即接管通过，而等待80ms后约0.417s撞到同一类右门框。这是值得研究的等待敏感性。它目前是单回路校准证据，不能称为“FALCON撞而本框架安全”。

环境足够难并不自动意味着调度可以挽救。立即接管也撞的状态，首先暴露控制器/任务恢复能力；立即接管能恢复而等待后撞的状态，才适合检验状态期限和共享资源调度。

## 接下来的有限步骤

1. 完成直接碰撞接口下的240轮基础校准，保留成功、碰撞、净空违反及实时性不合格记录。
2. 仅对“立即接管在两种几何都通过、80ms未通过”的模型/状态补测20/30/40ms等待。选取所有已测较短等待都通过的最大测试上限；80ms失败保留为上限外证据，绝不改成成功。
3. 每个合格模式携带已验证的经验等待上限。运行时查表仍选最低经验成本合格模式，下一命令期限取物理预算、80ms基本更新上限与该模式等待上限的最小值。没有新增在线(T,c)笛卡尔积搜索。
4. 新接口下重新测量七机完整流水线，冻结经验成本；在同条件正常工况中检验有限静态候选，包括之前较好的短周期候选。不能用过弱基线制造优势。
5. 对等待敏感状态做真实多机配对：同模型来源、同初始状态/旧控制、同门框、同资源及失败处理；包含不同临界无人机位置和扰动方向。记录真实碰撞、任务完成、过期控制与完整窗口J。
6. 若出现静态真实碰撞、动态按时无中止完成，再做独立重复及相邻状态确认。若没有，保留完整负结果并据此调整假设。

等待扫描仍只覆盖有限状态与若干等待点，不证明整个状态格子或连续等待区间安全。B仍为启发式，CPU结果不转称FPGA安全保证。后续有必要时再增加门洞/路线难度，并为两种方法同时采用相同几何与正常工况基线。

等待细化仅修补原来没有80ms合格模式的格子；原本已有合格模式的格子保持原80ms候选范围，避免为追求单次推理更便宜而无依据地增加更新频率。

七机开发复核发现：`h=0.2461, hdot=-0.2566`与更危险的代表状态处于同一粗格子，被施加20ms上限而无法接纳。随后只对`h∈[0.225,0.25], hdot∈[-0.35,-0.2]`的小区域作局部细化，既检查实际捕获的姿态/旧控制，也检查名义条件，再检查直线与转弯代表点。通过这些检查的模型在这个小区域可使用80ms；原危险区域仍保留20ms，未整体放宽父格子。

上述局部复核也不证明整片连续区域安全；它是明确记录适用范围的经验原型。

### 仍需解决的限制

20ms危险区在当前经验CPU流水线预测下即使单独执行也无法接纳。冻结测量下，33×512的孤立任务预测约33.93ms，不能为了得到优势把期限延长为40ms。这个数字是带余量的经验预测，不是物理最短时延或WCET，也不证明所有Windows实现或FPGA都无法满足20ms。

局部细化修复了这次正常工况中的过度限制，但未消除全部二维格子别名，也未证明所有危险状态均可恢复。下一阶段应寻找经验证可恢复且更新时间窗口可实现的等待敏感状态，再冻结强静态候选做独立多机配对；还没有得到“静态真实撞门、动态安全完成”的确认结果。
