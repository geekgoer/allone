# 超期恢复与未来期限维护：本阶段实现和结果

日期：2026-10-31。代码、回放、真实十机影子试飞已执行；新建议没有接管控制。

## 核心结论

当前不再把“过去违约无法补救”直接等同于“未来不能再调度”。同时发现并分开了另一个问题：**缺少某个周期的J评分，不等于该周期在时序上不可行。**

最终真实影子运行304次，产生25个时序可行建议，其中20个覆盖当时全部待检查的回路，17个发生在任务前10秒内。25个都是没有J排序的时序恢复建议，控制质量尚未验证，不能称为总体J最优、安全救回或已部署策略。

## 改了什么

### 1. 历史违约与未来可行性分开

`joint_contract_optimizer.optimize()`默认仍使用严格行为。显式开启`recover_after_miss`后，只允许已经过期的在途义务退出“必须在过去完成”的判断；原ID、原期限和剩余阶段保留，计算、段阻塞、前端及IO占用继续计入。

没有删掉旧任务来伪造空闲资源，也没有忽略尚未到期的任务。旧任务仍然太重、会挡住新任务时，恢复检查仍会拒绝。

`future_feasible`表示给定快照中未来义务可以满足；`strict_timing_passed`仅反映该有限快照所提供的违约记录，不能当作整段飞行从未违约。`historical_deadlines_repaired`始终为false。

### 2. 安全期限必须有控制输入的归属

未来计划现在携带：

```text
obligation_actuation_s：这条保持期限所依据的控制确认时刻
obligation_sample_s：分析所用观测时刻
```

独立释放日历产生后继任务时继承这些时刻，而不是在每次释放时重置B。

新命令已经生效时，旧输入的保持区间已经结束，需要给新输入建立自己的未来义务。若确认时刻晚于旧期限，旧违约仍记账；若在旧期限前结束，不能仅因为之后看到了一个旧期限就把它误记为仍未完成的保持义务。

同一输入不变时，不推迟尚未过期的义务。若旧期限已经过了，只能在获得旧期限之后的新观测、与实际保持输入配对且有剩余条件安全时间时，建立新的未来义务。证书与释放槽ID分开记录，旧义务不会被改成“按时完成”。

这种更新只用于**未发布的安全保持义务**。普通计算任务的原始响应期限、已发布任务的原ID/承诺不因此修改。临近发布、缺少配对观测或仍有未确认控制在途时，明确延期处理。

这些判断使用命令RPC确认作为生效时刻代理，模型误差界尚未在真实对象上验证；不是无条件物理安全证明。

### 3. 配对观测不再等待旧规划器

命令确认后的状态回读到达前端时，就更新影子进程使用的状态与实际控制。旧规划器随后到达的较早记录不能覆盖这个较新的配对。

发现并修复了一次开发中的误触发：确认回调使用旧计划期限判定新命令危险，而旧规划器随后又用新预算判为宽松，导致边沿反复跳变。现在确认回调只更新状态、标记普通变化；危险边沿来自新预算分析。

门框几何改为进程启动时一次传入，避免每个快照重复编码；快照也不再重复编码同一份未来日历。

### 4. 先恢复时序可行性，再谈性能排序

原性能先验很稀疏。例如某模型只测过80ms，但当前安全保持上限扣掉R后最多允许约65ms。原代码因为找不到该模型的60ms评分，就把它从候选集合排除。这是性能信息不足，不能据此证明时序无解。

开启恢复影子模式后：先尝试有性能先验的候选；若单回路候选已被评分覆盖问题排空，再在同一个6ms搜索预算内尝试仅检时序的分支。释放点来自20ms最小间隔、当前规划完成时刻、当前释放点/期限等条件，最长间隔仍受原控制上限和实际期限限制。

该分支不虚构J，使用零值占位目标，只返回可调度性结论，标记：

```text
selection_objective = timing_feasibility_only
quality_ranked = false
recommendations_applied = false
```

零目标及零对偶差距不是飞行J，也不是性能最优性证据。没有恢复质量资格的候选不能仅凭时序检查通过就宣称安全。

调度器仍是两层完整FC为一个不可中断段的EDF；本阶段没有加入新的调度算法搜索、RL或整套神经决策网络。

## 已执行的结果

### 冻结快照回放

来源`joint_contract_shadow_20261030_v4`的303个快照：原严格规则0个，恢复规则1个可行建议；该1个在任务末尾，不能当作救回案例。

来源`joint_contract_recovery_shadow_20261031_v2`的304个快照，用相同队列、成本和记录证书比较：

| 规则 | 时序可行建议 | 覆盖全部待检查回路 |
|---|---:|---:|
| 原严格检查 | 0 | 0 |
| 恢复检查，但仍只用已有J工作点 | 0 | 0 |
| 恢复检查＋无J评分的时序探查 | 14 | 13 |

进一步按单回路计数：原评分候选为空的情况中，357个存在隔离条件下的可行时间范围，但没有被J表覆盖；189个在当前时延/期限界下确实没有隔离可行时间。这里是单回路拒绝次数，不是独立飞行场景数。

回放没有重新模拟建议产生后的队列和飞行轨迹，不能作为控制收益证据。

### 最终真实十机影子运行

结果目录：`results/joint_contract_recovery_shadow_20261031_v3`。

| 指标 | 结果 |
|---|---:|
| 处理的影子快照 | 304 |
| 时序可行建议 | 25 |
| 覆盖全部待检查回路的建议 | 20 |
| 前10秒内的可行建议 | 17 |
| 有性能排序的建议 | **0** |

| 状态记录＋采集累计同步占用 | 185.84ms，约任务窗口1.26% |

| 快照到结果平均 / P99 / 最大观察值 | 4.208 / 9.263 / 25.010ms |

同步占用不是精确CPU使用率；工作进程的CPU占用也不代表总系统CPU开销。6ms是有界候选搜索预算，不能当作Windows端到端硬上界，安全分析、唤醒、系统抢占和日志时间另有计量。

最终旧控制策略下零碰撞，独立传感观测覆盖任务窗口、物理过门检查通过；名义周期期限迟返/未交付均为零。不过，旧策略使用的安全期限仍有943次迟返，初始预测准入也未通过；不能称为严格安全实时验收通过。控制侧记录的尾部窗口覆盖标志仍为false，与独立传感观测覆盖标志分开保留。

新建议未应用，因此本轮的J属于旧控制策略。不能据此声称新建议改善碰撞率、保持J或证明新框架胜过FALCON。

首次恢复影子版本曾出现1次碰撞，同时误触发使求解频率升到约98次/秒。该失败完整保存在`joint_contract_recovery_shadow_20261031_v1`。修复后的v2、v3均零碰撞；这是开发过程中的不同版本，不能当作统计显著的算法对照，也不能仅凭这几次运行认定误触发是碰撞唯一原因。

## 验证与审计

195项相关检查通过，覆盖：

- 过去的违约不能被重标为按时；未来任务未到期的约束不能被忽略。
- 大型过期任务仍会消耗完整剩余资源，并可能导致新方案被拒绝。
- 新控制结束旧保持区间；同一输入不能随意推迟未过期义务。
- 观测时钟、状态/输入配对、在途命令和发布边界检查。
- 稀疏J数据和真正时序不可行的区分；无评分分支不制造J。
- 原生独立释放日历、有限段抢占和已有全局保护回归。

最终目录下：

- `recovery_audit.json`：逐个核对25个建议的原ID、未来期限来源与过期任务资源计入情况。
- `source_manifest.json`：源码与原生DLL哈希。
- `shadow_worker/decisions.jsonl`：完整建议、约束、历史记录和拒绝原因。
- `cpu_placement.json`：实验CPU亲和性已恢复。

## 当前架构状态与下一步

已完成：期限归属、超期恢复语义、及时状态配对、有界时序恢复和真实影子记录。

尚未完成：对这些时序候选给出可信的状态/周期相关效果排序，以及提交前重新核对最新控制、证书版本和原生日历的一致性。捕获时的日历检查不能代替真正接管前的原子重验证。

下一步优先补少量有针对性的周期工作点或小效果模型，输入包括状态、候选c、周期T和预计生效延迟；学习“候选效果”，由显式优化器继续决策。无需重训控制DNN，也无需现在迁移FPGA。质量未知的时序候选保留为探索证据，不能直接提升为“最低成本合格模型”。
