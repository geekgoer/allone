# Framework CPU 分段原型：核心隔离与硬件边界

日期：2026-10-24。本文件补充此前阶段报告；新入口默认输出到 `results/framework_runtime_v6_affinity`，旧 v1–v5 结果完整保留。

## 这一步解决什么

把推理、通信、前端放到不同物理核心，并把通信从前端 Python 进程中分开，减少共享核心和 GIL 对实验的干扰。它没有改动控制器权重、特征、模式表标签、门洞、B、80ms 最大控制更新范围或失效处理。

这是 Windows 上的 CPU 行为原型，不是 FPGA 时延仿真器。实际的推理是在执行已有237D网络，不是添加 sleep 模拟某个 FPGA 的执行时间。

## 实际资源配置

Windows CPU-set API 查询显示：i9-13980HX，24物理核心、32逻辑处理器，8个较高性能等级物理核心带SMT，另16个效率核。代码读取真实 group/core/efficiency 信息，不把两个SMT线程当成两个独立物理核心。

| 组件 | 本机逻辑CPU | 运行方式 |
|---|---|---|
| 共享DNN执行器 | 14 | 独立进程，一个执行线程，PyTorch算子线程数1 |
| 前端采样处理、模式选择、释放规划 | 12 | 主进程主线程 |
| AirSim通信 | 8、10 | 另一个独立进程，有限线程池，每回路最多一个在途I/O |
| Unreal | 排除8–15后的原CPU集合 | 仅改变精确匹配12机配置的编辑器，结束后恢复 |

8–15包含上述四个物理核心的SMT兄弟线程。Unreal和本试验不把其他工作分配到这些兄弟线程，避免“逻辑CPU不同、物理核心相同”的伪隔离。

每个进程/线程的请求和实际亲和性均读回记录；编辑器原mask、PID及创建时间也记录，恢复前核对PID未被复用。异常退出路径同样执行正常恢复。强杀整个Python进程、断电等不能靠finally保证恢复，应检查保留的 `cpu_placement.json`。没有改注册表、电源方案、驱动或系统优先级。

**这不是OS独占核预留。** Windows中断、其他程序、内存/缓存/功耗竞争仍可能干扰；相同通信进程中的多个Python线程也仍共享自己的GIL。推理、前端、通信三个进程的GIL则相互独立。不能据此声称硬实时。

## 抢占语义及未来FPGA

1. 当前任务模型、输入和绝对deadline一旦承诺就固定。
2. 一段至多两个完整FC层和原ReLU。调度器必须等这一段返回，才选择下一个任务。
3. 活跃任务暂停时保留其activation和层cursor，之后从原任务的下一段恢复。不会借另一时刻的输入复用activation。
4. Windows自身可能在段内把线程换出，这是不可控OS干扰，不是算法支持段内抢占。
5. 这不是DPU任意时刻可抢占的实现。现有DPU若只能整网不可抢占，就应将整网视为一个段；不能把CPU多段测量直接写入DPU调度模型。
6. 手写PL加速器后，只有在硬件已实现的安全边界才能pause/resume。必须重新测量段执行、保存/恢复、DDR搬运和通信成本，并计入最长不可抢占段阻塞。当前CPU结果不提供这些值。

## 本次观察与结果

开发过程中的失败和中止均保留在新结果目录。

- 第一轮仅绑核、通信仍是前端线程时：三机静态完成，动态约49ms预测拒绝。动态通信/排队出现约30ms停顿；绑核本身没有解决。
- 将通信独立为进程后：三机静态和动态均完成原3秒任务窗口，无碰撞、无越期命令。该次J约为1.58814与2.05119。这是集成观察，不是优化后的FALCON比较。
- 七机独立进程配对：静态完成，J约4.09313；动态执行104次命令后，约0.394秒因规划超预留中止。一次规划2.9367ms，原预留1ms。其采样RPC最大2.373ms、命令RPC最大1.677ms；不能把这次预测拒绝解释成已经撞门。
- 按预先声明的统一规则，由上述七机开发试验冻结经验成本表：各阶段 `max(1ms, 开发数据最大值×1.25+0.5ms)`，保留原20ms派发防护和1ms完成余量。随后新七机配对中，静态完成J约4.12492，动态约81ms因有界预测找不到可行计划中止；记录中没有实际越期控制。不能把这个拒绝说成物理上不可能调度，也不能算任务安全完成。

成本表记录并发规模、CPU分配、来源日志哈希、运行源码哈希和各阶段统计。`--cost-profile` 会检查并发规模和布局是否一致。它只是经验预测，未证明WCET；保守成本重复叠加排队/前端等待可能造成拒绝，预测细节仍待审计。没有为通过而放宽deadline或使用失败后的hover算成功。

代码分离过程中出现过一次spawn子进程未加载AirSim依赖的基础设施失败，已修复并保留原目录；它不是控制器恢复失败。源文件改变过的开发记录不能混称同一冻结版本，`stage_summary.json` 会逐一标记当前源码是否匹配。

## 成本计时说明

- 命令RPC服务：helper实际开始处理到send+ping返回。
- 完整命令交付：父进程提交到上述返回，包含IPC/通信队列等待。
- 采样：父进程提交到状态包返回，包含采样派发/通信等待。
- 命令返回之后的新状态读取占通信资源，但不再计作该条命令是否赶上其deadline。
- helper在命令返回时立即发送ack更新，不等后续状态完成；关闭时同样记录已在途RPC，避免把收尾发生的晚命令漏出报告。
- 命令send+ping仍只是作用时刻代理，不是电机或FPGA硬件确认。

## 接下来做什么

1. 先固定当前CPU隔离和独立进程协议，确认三机结果；七机未验收，不直接扩大到12机。
2. 从保留的七机预测快照审计排队、执行、前端阻塞和IPC成本是否重复收费，并检查有界release候选是否过度挪动旧承诺。先离线复盘，不继续盲目试飞或移动安全期限。
3. 两种策略在相同规模正常工况都能完成后，再做有限静态总J搜索、扰动配对和独立确认。当前smoke的静态候选不是完整FALCON、也不是总体J最优。
4. FPGA阶段替换执行器与成本表，保留“固定任务配置、段边界、原绝对deadline、拒绝不能算安全完成”等不变量。PL段边界、上下文保存和实测成本到位之前，不宣称FPGA实时性。

六模型目前的经验合格分布仍相同，尚无状态必须使用更大模型的证据；本次没有制造c切换或扩大模式表合格区域。
