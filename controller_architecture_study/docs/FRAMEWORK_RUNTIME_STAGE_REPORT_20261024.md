## 先看结论

这次已经实现并实际接入AirSim的是“状态/当前控制 → 绝对控制期限；状态 → 最低成本经验合格模型；有界释放规划 → 单执行器分段EDF → 控制命令”的Windows/CPU原型，不再是只改变固定周期的脚本。

## 实际在线链路

```text
实际已发送的u + 随后新观测x
               │
               ├─ Safety Analyzer → 下一控制生效的绝对D
               │
               └─ (h, hdot)查表 → 最低计算成本的经验合格c
                                      │
                    有限候选的全局下一批任务预测
                                      │
                          承诺未来release（不移动D）
                                      │
              异步采样 → CPU特征 → 单个分段执行器
                                      │
                      段边界EDF暂停/恢复，同任务c不变
                                      │
                  命令发送/返回代理 → 后续状态读取
```

每次任务的模型、输入上下文和绝对deadline独立保存。模型只在下一任务边界选择；当前任务只在段边界暂停/恢复。没有把中途替换一个独立模型冒充增量执行，也没有重用另一时刻的activation。

一段至多包含两层FC及原ReLU；同一时刻只有一个推理工作线程实际计算。多个I/O线程只并行通信，不是多个DNN同时使用执行器。每条回路最多一条在途任务，每个Tornado客户端归其所属线程使用。

“最危险优先”在此具体化为安全绝对deadline较早者优先，不直接把h较小者无条件排第一。h相同但闭合速度、当前观测/控制时刻不同，绝对期限可以不同。

## 时间定义：不要再混淆

- 对FALCON中采用D=T的配置，响应R>D等价于R>T；一般R>D并不要求D一定等于T。
- 这里生成的是下一条控制的绝对生效期限，不是永远固定50ms。
- 当前原型D=`min(新状态采样时刻+B, 上一命令返回代理时刻+80ms)`。B仍是距离/速率启发式，不是Yang式CBF safe period，也没有显式DNN近似误差变量。
- B的观测起点和上一命令作用起点是两个分别记录的时刻。后续换严格安全分析时，应输出清楚定义的绝对expiry，不能默默把“采样时刻的剩余时间”当成“从更早actuation起算的完整时间”。
- 命令发送加ping返回仅是作用时刻的代理，不是物理电机确认。其后的新状态读取占通信资源并延迟下一次分析，但不是这条已返回命令的生效期限。
- `delivery_budget_exhausted`表示预测交付余量不足，可能在真正超时前就拒绝；`admission_refused`表示当前有界策略没有找到预测可行安排。两者都不能自动翻译为已经发生R>T，也不能把它们的零碰撞算安全任务完成。

## 软件时延问题及实际修复

1. 把同步状态RPC移入独立通信线程，避免一个采样阻塞其他回路的命令交付。
2. 到期release和已在途任务优先于下一任务的可延后分析；新的非抢占CPU工作还需要检查是否挡住紧急输出。
3. 规划前收取已经完成的后端结果，避免给已完成任务重复收费整网计算。
4. 区分命令返回和之后的状态读取；仍保留完整I/O通道占用。
5. 显式计入IPC及规划时间，规划超预留只能由原deadline内余量支付，不能延长期限。
6. 捕获到一次第2代GC持续41.44ms，覆盖三路采样停顿并造成真实结果过期。现预热后、有限试飞窗口内暂停自动GC，结束恢复；引用计数仍工作。此前另一次53ms停顿的原因不能倒推确定。
7. 237D直接编码省略原输入不用的参考体角速度/对象构造，数值检查与原特征逐位一致。
8. 两次TCP_NODELAY诊断未显示改善，因此没有启用它或修改系统/依赖包。
9. v4将已知固定初态的首批计划移到暂停初始化，两种策略同样处理；首次推理和所有稳态重规划仍在窗口内计时。它不是在运行中暂停物理来“获得”实时性。
10. v4七机试验暴露出共同释放造成的采样突发：采样约27–36ms，个别CPU特征阶段约15ms，不能沿用三机成本表就声称七机预测可靠。v5在原最多5个候选内加入逐回路错峰，仍使用同一全局预测、同一模型/门/期限，不新增在线优化器。
11. 补全状态包解码和整个237D特征路径预热；预热特征被丢弃，实际推理仍使用release后的新采样。该措施没有被用来删掉七机失败或宣布成本已经可靠。

当前成本表为经验预测而非WCET，部分CPU阶段实测仍超过预测。一次完整飞行实际按时完成，只能作为该次观察，不能因此宣布有硬实时/物理安全保证。

## 仍没有完成的东西

- 没有完成“较大规模下，搜索出的FALCON式静态候选碰撞，而本方法同场景按时且安全完成”的正式配对证据。
- 六模型能力分布相同，尚未建立状态相关最低神经计算量这一核心假设。更大的网络不自动补足资源缺口。
- B不是控制相关、含扰动界的安全时间证明；实现接口保留这些字段不代表已实现该证明。
- 还不是FPGA/PL执行器，未部署现有136配置超网，也没有在PL上验证抢占、量化或上下文缓存。
- 有界预测只检查当前已知下一批任务，拒绝不等于理论不可调度；允许当前批次也不是未来无限时域可行性证明。

## 接下来按最小范围推进

1. 先把当前主机上能稳定容纳的活动回路规模和端到端预测成本对齐；不能把“推理核很快”当成整条响应链很快。已有数据说明采样/特征成本受活动回路数和释放模式影响，三机成本不能直接搬到七/八机。可先分析已有静态/动态请求日志，按并发规模、错峰/突发条件标定，不必再盲目试飞。八机拒绝时检查完整报告，而不是强行发过期结果或放宽D。
2. 只在两种策略正常工况都能完成的规模上，冻结软件/门/初态/失效处理，再跑有限静态总J搜索、预声明扰动配对、独立确认和deadline-only消融。
3. 若所有合格模式仍无能力差异，报告这一负结果：先验证deadline/释放/分段调度的价值，不强行宣称c适应收益。
4. 需要扩大控制间隔时，另做延迟/周期标定并另开版本；不能把80ms表直接用于更长等待。转到PL也要重新测整条响应链，不能假定Windows采样开销会随DNN上板自动消失。

资源不可行时，本实现是“拒绝/中止该实验”，并没有实现一个能保证任务继续且安全的应急控制器。第一阶段应先限制在经过验证的接纳域，不能把实验清理用的hover说成框架安全保证。若以后要容忍超订阅继续执行，再单独定义并验证应急动作；当前不为此增加未经验证的新模块。
