# 机上做什么，共享 DPU 做什么

## AirSim 里的“机载算力”是什么意思

当前实验的 12 架 AirSim 无人机都用 SimpleFlight。它在仿真器里运行基础飞控，接受姿态角速度和油门指令。237D 状态准备、DNN 控制以及调度在 Zynq PS 和 DPU 上运行。现在每架虚拟飞机都没有独立的**实验用伴随计算单元**。AirSim 的架构允许应用与飞控分开。可以给每架飞机增加一个仿真的伴随计算单元，由 Windows 进程或额外硬件实现，并分别约束执行时间、CPU 和通信成本。Windows 上测到的耗时只属于该仿真配置。真实机载时序需要在目标硬件上复测。[AirSim 架构](https://microsoft.github.io/AirSim/paper/main.pdf) · [SimpleFlight](https://microsoft.github.io/AirSim/simple_flight/) · [PX4 飞控和伴随计算机的分工](https://docs.px4.io/v1.13/en/concept/px4_systems_architecture)

## 先分清三种“搬到无人机上”

| 分法 | 仍要等什么 | 有机会改善什么 |
| --- | --- | --- |
| 只搬参考构造、特征编码和单机分析，保留原采样与下发路径 | 保留状态、碰撞及命令 RPC | 缩短共享 PS 计算和锁等待，对已发生的 RPC 长尾作用有限 |
| 机上取状态并备好输入，中心仍跑 DNN | DNN 请求仍要上传，控制仍要返回 | 有机会合并每周期的状态读取及准备开销。收益取决于新上传路径，发送 237D 本身也要计入预算 |
| 机上运行轻量控制并直接交给本机飞控，中心 DPU 提供可选的 DNN 更新 | 本地路径依赖本机状态、计算与飞控接口。中心更新仍要承担远端排队和往返 | 有机会让基本控制继续更新，并把一部分请求移出共享队列。轻量控制必须在路线和阶段上验证能力 |

第三种分法改变了路线 B 的资源分工。原来的 \(T,c,\sigma\) 可以继续用来管理**送往中心的请求**。本机保护更新另有周期或触发条件。中心的结果需要通过本机的版本和截止时间检查，防止超时结果覆盖已经生效的本地命令。机载兜底已有先例。例如 Damigos 等人组合边缘 MPC 和机载 PID，并在链路退化时切换。路线 B 仍需验证自己的问题，即多机争用同一 DPU 时，什么时候值得提交中心推理、这些请求怎样安排，以及这个策略能否优于相同机载能力下的静态分工。[Damigos 等，ISIE 2023](https://ltu.diva-portal.org/smash/record.jsf?pid=diva2%3A1799032)

## 用 14,850 条真板任务日志复算一次

使用冻结的自然负载 `natural_retime20`。这轮十机、初始 20 ms，固定真实 DPU 模型 ID 11，允许逐机放宽周期。16 次触发均失败。Drone8 一条 39.579 ms 的准备记录中，状态 RPC 往返花了 **36.657 ms**，随后碰撞查询至返回为 **0.730 ms**，最后才是参考、安全估计、237D 编码及可能的锁等待，共 **2.192 ms**。另一端，Drone4 和 Drone5 两条迟确认的任务，**发布后约 3.67 ms 已经得到 DNN 输出**，随后花 **39.276 ms、38.327 ms** 才拿到命令确认代理，其中 ping 区间约 **39.196 ms、38.254 ms**。这里测的是程序看到的响应，链路、仿真器处理及主机等待还未精确分开，命令实际进入飞控的时刻也尚未测到。[原始闭环试验](Route-B关键控制更新闭环对照_20261123.md#六轮逐机恢复实测)

读每次尝试之前的准备记录和逐机确认时延，重建当时的成本。然后只改变指定的一段，问“候选周期给下一条任务的本机时间窗能否容纳这笔成本”。候选窗口从未来发布时间算起，同时受周期截止、旧命令保持截止、输入新鲜度和试验终点限制。采用该次任务日志里的保持截止，缺少完整提交快照，因此结果属于单条任务的成本筛查。计划落地还须检查任务版本、真实发布状态、同一 DPU 上的其他义务以及本机飞控是否实际用到了命令。反事实对 16 个已记录的时点各自提问，避免把前面一次改期可能改变的后续轨迹算作多次额外救回。

| 对同一批 16 次尝试做的复算 | 有一个周期装得下的时点 | 第一个满足账面的周期 |
| --- | ---: | --- |
| 保留原有成本 | 0/16 | 无 |
| 把碰撞 RPC 返回后的工作成本乐观设成零，保留此前 RPC，准备预算仍保留初始下限 | 0/16 | 无 |
| 把整段准备成本压到 5.514 ms | 4/16 | 60 ms |
| 把 DNN 输出到确认的成本压到 5.265 ms | 4/16 | 60 ms |
| 同时压低两段 | 10/16 | 30 ms |

5.514 和 5.265 ms 来自原试验的初始预算。复算用它们表示一条可测的目标线，机载系统是否能达到仍待实测。后半段缩短时原来的触发原因也可能消失。例如两条晚确认任务在已有输出后各剩约 **16.33 ms**；保持此前时间线，如果最后一段真能缩至 5.265 ms，它们就能赶上原 20 ms 截止。这个比较直接说明，应该先测命令何时被接收并使用，再判断缩短确认延迟能改善时序检测、实际控制，还是两者都改善。

## 下一次闭环怎样比较

1. **先量同一条命令的三个时刻。** 记录发出、仿真器飞控入口采用、发送方收到确认。通过控制序号配对。已在本机 AirSim 源码核对入口。`MultirotorRpcLibServer.cpp` 接收角速度与油门，`MultirotorApiBase.cpp` 将它交给 `SimpleFlightApi.hpp` 的 `commandAngleRatesThrottle`，随后调用 `setGoalAndMode`。可以记录目标被接收的时刻，再记录 `firmware_->update()` 第一次消费该版本的时刻。如果采用已经很早，优先处理确认依赖和预算归属。若采用同样晚，才有证据说明应缩短实际控制路径。仿真器时钟和墙钟要先对齐，或在同一时钟中比较相关时刻。
2. **先做两机离线和短闭环。** 保留原外部控制作为对照。为每架飞机模拟一个受限 CPU 的伴随控制单元，用相同状态接口和固定小模型或已验证的备用控制器，记录其从新状态到实际用上新命令的时间。若仍通过外部 RPC 读取状态和应用输出，就把这两个 RPC 明确计入结果，报告为外部进程代理。只有接入仿真器内的状态和飞控接口，或实际搭建本地硬件链路，才可测真正去除这段 RPC 的效果。沿用历史路线、同步时序、明确记录中央及本地产生的有效指令。
3. **再测试联合调度有多少额外价值。** 比较纯中心、同等机载预算下的静态分工、同等预算下的动态分工。先固定模型和期限定计时收益，再放开中心的 \(T,c,\sigma\)。记录实际生效间隔、最差单机空窗、共享 DPU 次数、发到中心的通信量、最小过门净空、完成率和本机资源消耗。分别测正常负载、共享队列拥堵和接入路径长尾。对于历史模拟的晚确认，也要注明注入发生在 RPC 返回后，避免当作真实飞控收命令延迟。

## 本轮复现

工程根目录运行下面的离线脚本。输出路径应指向一个新文件。

```powershell
$trial = 'controller_architecture_study/results/ps_fleet_ack_retime_20261123_001/live_h3i1EP/runs/natural_retime20/trial'
$out = 'controller_architecture_study/results/ps_onboard_partition_20261124_001'
python -m controller_architecture_study.ps_planner_repair.analyze_onboard_partition `
    --trial $trial --output "$out/screen.json"
```

两次独立输出的 SHA-256 一致。脚本读冻结日志并输出分段耗时和 16 次复算，未运行飞行或改变 PS/DPU 程序。相关原始数据需随已有 `live_h3i1EP` 归档取得。
