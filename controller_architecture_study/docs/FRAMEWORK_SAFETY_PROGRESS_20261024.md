## 本轮新增代码的具体边界

1. `framework_runtime_wire.py`：正常推理消息仅发送237D输入、模型/任务标识、冻结期限及必要时戳；输出为4D物理控制值及执行时戳。启动与清理元数据仍可使用pickle。输入在原控制器也会转成float32；输出按float64封装保留已有数值，网络内部计算不变。
2. `framework_runtime_worker.py`：后端使用上述紧凑连接。父进程保留原任务字典，返回消息不再覆盖前端分析历史；原有冻结模型和deadline核对保留。
3. `framework_runtime_flight.py`：反馈分析的经验耗时若会越过已有任务承诺的释放时刻，则先推迟这次分析，兑现已有释放。没有把原绝对deadline向后移动，也没有修改当前任务模型。
4. `tests/test_framework_runtime_wire.py`：覆盖输入/输出数值、上下文与deadline保持、消息长度、控制消息兼容及实际失败快照中的释放保护；总相关回归65项通过。

紧凑消息是CPU原型的实现优化，不能作为学术创新或控制安全保证。v15与v16同时涉及切换间隔撤回和传输格式变化，且仅少量隔离运行，不能把全部延迟差异单独归因于传输格式。

## 已明确的剩余问题

- 后端隔离测试完成，但完整运行仍观察到几十毫秒入站/通知尾部；例如v16一次入站约30.386ms，而该任务推理本身约1ms。不能再把长等待都说成DNN太大、门太难或编辑器后台节流。
- 七机动态拒绝也包含有限候选预测找不到可行计划，而非只有真实过期；它不证明理论无解，更不能算避免碰撞后完成任务。
- 经验成本各阶段取p95再串联不构成硬上界；尾部余量升级也不提供概率或最坏时延保证。后续应优先处理前端/I/O传输、已提交工作的进度可见性和规划占用，避免反复调整物理期限来掩盖问题。
- 当前六模型的合格模式分布相同，尚无状态需要不同最低复杂度的实证；不能强制模式切换或把未知格子改成合格。
- B仍是距离/速率启发式；当前正常集多数/全部由80ms更新上限约束。即使正常J好，也没有证明状态物理期限带来安全收益。

先稳定正常三机/七机端到端，再在最新实现下重新验证静态候选可行族（更快传输可能让更短周期变可行），随后才运行既定16场景发现与确认。若转向可控逻辑时钟或FPGA实测，应另立清晰协议，不把仿真时间或CPU时延当作真实FPGA保证。

## 已定位的时间记账问题

1. 旧释放锚点把可流水的IPC/推理成本按多机串行相加，可能过早启动和频繁重规划。现在最多5次完整流水线检查，试探较晚释放；不声称求得全局最晚。
2. 后端接收确认使前端知道输入已经到达，不再继续收费已完成的入站IPC。
3. 旧规划把快照时刻提前到规划预留结束，却不推进任务阶段，制造负剩余时间。已改成真实快照时刻＋前端独占规划预留，其他资源正常推进。

5. 经验p95不是硬上界。在途名义超支使用同一开发数据的带余量最大值减去已过时间；绝不重置操作时钟或物理deadline。尾部估计也耗尽则拒绝，不声称它是WCET。

## 新发现的运行环境因素

运行时只读查询：

```text
get EditorPerformanceSettings bThrottleCPUWhenNotForeground
→ True
t.IdleWhenNotForeground
→ 0
t.MaxFPS
→ 0
```

本机UE4.27源码 `Engine/Source/Editor/UnrealEd/Private/EditorEngine.cpp`：

- `ShouldThrottleCPUUsage`在编辑器非前台时读取上述EditorPerformanceSettings标志；所有窗口隐藏/最小化也可能触发节流。
- `GetMaxTickRate`在应节流时返回3FPS。
- 日志中多处相邻帧约333ms，与此环境行为一致。

**这是必须控制的环境因素，但尚未通过A/B试验证明它解释了全部RPC停顿。** AirSim物理时钟、编辑器帧率和RPC不是同一个量，不能把3FPS直接当成无人机物理更新只有3Hz。

没有编辑项目或用户ini。尝试对精确默认对象作可恢复内存修改时，编辑器明确返回 `Set commands not allowed in the editor`；读回仍为True，未把修改失败误报为关闭成功。没有使用内存注入或强制操作屏幕。

用户现已在编辑器偏好设置关闭“Use Less CPU when in Background”，并保持窗口未最小化，Agent读回False。此操作由用户完成；Agent不操作屏幕。关闭后仍有偶发时延，不能归因于单一设置。

## 实现与Framework的对应关系

当前已实现的闭环路径是：新鲜状态与实际发送的控制量 → 可替换Safety Analyzer接口 → 查表选择最低经验计算成本的合格模式 → 生成不可移动的下一控制绝对期限 → 最多5个候选的全局流水线可行性检查 → 独立共享推理核上的分段EDF → 发送新控制并读回状态。

- 当前任务的模型与deadline在提交时冻结；当前任务只能在完整段之间暂停/恢复，改模型仅对下一任务生效。
- 推理核、前端核与通信进程按不同物理核放置；试验期间Unreal排除这些物理核的两个SMT线程，结束后恢复原亲和性。不是操作系统级独占或硬实时保证。
- B先约束下一命令的最迟生效代理时刻，另有80ms更新上限，不能因“目前不危险”无限推迟更新。
- 未知/已有失败而无合格模式的查表格子会拒绝，不自动认为最大模型可以恢复；这种中止不算安全完成。
- 当前使用六个独立237D模型而非超网，允许先检验期限、接纳与分段调度主线。已有模式表中六模型的合格分布相同，不能据此声称发现了不同状态需要不同复杂度。
- B的接口记录实际控制u，但当前距离/速率公式不使用u进行动力学推导，不是用户计划中的最终CBF版本。
- 计划器是低候选数的可行释放搜索，不是数学上精确的latest feasible release，也不在线搜索(T,c)笛卡尔积。
- 当前只预测已知的下一批任务，不证明无限未来任务的可调度性。
