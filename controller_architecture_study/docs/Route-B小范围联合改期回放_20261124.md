# 给几架飞机一起改期，能排得开吗？

在同一次十机故障的约 75 ms 内，逐机改期曾 18 次被邻机挡回。这次用同一份日志试了两种做法。第一种只给原申请的飞机改期。第二种把当时下发预算单独超过周期的 3–5 架一起改期。**小范围联合改期没有找到能让全队按时的配置。** 即使让各机 RPC 重叠、免去下发后的收尾、也暂时拿掉在途任务，结论仍相同。[前一轮的拒绝归因](Route-B邻机拒绝的准备与下发预算复算_20261124.md)

## 怎样摆同一张时间表

1. 从日志找每次原改期尝试、还在运行的回路、已经发布的任务及下一次发布。所有飞机的首次未发布任务留在原采样时刻，选中飞机使用新的相对时限，更后面的发布才按新间隔走。其他飞机继续用 20 ms，模型固定为原测试的 ID 11。
2. 首次更新继续受旧命令保持期限和新鲜度限制。保持期限取有匹配版本的已记录观测和 ACK 后最多可保持时间中较早的一项。没有可确认的匹配观测时，宽松回放只保留 ACK 后的绝对上限。后续任务以首次按时交付为前提，检查它们的周期和新鲜度。
3. 使用原有 30、40、50、60、80 ms 候选，在同一快照之后 **80 ms** 的发布窗口内比较。先检查单架独占时也能否完成，只有过这关才进入共享 PS 和非抢占 DPU 回放。搜索只是离线检查有限周期网格。
4. 在途任务按原轨迹单列。当前安装规则遇到尚在 DPU 或下发阶段的邻机就拒绝。新任务的离线回放先放宽这道门并忽略在途负担，给联合改期更有利的条件。只要这个宽松检查仍有单机时间缺口，就能指出准入门以外的具体障碍。日志没有记录每次持锁时的完整快照，因此这些结果不承担在线提交或物理安全承诺。[回放实现](../ps_planner_repair/replay_joint_retime.py)

## 结果

18 个时点里，有 **1 个**已经越过一架邻机的原发布时间。它不进入新任务网格回放。其余 **17 个**使用同一个候选表对照。

| 回放给定的条件 | 维持 20 ms | 只改原申请机 | 一起改 3–5 架 |
| --- | ---: | ---: | ---: |
| 原规则记账，整段准备和下发计入共享 PS，收尾用统一预算 | 0/17 | 0/17 | 0/17 |
| RPC 可重叠，保留统一收尾预算 | 0/17 | 0/17 | 0/17 |
| RPC 可重叠，收尾按每架飞机的已观测预算计算 | 0/17 | 0/17 | 0/17 |
| RPC 可重叠，收尾取零 | 0/17 | 0/17 | 0/17 |

最宽松一行里仍有两个很具体的原因。

- **前 15 个可回放窗口还漏了 Drone8。** 它的下发预算只有 15.916 ms，单独看低于 20 ms，所以没有进入联合组。但加上准备 6.859 ms 和 DPU 1.934 ms，最少也要 **24.709 ms**，就差了 **4.709 ms**。按这套经验预算看完整路径，即使先不算争用和收尾，每个窗口也有 **7–9 架**需要更宽的时限。原来的 3–5 架名单每次都漏掉 Drone2、Drone7、Drone8 和 Drone9。
- **最后 2 个窗口，周期调再长也撑不到。** Drone10 的第一次待发布任务从原采样点到旧命令保持到期只剩 **28.418 ms**，但准备、推理、下发要 **33.493 ms**，差 **5.075 ms**。即使所有其他飞机都让路，延长周期也不能让这个旧命令保持得更久。

在途日志还指出，即使将来找到了新任务可行方案，提交也有独立障碍。**18/18** 在决策开始后至少 1 ms 内还有邻机在推理或下发阶段。**14/18** 有一条已发布任务在原日志中占用本机工作线程，延续到该机下一次原定发布之后。**8/18** 距队内最近发布不满试验预留的 1 ms，其中包含已经越过发布点的一次。三组数字描述同一批窗口，存在重叠。

## 可以据此做什么

这批日志支持两个改变研究优先级的结论。第一，诊断谁需要一起改期时，要看整条控制路径，单盯下发是否超过周期会漏掉其他飞机。第二，等到这一批失败都冒出来再改，部分旧命令的保持窗口已经用尽。更早处理才能给中央方案留下机会。在中央短时间给不出新命令时，让机载路径独立更新，是另一个值得做小规模验证的机制。[机载分工设计](Route-B机载分工与时序初筛_20261124.md)

本轮完成离线验证，线上仍使用上一版规则。支持或否定更早触发、机载控制以及其他负载条件下的联合改期，需要各自的测量。这里的 18 个时点来自一次故障，不能按 18 次独立试验统计。
