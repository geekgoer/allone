# 提前预警、恢复模型与端到端期限：本阶段实现和结果

## 完成的改动

1. 新预警读取已有未来2秒参考的整段几何变化，替代0.4秒后的单点加速度阈值。进入恢复模式后，未来无转弯且跟踪误差、速度误差、余量趋势稳定0.5秒，才允许退出快速模式。
2. 实际筛查同一237D数据训练的18个已有plain MLP，不改权重、不重新训练、不降低门洞或过门余量标准。原6个FALCON尺寸模型在校准种子0的Drone9后段路线、20ms请求周期下均接触末门。其余12个中，2×128和3×256通过，并在此前失败的种子3路线复核通过。
3. 两个通过模式可按独立校准结果加入模型池。选择计算成本较低的2×128，仅用于已检验的Drone9恢复分支；原来cruise/recovery同模型的占位已被真实下一job模式切换替代。归一化、源权重哈希和校准路线条件均核对。
4. 新增端到端预测检查，覆盖采样RPC、前端处理、输入IPC、有限段计算／排队、输出IPC、命令RPC及后续通道占用。复用现有有限事件流水线模型，最多检查当前释放计划和一个更早释放计划，不重新做大规模(T,c)搜索。
5. 启用期限保护时，先在物理控制任务开始前检查整个初始任务集。不可准入就不开始闭环任务，避免“启动后挨个停机、零碰撞”被误报为成功。运行中检查新计划、过期输出、发送裕量、命令实际迟返以及最大控制更新间隔。
6. 预测拒绝、实际超期、物理接触分别记录。截止时间与已运行job的模式不被后续规划修改，静态周期日历也不为掩盖释放抖动而重写。

当前92项相关检查通过，PowerShell入口语法检查通过。模型推理仍在独立CPU资源上按完整两层FC的边界执行，尚未迁移FPGA。

## 预警是否提前、是否还过早降频

旧规则：Drone9约8.1秒才首次请求20ms，且连续转弯中多次放回60ms；第一弯从7.14秒开始。

修正后最近一次记录：5.55秒进入20ms请求，保持到14.60秒左右才退出。提前约1.59秒覆盖第一弯，没有再在连续转弯中因一个加速度低点退出恢复模式。Drone9使用2×128后，在最新物理期限版本的十机观察实验中通过。

该次动态策略分析平均约0.385ms、p99约1.004ms。它包含预算、预览及选择逻辑，不能当成真实FPGA开销或WCET；只是当前CPU实测。

## 时间定义修正

旧原型还继承了FALCON式的名义期限D=T，并将它与B求交。这不是新版框架唯一的物理安全期限。

新版动态分支使用：

```
当前实际控制对应的剩余安全预算期限
与
当前控制生效代理时刻 + 最大控制更新间隔
取较早者
```

当前B仍是门框几何／速率原型，最大更新间隔仍为80ms，命令RPC确认作为生效代理。名义请求周期及其偏差另外保存为质量指标，不能冒充B约束是否满足。

若T是从当前命令生效到下一次任务释放的等待时间，R是从释放到下一次命令生效的完整响应时间，则对应T+R≤B。若T是释放到释放的周期，需要同时考虑前后两次R，不能混用时间原点。

检查在新计划生成后即进行，允许在保持截止时间和模式不变的条件下提前未释放任务；不等到原定释放时刻才检查。突发的风险采样可以请求更早执行，不会凭一个名义周期目标重新定义物理截止时间。

## 观察实验与严格保护必须分开

开发中保留了三个版本，不删除负结果：

| 版本 | 种子 | 静态接触架数 | 动态接触架数 | 动态整体过门／末尾检查 |
|---|---:|---:|---:|---|
| 预警／模式修复，仍混合名义期限 | 3 | 2 | 0 | 一处未达额外过门余量 |
| 同上 | 4 | 2 | 0 | 通过，但期限仍失约 |
| 明确物理期限后的版本 | 4 | 3 | 2 | 未通过；接触者为Drone1和Drone3，Drone9通过 |

因此不能只选择中间一行宣称稳定救回，也不能把最新结果写成整个框架已验收。时间约束／EDF优先级定义变化会改变实际轨迹，需要继续验证。

另外，动态新增了两个已筛查的小模型，而冻结静态基线来自先前6模型、20候选的有限搜索。本批用于开发诊断，**不是最终同模型池、重新离线选优后的FALCON公平对比**。正式比较前必须把同一候选池提供给两种方法。

最新严格保护版本：`preflight_enforce_seed4`。两组初始十机任务集在当前冻结经验时延模型下均未准入，DNN闭环请求数与施加数均为0；记录为任务未完成、物理验收失败、准入拒绝，不记录为安全飞行成功。

早期`paired_enforce_seed4`及`physical_deadline_enforce_seed4`是在物理任务开始后逐回路记录拒绝的开发版本，也保留用于对照；不要将它们与最终启动前准入混用。

## 为什么未必是算力超载，也不是自动变成软deadline

必须区分三件事：

- **资源／候选不可行：** 给定c、截止时间和时延假设，找不到满足全部已承诺期限的释放／执行安排。
- **模型保守或不充分：** Windows阶段尾延迟有波动，把各阶段最大值同时叠加可能很保守；只检查两个释放候选，也不能证明任意调度都不可行。
- **实际超期：** 已运行任务确实在真实截止时间后才返回。这是硬要求的失败，不能因为继续飞完而抹掉。

早期检查中，纯计算利用率估计仅约0.295～0.504，仍未通过完整流水线检查。可见不能一律归因于DNN计算资源超过100%。在那个记录里，单job的经验端到端包络约73～79ms，名义初始期限仅60ms；去掉排队也不能在该模型下满足60ms。最新版已将名义目标和物理期限分开，十机任务集仍未在该经验模型下准入。

包络冻结自原校准搜索的`candidate_15/requests.json`，使用每阶段观测最大值×1.25+0.2ms，保留尾部观测，不为制造成功而裁掉异常值。但这些数值**不是WCET证明**，也不证明现实中一定需要这么久；观察模式实际R通常小得多。

硬／软deadline是要求的语义，不是“程序有没有失败过”的分类。硬约束优化问题可以没有可行解；应限制研究适用域、调整配置／负载或报告不可行。若允许违反B仍算正常成功，只在性能函数中扣分，才是在把该要求软化。丢弃过期输出本身也不能建立硬实时保证。

当前正确表述为：**以状态相关期限为硬约束的框架原型，已实现经验模型下的准入、检查和拒绝机制；尚未获得当前十机域的硬实时／物理安全保证。** 要宣称保证，还需要可信的端到端时延界、可调度性论证及具有相应动力学含义的B。FPGA加速计算可以改善其中一部分，但不能替代这些条件。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "F:\FalconReproduction\airsim_control\controller_architecture_study\run_anticipatory_repair.ps1"
```

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "F:\FalconReproduction\airsim_control\controller_architecture_study\run_anticipatory_repair.ps1" -DeadlinePolicy observe -Interactive
```
