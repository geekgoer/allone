# 当前Framework是怎样实现的：易懂说明

更新日期：2026年11月2日。本文依据当前代码和最近试验说明实际行为，区分“正在控制飞机”与“可选建议链路”的部分。

> 后续已交付[CPU/XPU与建议服务修复](CPU_XPU_SERVICE_REPAIR_20261102.md)，真实试飞待用户运行。下文“建议排在已就绪工作之后”描述旧版本；新版本在主循环前部提供计费的CPU服务，CPU协调器选段、独立模拟XPU执行。历史飞行数字不变，最新实测以协作进度为准。

> 本轮已完成120次有效恢复采样和12次自然十机试飞。真实周期提交入口已实现：首轮安装过1组、15条标记控制实际完成；优化后的复核安装0组。旧动态方案能完成零碰撞，但新增评分器的额外收益尚未证明。详见[阶段结果与后续顺序](F:/FalconReproduction/airsim_control/controller_architecture_study/docs/BOUNDARY_TAKEOVER_RESULTS_20261102.md)。默认仍不打开新建议的真实提交。

## 1. 先用一句话理解

**每架飞机按自己的时间表请求控制计算；系统看到某架飞机越来越危险，就尝试让它更早获得下一条控制，同时检查这样做会不会挤占其他飞机的资源。**

可以调的三个东西是：

| 符号 | 用普通话解释 | 当前怎么实现 |
|---|---|---|
| T：控制周期 | 隔多久请求一次新的控制计算 | 修改这架飞机下一次任务的释放时间和后续名义周期 |
| c：DNN配置 | 用哪个网络计算控制量 | 实际飞行使用预设巡航/恢复模型；新的学习选型仍在影子验证 |
| σ：调度 | 多架飞机都要计算时，先算谁 | 固定使用分段EDF，每段结束后让绝对期限更早的任务先算 |

这里不是“危险时一律换最大的DNN”。大网络未必恢复得更好，而且更慢的计算也可能抵消精度收益。

**直接回答频率问题：通常每次获得可用的新控制反馈，就更新该机的局部危险判断；另有目标约20ms的独立监测。新全局联合选择通常约50ms合并一次，紧急事件可提前触发；EDF则在每个计算段结束后重排。因此不是每架飞机每个周期都完整搜索一遍T、c和σ。**

## 2. 当前有两条并行链路，不能混为一谈

```text
AirSim状态、当前正在作用的控制命令
              │
       ┌──────┴────────┐
       ▼               ▼
实际控制链路         可选联合建议链路
规则识别危险         计算控制相关的安全预算
提出周期/模型调整    小型模型给候选方案评分
检查共享资源         显式优化器联合选择方案
按分段EDF执行        用最新状态重建、全组复核
       │               │
       ▼               ▼
控制命令发给AirSim    记录建议和检查结果
                     默认只记录；显式启用后可提交
```

**实际链路已经会动态调整周期、按规则切换模型和改变计算顺序；新建议也有真实提交入口，但尚未证明额外控制收益。本轮对照固定每架飞机的DNN，只验证周期/释放时间建议。**

所以，“十机试飞零碰撞”与“新评分器已经救回十架飞机”是两回事。最近两次完整十机组的原子检查通过，证明新方案在当时的模型和上下文下通过了检查，尚不是执行后的安全收益证明。

## 3. 飞机平时是怎样被控制的

可以把一次控制任务理解为一次“问诊—开药”：

1. 到达预定释放时刻，系统登记这架飞机有一个新的计算请求。
2. 请求获得处理机会后，读取位置、姿态、速度等状态。
3. 根据参考轨迹构造237维DNN输入。
4. 将任务放进共享计算队列。
5. 被选中的DNN分段计算，得到4维控制量：推力加速度和三个轴的角速度。
6. 将控制量发送给AirSim。
7. 收到命令确认和可配对的新状态后，更新这架飞机的情况，考虑后续任务怎么安排。

**计算器是共享的，飞机的时间表是各自独立的。**当前用一个分段CPU执行器模拟共享加速器，采样、通信、前端处理与推理可以部分重叠。

已有的控制网络在运行前加载，不是每个周期重新读一次模型文件。某个任务发布时就确定使用哪个网络，算到一半不会突然换网络。

## 4. 系统怎样发现危险

### 4.1 实际飞行链路：观察当前趋势，再看前方路线

主要看三类信息：

- **现在偏得多不多**：离参考轨迹和允许边界还有多少余量。
- **偏差是在变好还是变坏**：是否继续朝边界运动，是否可能越过中心后撞向另一边。
- **接下来是否要急转**：查看已知参考轨迹未来约2秒的横向、高度变化。

例如，飞机目前还在中央，但前方马上连续转弯，就可以提前进入恢复模式。它不必等到马上碰到门框才要求缩短周期。

恢复后也不会立刻降频。已有规则要求位置、速度和运动趋势稳定，并持续约0.5秒，才退出恢复状态，避免刚好回到中间就过早放松。

这里的2秒是当前原型的路线预览参数，是一种提前识别规则，**不是“未来2秒已经获得安全证明”**。

### 4.2 新影子链路：计算当前控制还能保持多久

新链路考虑：当前状态、当前实际控制、门框几何，以及显式给定的动力学误差界。

它问的是：

> 如果暂时保持现在这条控制命令，在哪个时间范围内，还能根据这些假设得到不进入门框的充分条件？

代码使用控制相关的HOCBF区间下界，并把门框表示为膨胀后的有限盒子。它不只是用“横向距离÷横向速度”。

但有两个重要边界：

- 这部分已经实现并在影子链路使用，尚未全面替代实际飞行链路中的几何/恢复预算规则。
- 扰动和模型误差上界仍是开发假设，尚未认证；因此不能称为对AirSim或真实无人机的无条件物理安全保证。

## 5. T + R ≤ B，在代码里是什么意思

你的核心想法是：**下一条新控制必须在当前安全等待预算耗尽前赶到。**

- T：等待下一次计算请求的时间安排。
- R：请求释放后，到新控制返回所经历的响应时间。
- B：当前状态和控制对应的等待预算。

R不只是DNN计算时间，还包括采样、输入处理、排队、推理、传输和命令下发。因此只看“DNN只算了1ms”不能判断是否来得及。

为了避免混淆不同时钟，程序主要使用**绝对期限D**：

> 下一条控制命令最晚要在D这个时刻被接受。

新安全分析中，若状态在时刻s采到，剩余hold预算为B，当前控制在a时刻获得确认，则采用：

`D = min(s + B, a + 80ms)`

80ms是当前原型附加的控制更新上限，不是FALCON规定的常数，也不是你推导出的物理定律。

分析或排队已经花掉的时间不会凭空消失：若状态已经旧了10ms，这10ms就已经占用了预算，不能从“现在”重新获得完整的B。

实际执行中，程序用命令RPC确认时刻作为控制生效的代理；它不是电机实际响应的精确测量。

## 6. 危险时怎样选控制周期T

### 6.1 实际链路：先提出要求，再做全局检查

目前主要采用以下规则：

1. 急转或恢复需求明显时，提出约20ms的更新要求。
2. 平稳时通常倾向约60ms，减少计算请求。
3. 若大家都加频导致资源吃紧，优先放宽较不紧迫回路的周期。已有分配器使用20、30、40、50、60ms等工作点。
4. 联合检查正在排队、正在计算、等待通信的任务，以及所有参与回路的后续任务。
5. 能通过检查才提交这组变更；不通过则保留原配置或按既有恢复分支处理。

因此，**“危险时请求20ms”不等于“无论资源如何都保证20ms的新命令到达”**。

### 6.2 新影子链路：用有限候选联合选择

新选择器已不只考虑20/60ms：

- 常规周期候选包括20、35、50、65、80ms。
- 还加入当前周期，以及由最早合法释放、最晚可行释放推导出的候选。
- 所以可能出现列表之外的周期值，但不是无穷精度地穷举所有时间。

周期和模型组合先被评分，再由显式优化器分配共享资源。可以把它理解为：

> 先让每架飞机提出自己更喜欢的方案；资源不够时，给资源占用加“价格”，优先舍弃预计损失较小的选择，再检查整组能否及时完成。

这个方法有固定的搜索和时间预算，没有枚举十架飞机所有配置的笛卡尔积，也不保证找到了真实飞行性能J的全局最优解。

若建议返回时已不适用，前端会用最新状态重建；必要时在剩余预算内保持当前模型、只重算周期，尝试恢复整组时序可行性。默认只记录；显式启用真实提交后，通过最新全组检查与原生原子检查的建议才会安装。可选建议处理排在已就绪的前端控制工作之后。

## 7. 危险时怎样选DNN配置c

### 7.1 实际飞行：每机预设巡航/恢复模型

目前不是每个周期把8个网络都算一遍，再挑一个。

每架飞机有预设的巡航和恢复模型，进入/退出恢复模式时按规则切换。最近十机配置中，实际映射为：

| 飞机 | 巡航模型 | 恢复模型 |
|---|---|---|
| 1、3、9号 | 2×128 | 2×128 |
| 2、10号 | 9×1024 | 9×1024 |
| 4–8号 | 9×1024 | 9×512 |

这说明两件事：有些飞机恢复时只调整周期和计算顺序，不换DNN；也存在恢复模型比巡航模型更小的情况。当前没有假设“大模型必然更安全”。

该表只是最近这组试验的配置，不是框架写死只能这样。

### 7.2 新学习选择器：给方案打分，不直接控制飞机

新小模型输入的是当前状态特征、几何余量，以及候选的模型、周期和预计等待时间，输出相对效果评分。

它是一个486系数的线性条件模型，**不是另一个负责输出推力的控制DNN，也不是把整个调度器塞进神经网络**。

它只负责建议：哪种组合预计更有价值。随后仍要经过全部任务的deadline、资源和原子上下文检查。没有足够优势证据，或者超出已测工作范围，就保留基线/当前模型。

目前它的泛化和训练数据区分度仍不足，保守版本经常回退。因而“低成本且合格的DNN自动选择”还不能称为已经完成验收。

另外，当前实时实验使用的是8个独立237D网络。已训练的136配置超网尚未接入这条控制链路。

## 8. 危险时怎样改变调度σ

**目前没有在线选择“这次用EDF、下次用RL、再下次用另一种调度算法”。算法固定为分段EDF，变化的是任务的期限和执行顺序。**

EDF的意思是：绝对截止时间更早的任务优先。

例如，现在是100ms：

| 任务 | 最晚完成时刻 | 从现在还能等多久 |
|---|---:|---:|
| A | 112ms | 12ms |
| B | 140ms | 40ms |

A优先。不是单纯比较两架飞机原始B值谁小，因为状态采样时间、已等待时间也会影响实际紧迫性。

每个DNN切成若干段，每段最多包含两层全连接及对应激活：

```text
B计算第1段 → 到达段边界 → 检查队列
                            │
                       A更紧迫，先算A
                            │
                       再回来继续B
```

**只能在段边界抢占，不能随时打断某条运算。**暂停任务的中间结果保留，恢复后继续算同一个输入、同一个网络。

也不会拿上一个控制周期的激活直接作为下一个周期的结果，因为输入已经变化。当前分段CPU实现也不能直接等同于已完成FPGA有限抢占加速器。

## 9. 到底多久检查一次

这是最容易混淆的部分：系统中有多个不同频率。

| 工作 | 什么时候发生 | 是否每次都做完整联合搜索 |
|---|---|---|
| 每架飞机请求控制计算 | 按自己的已提交释放日历，通常几十毫秒一次 | 否，只产生一个控制任务 |
| 更新局部状态、危险判断和后续规划 | 新控制确认后，有可配对的新状态时；开始飞行时也做一次 | 主要是规则判断和准入检查，不是每次都运行新评分器的完整搜索 |
| 独立危险监测 | 每架飞机目标约20ms一次，与它当前控制周期分开 | 否，主要看运动趋势和危险事件 |
| 新后台全局选择 | 普通状态变化约50ms合并一次，处理整组回路 | 是，但一次整组选择，不是每架飞机各做一次 |
| 紧急触发 | 预计响应余量从正变为非正时，可绕过普通50ms合并等待 | 触发新建议，仍需计算和复核，不保证瞬时完成 |
| 推理任务重新排序 | 每个计算段结束时检查队列 | 否，只按EDF重新选下一段 |
| 新建议提交前复核 | 后台有适用建议返回时 | 用最新状态和队列复核；必要时做一次有界周期修复 |

例如十架飞机都以20ms请求控制，每秒可以产生约500个控制任务，**不意味着每秒运行500次新全局配置搜索**。普通合并机制下，全局选择大致每秒20次；危险边缘事件可能增加触发次数。

这里的20/50ms都是程序的目标节奏。Windows调度、RPC、繁忙队列可能导致实际观测或处理更晚，它们不是已经证明的最坏时间上界。

## 10. T设为20ms，是不是就每20ms执行一次控制

要分清两件事：

- **请求释放**：原生C++日历按时间产生请求，不需要等上一条DNN算完才产生下一条。
- **新命令到达**：请求释放后还要经历响应时间R，不能保证每个请求都立即获得计算和通信资源。

例如，两次任务相隔20ms释放，但前一次R为4ms、后一次R为10ms，那么两条新命令的到达间隔就是26ms。

所以控制周期是独立的任务到达安排；实际新命令间隔还受响应时间变化影响。正因为如此，框架才需要同时管T、R和共享资源。

如果来不及处理，同一架飞机尚未派发的旧请求可以被更新请求替代，替代会记入日志，不算作旧请求已经成功执行；已发布任务的模型、期限也不能随意改写。

## 11. 用一个危险场景串起来

以下数字仅帮助理解，不是新的实测结果：

1. 某架飞机原来按60ms安排更新，前方开始急转，横向余量持续变小。
2. 控制反馈、路线预览或独立监测发现趋势，提出进入恢复状态。
3. 假设当前分析只允许再等40ms，而原计划“60ms后释放再加8ms响应”显然太晚。
4. 系统尝试更早释放，例如20ms后请求；如果整组预测响应为10ms，则可以在这40ms预算内完成。
5. 若资源不够，尝试让宽松回路少请求一些计算，但它们各自的期限也必须满足。
6. 新任务进入队列后，分段EDF在可抢占点优先服务绝对期限更近的任务。
7. 当前已生效链路按预设规则执行调整；新学习链路默认记录建议、重建后的全组预测与原子检查结果，显式启用后才可提交。是否执行以实际命令版本标记为准，不能只看建议计数。

**不是先无条件缩短一架飞机的周期，再祈祷其他飞机没事；目标是先联合检查，再改变尚未发布的任务安排。**

## 12. 当前能做到什么，哪些还不能说已经完成

| 内容 | 当前状态 |
|---|---|
| 独立释放日历、状态反馈、独立监测 | 已接入实际飞行 |
| 规则式周期调整、预设模型切换 | 已接入实际飞行 |
| 两层FC为一段的有限抢占EDF | 已接入共享CPU执行器 |
| 其他回路的资源和期限检查 | 已实现，但基于实测包络和有限任务预测，不能保证所有情况下都可行 |
| 控制相关的HOCBF安全预算 | 已实现，当前主要用于新影子链路，假设尚未认证 |
| 学习评分与联合配置选择 | 已实现，默认影子运行；额外收益未证明 |
| 最新状态重建、完整十机组原子复核 | 已实现真实提交；首轮1组，优化复核0组，不代表普遍可用 |
| 可靠的最低成本合格DNN自动选择 | 尚未验证完成 |
| 全程严格满足所有物理deadline | 尚未验证完成 |
| 超网、PL加速器、板端真实分段抢占 | 尚未接入当前实时实验 |

最近的试飞是允许记录超期、继续观察物理结果的模式，不会因为一次新建议失败就强制停掉全部飞机。新建议被拒绝后保留旧方案，也不代表旧方案已经获得安全证明。确认发生碰撞时，最近多机试验按单机退出处理，其余飞机继续运行。
