# 八机动态安全框架比较：完整阶段结果（2026-10-23）

## 结论

本批已执行完 24 个静态候选、1 次动态正常工况、16 个状态的双策略配对，共 57 次八机试飞。动态正常工况通过，但 **0/16 个扰动状态满足“静态真实碰撞、动态完整完成，且双方时序有效”的成功判据**。

不能宣称已经证明新框架的安全优势。动态零碰撞主要伴随超时中止，不等于完成任务且安全。当前结果也不能推翻整个研究想法：本实现只验证固定模型下的动态截止时间/释放规划组件，没有完整实现状态到合格 controller mode 的选择、准入保证或严格 Safety Analyzer。

## 1. 本轮到底运行了什么

- AirSim 启动配置中有 12 架真实 pawn；本实验是 **8 架活跃控制回路**，不是 12 机实验。
- Windows、CPU、一个共享分段推理进程。两策略都限制一个完整任务在途，包含采样、特征、IPC、推理、发送。因此不声称实际发挥了层内抢占优势，也不是 DPU/FPGA 结果。
- 三个冻结的 237D plain MLP 候选，未训练或改写权重。网络可以按 FC/ReLU 层组分段，回归测试检查函数一致性与独立上下文。
- 使用已有 environment 48 / route 1 的曲线路径；净门宽 2m，高 4m，不缩小无人机碰撞模型。各机独立门组相隔 12m。
- 固定 3 秒任务。物理轨迹起始相位从 5.9355s 到 3.8355s 等距分布，与控制任务释放相位是不同概念。
- 预期通过门 ID 来自保存的参考轨迹：Drone1/2 为 [3,4]，Drone3–6 为 [3]，Drone7/8 为 [2,3]，合计 12 次预期有效穿越。任务要求不根据实际结果降低。
- 无 MPC fallback；过期输出不施加。悬停、中止和未覆盖完整窗口均不计任务完成。
- 没有操作屏幕；没有覆盖原三机 AirSim 配置。

## 2. 静态基线范围

这里是 **FALCON-style 受限实测近似**，不是完整原文复现：固定 CPU、3 个模型、6 个周期和有限邻域，不使用缺失的 SVM，也没有全硬件映射或全配置搜索。

评分采用原文 Eq.(4) 形式的跟踪性能：位置、速度、四元数状态误差，Wx=I10，20ms 公共插值网格、K20 窗口、窗口成本均值的倒数，最后对八机等权求和。它不是 DNN 模仿 MPC 的标签 MSE。原文完整数值权重未获得，所以不能声称数值 J 与论文完全相同。

已测网格是 3 模型 × T={25,50,75,100,125,150}ms，再检查相位翻转、优先级反转、最后一机的模型/相邻周期，共 24 个候选。只从任务完成、时钟有效、无过期输出和命令返回越期的候选里选实测 J 最大者；不是全局最优或重复统计确认的最优。

选定 `neighbor04`：八机均 `plain_mlp_h21_w512_seed0`；Drone1–7 的 T=D=100ms，Drone8 的 T=D=75ms；错峰释放，固定优先级 Drone1 到 Drone8。

## 4. 能确定的问题与不能确定的结论

### 已修复且有回归的实现问题

1. 命令发送后的规划必须使用 RPC 返回后的新时刻，不能用 RPC 之前的旧 now。
2. Windows 的 `Pipe.poll(0.0005)` 在本机实测约等到 15.5ms，造成不必要的 ready 等待。改为非阻塞 poll 加短 sleep，未修改系统定时器或 NVIDIA 驱动。
3. 各回路独立推迟释放可能挤占彼此承诺。v4/v5 每次交付后按绝对 deadline 统一重排所有尚未释放的任务，绝不延长 deadline。
4. 不同物理相位的任务要求由参考轨迹预先确定，不再写死每机两门。

相关单元回归共 12 项通过；不构成闭环或连续时间证明。v4 同步物理相位工况的失败也保留在独立目录，未覆盖成 v5 的成功。

### 当前瓶颈证据

将所有扰动任务日志合并后，测得完整任务时间均值约 10ms，p99 约 21ms。DNN 只是其中一部分：

| 阶段 | 静态均值 / p99 ms | 动态均值 / p99 ms |
|---|---|---|
| 状态与碰撞 RPC | 2.251 / 2.980 | 2.143 / 2.932 |
| 参考与特征 | 1.999 / 2.671 | 1.908 / 2.636 |
| CPU DNN 实际计算 | 2.638 / 3.664 | 2.524 / 3.590 |
| ready 到前端处理 | 1.333 / 2.179 | 1.301 / 2.114 |
| 命令 RPC | 1.044 / 12.751 | 1.064 / 12.575 |
| 完整任务 | 10.101 / 21.896 | 9.771 / 21.416 |

各列样本数因过期未施加或缺失某阶段而不同，不可以把各阶段 p99 相加得到响应时间 p99。完整任务只统计有命令返回的请求，可能存在成功样本偏倚；原始失败日志保留。

两个有代表性的首次违规：

- `i0_sign-1_v0.6` 的 Drone8：DNN 计算 2.892ms，任务开始时剩余 33.85ms，但完整处理用了 38.71ms。说明只按推理耗时推断可调度性是错误的。
- `i0_sign-1_v1.8` 的 Drone1：新状态上的启发式预算已缩至约 9.05ms；任务开始时承诺截止时间仅剩 5.49ms，最终约 7.65ms 才被处理而过期。单纯 EDF 排序不能让已无资源余量的系统变可行。

当前预测成本每任务约 17.24ms，来自正常工况 p95 加余量，**不是 WCET**。规划预测不可行后仍继续 best-effort 派发，这不满足“准入后可保证响应时间”的完整框架语义。

### 研究边界

现在使用的是距离/速率启发式 B，尚未实现依赖实际 held control、动力学和不确定性界的严格 safe period。它既可能过于保守，也可能漏掉风险，不能把零超期等同于物理安全保证。

命令返回时刻是异步发送加 ping 的 RPC 代理，不是硬件上真实控制生效时间。Windows 桥接的尾时延不能直接当成 FPGA 加速器的执行特性。

本批固定两策略的 controller modes 来隔离释放/调度的作用；没有证明危险状态需要更大 DNN，也没有测试超网切换收益。因此这不是“整个 framework 已完成”的验收。

## 5. 下一步应该改什么，而不是继续堆测试

1. **先完成可行性闭环。** 预测不可行时不能继续声称已获保证。明确是切换到已验证合格且成本更低的 mode、拒绝新增任务，还是进入明确标注的 best-effort；未完成任务仍不能记安全成功。
2. **资源模型要对应实现。** 当前把状态 RPC、参考构建、DNN 和命令发送全部当一个串行资源，尚未利用已做的层段。下一阶段优先将共享推理与前端分离，采用有界在途请求、及时处理 ready 输出和明确的剩余阻塞记账；两策略使用相同流水线。不要只给新方法降低采样成本。
3. **单独检验已有 Safety Analyzer 的适用性。** 按已确定的接口接入当前控制与允许等待范围；如果改 B 的假设或形式，另开版本、重做基线。不能为了通过实验把 9ms 改大，或在失败后重置物理 deadline。无需现在引入 DNN 误差实体。
4. **然后只做必要复测。** 先正常工况与一组固定扰动回归，确认新的资源/时间记账没有额外 overhead；通过后再用同样的完整预声明对照集判断安全优势。若找到差异，再做独立重复，而不是以发现阶段单个好结果结束。

不建议现在继续训练大 DNN、缩到 0.75m 的门、把中止计成功，或直接将上述结果转述成 FPGA 安全优势。下一阶段应先解决上述实现与准入缺口，而非再增加一轮不变实现的参数扫描。
