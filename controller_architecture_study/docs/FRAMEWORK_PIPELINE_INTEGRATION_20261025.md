# 七机状态感知框架：集成结果、当前缺口与下一步

日期：2026-10-25。当前源码入口版本为v37；运行目录和源码哈希优先于旧文件中的版本文字。v35/v36的一些setup仍写着v34，这是已修复的元数据错误，原文件没有事后改写。

## 结论先行

**尚未得到“静态真实撞门、动态按时完成同一任务”的有效配对胜例。** 不能把动态提前中止、清理悬停或没有观察到碰撞写成安全成功。

状态相关计算预算存在实验依据：已找到及时接管能恢复、等待更久不能恢复的状态。但当前模式表与调度原型还不能稳定兑现这些紧急预算。正常工况旧实现的成功，不能替代最新预测器的验收。

本阶段没有重新训练DNN、改权重、改归一化、缩窄门洞或扩大安全期限。111项相关回归通过，包含进程通信、段边界抢占、Windows计时器和期限不可延长检查。机器可读记录在[阶段审计](../results/framework_pipeline_stage_20261025/audit.json)。

## 实际实现了什么

链路为：当前状态与正在施加的控制 → 预算分析和经验模式查询 → 下一任务的模型与有限释放规划 → 两层FC为一段的EDF执行 → 命令发送与后续状态反馈。

- 七架真实AirSim仿真无人机同时运行，共享一个CPU推理执行器；每次只在完整段边界重选任务。
- 每个已释放任务的模型和绝对期限固定。没有段内抢占，没有在推理中途增宽/增深。
- 使用六个既有237D独立模型：隐藏层9/21/33，宽度512/1024。这里不是超网运行，也不是DPU或手写PL加速器的时延实验。
- 推理、前端和通信分配到不同物理核心，Unreal避开相应SMT兄弟核心。操作系统没有提供独占核心或硬实时保证。
- 模式查询选当前经验合格集合中估计成本最低者；不假定大模型恢复能力必然更强。
- B仍是距离/速率启发式，控制量虽记录在接口中，尚未进入动力学安全界计算。没有CBF证书，也没有增加DNN近似误差模块。

当前下一次控制的绝对期限取以下约束的最小值：

\[
D^{ctrl}_{k+1}=\min(s_k+B_k,\ a_k+T^{ctrl}_{max},\ s_k+\delta_m,\ a_k+H_m).
\]

其中s_k为后续状态观测时刻，a_k为前一命令返回代理时刻，δ_m为模式等待限制，H_m为模式更新间隔限制。任务实际释放时进一步收紧：

\[
D^{job}_{k+1}=\min(D^{ctrl}_{k+1},\ r_{k+1}+A_m).
\]

A_m为输入年龄限制，目前为30ms。真实状态采样通常晚于请求释放，因此从释放起算更保守；发送前及命令返回后仍检查实际输入年龄。已发布的期限不向后移动。命令返回只是send+ping代理，不是硬件生效确认。

## 任务和对比边界

门洞净宽2m、高4m，使用0.5m无人机包络半径与0.025m净空。航道间距12m；七机使用同一保存的转弯路线、不同参考阶段，标称5m/s。验收窗口为3s，要求穿过该窗口内预期的门、足够前进进度、最后250ms跟踪恢复、无新碰撞、时序和物理时钟均合格。这不是整段五门任务完成率。

碰撞来自`simGetCollisionInfo()`的新事件时间戳，不再依赖未填充的`getMultirotorState().collision`。初始历史碰撞不当作新碰撞。

静态配置固定为此前52候选及重复复核中选出的9×1024/T40、错峰启动、Drone1到Drone7固定优先级。这是有限FALCON式经验搜索，没有SVM、完整硬件搜索或全局最优证明。运行时继续改进后，最终论文对比前还需复查更短周期候选，不能一直宣称旧选择是当前实现的最优。

J采用K=20、Wx=I、统一20ms采样网格的倒数状态代价形式，**越大越好**。只有完整可比任务才比较总J；碰撞或中止前的部分轨迹不与完整任务比较。

## 持续输入老化检查

`recurring_input_age_v2`对三个开发初态测试每次更新均有输入老化，而不仅是第一次：新鲜、约10ms、约25ms及5/30ms交替，共12个条件。

- 12/12恢复，无实际碰撞。
- 10/12实际最大更新间隔不超过40ms。
- 另2个条件测得42.000896ms，虽恢复，也没有作为40ms合格协议加入模式表。
- 三个交替延迟条件测得最大输入年龄约30.000640ms。

这些是暂停后按物理时间步进的控制实验，不是多机实时或连续区间安全保证。数据来源见[原始审计](../results/recurring_input_age_v2/audit_20261025.json)。

## 模式表的改动与限制

当前开发表为`context_mode_map_v7/mode_map.json`，1432个稀疏格子及9个直接校准回退单元。查询特征为：

\[
(h,\dot h,\psi),\qquad \psi=\mathrm{sign}(e\cdot n)(a_{ref}\cdot n).
\]

h是移动参考管道余量，不等同于实际门框距离；ψ来自已有参考和状态，不改DNN输入维数。增加ψ是因为此前同样(h,ḣ)在不同参考上下文的恢复结果不同。

来源包括5条完整正常轨迹、30个通过直接校准的80ms协议、10个严格更新间隔合格的持续老化协议及8个失败否决点。失败等待优先否决，短等待成功不自动把更长的成功等待收紧为必要期限。未覆盖格子仍为未知。

参考上下文的范围由保存路线的多项式加速度分量极值构成保守包络，避免把离散采样最大值误当连续上界。它仅约束参考域，不是飞行动力学安全界。原校准的部分回退区域仍继承二维、与左右符号无关的经验假设，没有获得逐ψ认证。

**成功轨迹经过一个格子，不等于该格子的所有状态、保持控制、切换序列和允许延迟都已验证。** 当前表明确是开发用经验表，不是恢复不变集；不能将其输出当作形式化合格证书。

## 本阶段具体修复

1. v33将已返回命令的反馈处理移到未释放的后续采样之前，避免后续规划被普通新请求长期挡住。早期失败现场中，命令返回至处理约12–15ms。
2. v34将30ms输入年龄限制同时纳入预测与实际释放后的EDF期限；之前只在输出端检查，可能先接纳再因输入过老拒绝。
3. v35增加紧凑错峰候选。较疏错峰可能错过物理期限，全部同时释放又可能耗尽输入新鲜度；两者之间还存在有用候选。仍最多检查5个方案。
4. v36/v37对齐预测器与实际前端：不能在前端忙碌期间无代价发起采样；已经采回的承诺输入优先于反馈规划，反馈优先于新的未释放采样。此修改暴露旧预测器的乐观可行性，不能把v35正常通过当成最新版本通过。

原来某个现场在旧预测器下重放可行，修正前端次序后已不再足以证明可行。保留旧快照及负结果，没有修改现场报告为通过。

## 最新成本与为什么不继续盲目试飞

v37按既定规则重新冻结成本：每阶段`max(1ms, 1.25×开发p95+0.5ms)`，仍保留原完成/调度余量。中止后的清理等待不进入统计；开发失败记录保留，成本来源并不要求整轮通过。

新估计没有下降：输入约2.346ms、反馈约4.472ms、采样可见约8.262ms、命令返回可见约6.696ms、规划预留约3.716ms。使用新成本重放v36启动现场，有限规划仍找不到方案，因此没有重新启动相同已知不通过的扰动批次。新成本未获独立验证，也不是WCET。

另做只读计时分解：动态开发记录中，助手完成后的采样通知等待约40.2%、命令通知等待约37.0%、推理接纳通知等待约75.7%，与已记录的前端忙碌区间重叠。这些比例针对通知等待部分，不是整个响应时间。

这提示一个需要处理的成本记账问题：若把包含前端排队的整段可见延迟作为外部服务成本，再另外模拟同一前端工作，可能重复计入部分等待。与此同时也确实存在RPC、IPC及操作系统等待，不能把全部延迟删掉，不能直接改用助手完成时刻而忽略父进程可见性。**本阶段只做诊断，没有从冻结成本中减去这些重叠时间。**

## 下一阶段只做两件事

1. **修正成本分解并稳定完整流水线。** 在同一个串行前端资源中计入输入、反馈、规划及通知处理；把助手服务/传输与由前端忙碌造成的等待分开，避免遗漏或重复。以有限现场重放和同资源正常七机运行验证，成本在开发集冻结后再做独立复核；不放宽原期限。
2. **补实际闭环会访问到的恢复区域。** 先针对约0.096s的未知现场，保留完整状态、参考阶段和正在施加的控制，做持续输入老化及最大更新间隔下的恢复检查。通过数据再扩表，失败则收缩运行域或修控制器，不能直接把邻近未知格子改成合格。暂不增加更多查表维度、RL或额外安全模块。

两者完成后，才复查静态短周期候选、重跑相同扰动配对。若出现真实静态碰撞而动态完整通过，再做预先固定的邻近状态复核与期限/模型消融。之后才有依据扩大到8/12机、超网和FPGA。

目前结论是“状态相关预算方向有证据，完整多机框架的收益尚未证明”，不是“idea已经失败”，也不是“已经证明超越FALCON”。
