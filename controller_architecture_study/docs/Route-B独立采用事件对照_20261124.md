# 飞控用上命令后，单独发一张签收单

上一轮把采用时刻附在 RPC 回话里，只覆盖约两成命令。很多时候回话发得早，飞机还没用上那条命令。独立采用事件允许飞控更新模拟电机后，再报告对应的命令序号。[上一轮的开关对照](Route-B采用凭据与改期预算开关_20261124.md)

## 谁在等，谁继续做事

1. 飞控第一次用上带序号的命令时，只写入一个定长事件队列。每条事件带命令序号及首次固件更新的开始、结束时刻。重复更新同一条命令不重复发布。
2. PS 开一个独立的线程和 TCP 连接收事件。仿真器在空队列时以 4 ms 为超时等待新事件，一次最多取 64 条。实际唤醒时间受操作系统和 RPC 排队影响。它与 `ping()` 使用不同连接，共用物理网线和独立仿真端口 41591，仿真器负载仍可能同时影响两条链路。
3. 每架飞机仍按原方式保护期限。在下一次实际进入采样、提交新 DPU 请求之前，工作线程只查一次上一条命令的事件，使用原命令序号与版本配对。这个查找不发 RPC、不等待事件。记录缺失、时钟区间不一致、或无法确定改期条件时，继续用原 `ping()` 算预算及触发。

两组都开相同的事件接收线程，都在下一次工作开始前读证据。**只记录组**依然用 `ping()`，**用于调度组**允许匹配且结论确定的采用事件更新本机成本及改期触发。旧命令保持、版本提交、硬期限和命令发送逻辑沿用同一套实现。若一个事件来不及赶上这次决策，日志会保留稍后收到的记录；它不会回头修改已经执行的调度决定。

## 可核对的范围

使用原十机路线、真板 ID 11、20 ms 初始周期和独立离屏 Blocks。两组的冻结配置只差 `use_adoption_event`，都用同样间隔的三次短时限核。每轮以自然出现的慢事件为准，两组个别延迟可能不同。结果主要比较同一条命令的两种时刻和决策证据，飞行改善需要匹配负载与多次重复。

[生成板端程序](../airsim_command_timing/prepare_event_pair.py)、[事件版本的回归](../airsim_command_timing/adoption_event_test.cpp)、[短时加压入口](../airsim_command_timing/run_ps_trace_pulses.ps1)和[结果复算](../airsim_command_timing/summarize_event_pair.py)都在本工程。测试覆盖重放、乱序编号、缺失或不匹配的凭据，以及先收到 `ping()`、后来才确定飞控真的晚用的情况。

原始产物放在 `controller_architecture_study/results/ps_event_pair_20261124_001/`。`trace_live_events.json` 是 PS 实时收到的事件，`requests.jsonl` 的 `prior_adoption_decision` 说明下一轮实际用到了哪个凭据以及选了哪种预算。

## 用于调度组的实测

两条连接都正常运行。3,052 条发出的命令里，PS 最后收到了 **3,045** 条采用事件，其中 **511** 条在 `ping()` 返回前就到。3,050 条进入下一次采样前的成本决策，**3,037 条**当时已有能裁定改期触发的采用证据，覆盖 **99.57%**。13 条没拿到匹配凭据，继续使用原规则。上轮用同一次回话携带证据的开组覆盖为 19.9%，本轮允许等到下次实际工作开始，两者的统计时点不同。

按试验前后校时和 200 ppm 假设估算，飞控更新完到 PS 收到独立事件的延迟上界，样本 P99 为 **4.11 ms**，最大观测上界为 **29.20 ms**。这是含校时误差、传输和两端处理的估计，还没有单独测接收线程的 CPU 开销。

| 事件 | 按 `ping()` 算出的原预留 | 按采用凭据实际使用的预留 | 该条命令带来的变化 |
| --- | ---: | ---: | --- |
| Drone1 第 174 周期 | 45.379 ms | 19.958 ms | 采用超过了任务截止，但实际采用延迟未达到改期要求的 20 ms，初次触发撤销 |
| Drone7 第 177 周期 | 22.354 ms | 6.960 ms | 采用在截止内，初次触发撤销，第 179 周期恢复交付 |
| Drone5 第 175 周期 | 18.979 ms | 26.278 ms | 飞控真的晚用，补上初次触发，后续改期尝试未安装 |
| Drone7 第 773 周期 | 18.180 ms | 31.992 ms | 飞控真的晚用，补上初次触发，后续改期尝试未安装 |

所谓初次触发，只是说明新命令的采用同时越过任务截止和响应时长门槛。改期还要有同一控制版本的后续任务被拒，以及下一次发布和旧命令保持期限之间确实还有可行窗口。该轮真实改期尝试 **26** 次，安装 **3** 次，程序跑满约 32 秒，**8 架**到期退出。独立采用事件提升了可观察性，还无法据此声称改善整队飞行。

## 与只记录组对照

| 组别 | 下发命令 | 最终收到采用事件 | 下一次采样前能裁定／实际决策 | 改期尝试／安装 | 到期退出 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 只记录，仍按 `ping()` | 4,198 | 4,197 | 4,182／4,194（99.71%） | 20／6 | 7 |
| 采用记录用于调度 | 3,052 | 3,045 | 3,037／3,050（99.57%） | 26／3 | 8 |

两轮程序都运行约 32 秒，事件接收均无错误。离线核对，两组最终收到的事件数分别与事后找到的固件更新数一致。只记录组确认了证据覆盖提升，使用组也确实在同一批命令上改正了两类判断。单次对照中，采用事件组的退出更多，且两轮叠加的延迟不同。现有数据无法证明改变计时信号能提高飞行完成率。

下一步应追踪两条真正晚用命令触发后为什么没有可安装的方案。优先把「剩余保持时间不够」「任务已经发布」「预算被局部或共享估计抬高」分开。分离计时解决了系统判断错的问题，之后的改期仍需回应实际的瓶颈。
