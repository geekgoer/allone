## 已经落到代码的规则

入口为 `obligation_scheduler.plan()`。调用方提供同一时钟下的任务、三种绝对期限、采样后输入处理可开始的时刻、前／后处理成本、模型资格集合、可编辑的释放选项及跳过资格。`prep_ready` 是输入前处理可开始的预算，DPU 的实际就绪仍由共享 PS 仿真推进。倒推只用乐观就绪估计提出候选，批准时始终执行整个 PS／PL 事件仿真。

首版为了完成可重复的实现，规定以下有限顺序。它是明确的启发式选择，实验可以证伪其收益。

1. 以绝对生效期限 EDF 作为初始设备顺序，全组检查当前模型。
2. 当前方案失败时，检查各任务允许集合中最快的模型。成功后保留这条尾顺序作为本次已验证的设备承诺。
3. C 类才尝试至多两个替代队首。后面的设备次序保持确定，等待相应输入就绪。它可以保护仍在 PS 阶段的任务。
4. 仍失败时，尝试调用方预先给定的合法单槽释放选项。已经发布的任务和强制补更不可通过这个入口改期。修改会重新计算采样到前处理的偏移，旧控制保持期限和输入有效期继续约束结果。该首版只改一个待发布槽，之后的周期性日历由调用方提供。
5. 仍失败时，考虑一次计划跳过。资格必须显式存在且在提交时未过期，目标未发布，后继是该回路紧邻的下一槽，该回路未欠补更。候选按最快合格模型仍占用的服务时间从大到小排列，修改后把后继标为强制补更并收紧它的保持期限。全组检查包含它及其他回路的任务。最多批准一个跳过。
6. 原计划或修复计划通过后，在剩余预算里，对下一条派发任务做至多一次质量升级。按完整尾序列倒推它能占用的时间，在可容纳档位里挑训练内评分最好的，再用完整 PS／PL 仿真批准。若失败，保留此前已经通过的方案。

每次最多 **8 次完整检查、12 个进入检查的候选**。当前两种计数基本同步，模型表扫描和窗口诊断另外计费。默认初始任务为 EDF 顺序。这个版本没有实现任意排列搜索，质量升级也只看下一条派发任务。

`Calendar` 为不可变的离线状态机。计划带快照 revision 与提交截止时刻。`commit()` 拒绝旧版本、超时提交或修改已发布槽。`tighten_hold()` 接收外部分析器提供的新保持期限，收紧相应任务并推进版本，使旧方案失效。跳过后记录 `(vehicle, successor)`，有效补更经 `delivered()` 到达后才清除。错误或过期交付无法消除补更。真实程序仍需把这一状态替换操作放进现有日历锁，并为输入、真实命令 ACK 和任务完成事件提供适配。

已有 `bottleneck_joint.simulate()` 增加了可选的显式 DPU 顺序。PS 仍按端到端期限排非抢占原子处理段，DPU 只执行指定顺序并在输入未就绪时等待。原调用方继续用原接口。新调度器以完整任务的前处理、板内服务、下发处理和传输阶段复用它，还检查同一回路前一任务是否在下一次释放前结束。用 `blocked_until` 保留当前不可抢占服务的占用；调用方还需负责登记活动命令的剩余交付义务。

## 本次离线结果

任务使用真实 18 档新板端服务成本和 TRAIN512 评分。4／8 机、40 种种子、耗时×1／×1.5，每个决策预留共 160 场景。总共 480 个场景，每场景运行五种策略，合计 2400 个决策。合格模型集合由合成的误差门槛给定，保持界、输入有效期和相位资格是显式合成输入。输入状态没有 UAV 动力学演化。

| 策略 | 0.5 ms 决策预留 | 3 ms 预留 | 8 ms 预留 |
| --- | ---: | ---: | ---: |
| 固定模型，固定 EDF 尾顺序 | 18/160 | 18/160 | 1/160 |
| 同顺序＋可换合格模型 | 156/160 | 154/160 | 25/160 |
| 再允许替代队首 | 156/160 | 154/160 | 25/160 |
| 再允许单槽改期 | 156/160 | 154/160 | 25/160 |
| 再允许计划跳过＋补更 | 156/160 | 154/160 | 25/160 |

新模型池中，便宜的合格档已足以解决这批构造出的多数计算冲突。额外的重排、改期和补更没有提高通过数，也没有实际发生计划跳过。定向的真实成本算例证明代码会在可保持阶段撤回一个长模型任务并按期补更，在保护相位或补更期限太紧时拒绝。它是机制例子，频率和飞行收益由后续实验决定。

3 ms 预留组的完整策略 Windows 决策 P99 约 1.7 ms、最大约 2.0 ms，以本轮日志为准。0.5 ms 的名义成本小于观测到的部分算法耗时，作为机制敏感度对照。0.5／3／8 ms 三组在本轮均使用同一份任务资格和模型可选性，只有占用 PS 的决策时间及到提交时刻已经不可编辑的释放受限。它与旧 326→29 实验的任务构造不同。有限窗口通过只说明在给定输入下所有保留义务的预计交付满足时序。
