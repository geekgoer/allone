# C++ 接入后仍撞门：原因定位

## 结论

当前证据指向运行时实现的两个具体问题：**上一任务完成后的收尾处理卡住了同一飞机的下一任务入口；旧超期任务又让新配置准入长期回退。** 不能简单归因为 DNN 算得慢，也不能把这批结果当成 framework 已充分执行、但思想无效。

同模型、同路线、匹配局部初态的三个低延迟单回路对照，在 **30ms 周期** 下都零碰撞通过全部 8 个门。这支持运行时问题是重要原因，但不等于已逐一证明所有碰撞或所有临撞状态都能救回。

## “发布”与“派发”到底是什么

- 发布：周期到达，系统创建“这架飞机应该再更新一次控制”的任务，记录其到达时间、模型和期限，加入等待队列。
- 派发：系统允许这个任务真正进入采样、输入构造、推理、下发命令的流水线。

例如 0ms、30ms、60ms 都可以创建任务，即使上一任务尚未完成。周期独立不意味着每个任务都能立即执行，更不意味着每 30ms 必然有新控制生效。

当前程序是**到派发时才获取或选择新状态**。因此，任务排队 2s 不代表飞机必然 2s 没有新命令，也不代表该次 DNN 输入已经老了 2s。任务响应时间、数据年龄和实际命令间隔必须分别记录。

## 为什么能积压到秒级

### 1. 发布持续进行，过时任务没有合并或丢弃

初始十机每机 30ms 一次，约每秒创建 333 个任务。新日历不会因上一命令返回慢而隐含减少到达数；当前原型仍保留并逐个处理全部等待任务。

首次碰撞前的共同时间窗已经存在积压：

| 对照窗口 | Python 已发布/已交付 | C++ 已发布/已交付 |
|---|---:|---:|
| seed4，截止 7.177s | 2470 / 1717 | 2396 / 1806 |
| seed5，截止 9.583s | 3328 / 2196 | 3337 / 2147 |

这不是碰撞后退机导致的统计假象。但“处理速度落后”仍不是最具体的原因，下面的入口阻塞会人为放大它。

### 2. 已经收到命令完成，程序仍把这架飞机标成“忙”

代码关系：

1. `ReleaseQueue.dispatchable()` 要求该飞机不在 `pending` 中，才能开始下一任务。
2. `pending` 不是在命令返回或其后状态回传时立即移除，而是在前端执行 `completed` 分支、处理收尾时移除。
3. 前端保护逻辑优先处理未完成工作；收尾/下一配置规划会被其它采样、输入、释放工作挤后。
4. 已经创建下一计划的任务，其维护优先级还依赖不断向前推进的下一计划释放时间。积压任务的旧 deadline 往往更早，收尾可能长期得不到处理。

所以出现了：**这架飞机的 IO 和 DNN 都已经结束，但下一任务仍进不来。** 这是前端管理和优先级处理的问题，不能用增加 FPGA DNN 计算核心直接解决。

真实例子：seed5 C++，`Drone2:50`：

- 上一命令在飞行约 2.040s 时返回；
- 约 5.17ms 后，后续状态已回到前端；
- 下一计划约 5.09ms 后也已算完；
- 但收尾直到命令返回约 **4860ms** 后才执行；
- 同一飞机的下一次命令因此长期无法进入，出现约 4.88s 的真实命令空窗。

这里的秒级等待不是几秒钟的 DNN 运算。审计排除了“飞机已经碰撞退出后，最后一个任务的延后清理”记录；上例发生在该飞机仍活动、尚未碰撞时。

### 3. 动态改配置几乎全部被挡住

| C++ 组 | 成功采用新配置 | `infeasible_retained` 回退 |
|---|---:|---:|
| seed4 | 1 | 3617 |
| seed5 | 0 | 3253 |

seed5 有 964 次“建议 20ms、最后保留 30ms”，还有 2274 次“建议 60ms、最后保留 30ms”。seed4 也大量出现这两类回退。

准入代码发现任何未完成义务已经超期，就返回“无法修复过去期限”，继续保留旧配置。在严格拒绝不可行工作时，这个判断有其意义；但当前实际运行选择了**观察模式继续飞、继续保留并执行旧任务**，又没有配套的过载恢复分支。

结果形成反馈：旧任务超期 → 新周期/模型建议被拒 → 保留旧流量/配置 → 旧任务继续积压。轻松回路未能及时放宽到 60ms，危险回路也未能采用建议的 20ms。

初始化的 `initial_taskset_forecast_passed=True` 只验证有限的下一批任务。`simulate_pipeline()` 明确不认证更远的周期性到达，不能据此证明十机长期每 30ms 一次一定可调度。

## 原来的 17.34ms / 46.70ms 还存在吗

两轮有效 C++ 十机试飞中，控制路径实际 RPC 采样共 4055 次：

| 相近阶段 | seed4 C++ p99 / 最大 | seed5 C++ p99 / 最大 |
|---|---:|---:|
| 提交到 C++ IO 工作线程开始 | 2.739 / 6.022ms | 3.994 / 24.948ms |
| 读取状态、碰撞信息及解码 | 1.173 / 3.288ms | 2.075 / 6.554ms |
| 读取结束到前端取回 | 2.839 / 7.159ms | 3.866 / 9.294ms |

准确解释：

- C++ 控制 IO 已没有原来的 Python 辅助进程，原来的“跨进程等接收”环节已经移除。
- **等 IO 线程开始仍存在偶发长尾**：seed5 有 6 次超过 10ms，最大 24.95ms。它们集中在约 6.89s，不能宣称尾延迟已经消失；当前日志不足以唯一确定是 Windows 唤醒/核竞争、缺页或其它暂停。
- **46.70ms 的状态/碰撞读取长尾在这两轮 C++ 控制路径中没有再观察到**，最大为 6.55ms。这是观测结果，不是未来最坏时间保证。
- 仍使用 Python 的独立观测服务，这两轮状态/碰撞读取最大分别为 7.37ms 和 10.16ms，也没有记录到 46.70ms。

## 碰撞前真正的控制空窗

例如 seed4 C++ 一号机，在碰撞前最后一秒内有一次 93.697ms 的命令间隔：

| 相对上一命令返回 | 系统进度 |
|---|---:|
| 后续状态回到前端 | 0.556ms |
| 终于开始处理下一计划 | 86.042ms |
| 收尾结束，允许下一任务进入 | 87.398ms |
| 下一任务派发 | 87.863ms |
| 下一命令返回 | 93.697ms |

下一条命令的 DNN 计算只有 **0.158ms**。本次不是 DNN 在 FPGA 类后端被反复抢占了 90ms，而是前端入口直到约 88ms 后才放行。

其它 C++ 碰撞机在最后一秒内的较大命令间隔包括：seed4 二号机 54.40ms；seed5 九号机 234.14ms、一号机 92.43ms、三号机 159.19ms、二号机 97.01ms。不能仅由一个最大值推导某条轨迹的通用碰撞阈值。

## 用同模型低延迟飞行检查模型能力

有效结果：`results/native_collision_cause_20261029_v2/isolated_summary.json`。

| 原失败路线 | 同一 DNN | 周期 | 平均采样到命令返回 | 实际最大命令间隔 | 物理结果 |
|---|---|---:|---:|---:|---|
| seed4 一号机 | 2×128 | 30ms | 2.374ms | 56.629ms | 8/8 门、零碰撞 |
| seed4 二号机 | 9×1024 | 30ms | 3.943ms | 50.980ms | 8/8 门、零碰撞 |
| seed5 九号机 | 2×128 | 30ms | 2.377ms | 47.160ms | 8/8 门、零碰撞 |

三个对照都没有训练/更换模型，没有用 MPC 接管，也没有改到 20ms 才成功。局部参考轨迹与初态在启动物理前核对；单机使用原十机回路的局部坐标轨迹，移除其它共享负载。它是能力诊断，不是多机容量证明，也不是临撞状态可恢复性证明。

v1 单机预备记录因编队平移没有保持相同局部初态而被排除；还修正了诊断辅助函数的终点覆盖，让轻微墙钟/仿真时钟偏差不会把全门通过错误算成“窗口未覆盖”。有效 v2 三组均有相同局部初态记录和完整物理检查。

## 应优先修什么

1. **解除入口与低优先级收尾的绑定**：命令 IO 完成并被确认后，及时释放对应流水线占位；日志/统计/下一配置维护不能无限阻塞下一次控制。仍须保持命令顺序，不是任意重叠发送。
2. **明确过时任务语义**：记录已经发生的超期；对尚未开始、被新请求替代的任务设计有限队列/合并或丢弃规则。不能悄悄删任务后报告“零超期”。
3. **让过载后允许有意义的恢复决策**：继续检验其它回路的未来义务，但不能只因一个无法挽回的历史超期就永远冻结所有后续 T/c 修改。不可行状态仍要如实报告，不能靠重置 B/deadline 得到伪保证。

这次只做原因定位和单回路对照，没有放松 B、修改核心调度策略或自动丢弃任务。优先修运行时的这些具体问题，再判断还剩多少模型/B 定义问题。
