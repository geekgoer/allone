## 4. 89条跳更为什么没有安装

### 4.1 原拒绝理由是对的，但需要进一步解释

89条均为“快照内求解可行、包含skip”，但提交结果均为 `context_changed`。这里可行是提供的成本、保持资格及固定窗口内可行，不是任意真实状态安全。

独立核对得到：

| 项目 | 数量/统计 |
| --- | --- |
| 含skip的可行候选 | 89 |
| 超过其 `commit_by` 的候选 | 0 |
| 目标被跳槽的release已经过去 | 0 |
| 提交时距目标release仍有多久 | 约2.746～10.063 ms |
| 搜索期间有实际发布记录 | 89/89 |
| 搜索期间有实际命令开始/返回记录 | 89/89 |
| 墙钟耗时均值/P99/最大 | 11.124/13.023/13.213 ms |
| 线程CPU耗时均值/P99/最大 | 9.713/10.215/10.243 ms |

这些不是89个“算法算完已过目标release”的案例。它们是**算法算完时目标还可修改，但算法依赖的全局任务状态已经变了**。

源码中 `observe()`、`release_due()`、`queued()`、`take()`、`dpu_done()`、`command_begin()`、`command_return()`、`finish()`等都会推进同一个日历revision。`install_unlocked()`首先要求revision与快照完全相同；任何相关生命周期推进都能拒绝整份计划。

原始日志没有完整逐次revision变更轨迹，所以不能唯一认定每条记录究竟被哪一次变化拒绝。但所有89条都有真实生命周期变化的直接时间见证，且源码的全局CAS条件明确。不能把这89条简单解释为“安全条件太苛刻”或“确实没有可行解”。

### 4.2 一个实际快照例子

取 `pressure30_skip_on_003` 第134条规划日志，以该快照为0：

```text
0 ms          读取快照，准备跳过Drone2:70
约3.119 ms    Drone1:70计划release，其后实际推进采样/设备/命令
约9.4 ms      规划完成；全局revision已变化，提交拒绝
约18.119 ms   Drone2:70原计划release，目标尚余约8.727 ms
```

本次墙钟9.396 ms、线程CPU约9.394 ms。目标没有过期，规划也没有超过15.432 ms提交预算，但是其他任务已经正常往前执行。新计划是否仍可用，必须按新占用、状态和控制版本再验证，不能忽略revision直接接受。

### 4.3 T20没有候选是另一种原因

T20启用组有717次eligible权限，但目标剩余提前量最大约14.286 ms，小于配置的15.432 ms规划预留。它们在进入skip检查前被排除。这一组属于**提交窗口不够**；T30的89条则属于**搜索期间上下文变化**。两种原因不要混为一谈。

15.432 ms来自早期实测规划最大值约12.345 ms乘1.25的经验设置，不是经过证明的最坏响应上界；更不能为了让skip触发而随意缩小它。

最长记录来自 `dual_adaptive_102` 第1110条规划：

| 量 | 观测 |
| --- | ---: |
| 墙钟 | 24.987 ms |
| 线程CPU时间 | 22.218 ms |
| 完整候选检查数 | 1 |

这条记录说明：即使只检查一次原计划，规划线程仍可能实际使用较多CPU。它不支持“都是网络阻塞”“全由Linux抢占导致”或“只是候选太多”的解释。

目前只有粗粒度线程CPU和墙钟，尚不能把22.218 ms精确分到JSON构造/分配、诊断、前推、复制或快照处理。小部分CPU/墙钟比略大于1也与计时区间和精度不同有关，不应当作超物理执行。下一步必须加阶段计时/采样剖析，而不是凭直觉重写整个系统。

## 6. 这对新版Framework意味着什么

迁移的是原保留优先的义务日历实现。与 [新版研究规格](../../../controller_architecture_study/docs/义务保护预算分配Framework_20261116.md) 的关系是：

| 机制 | PS迁移后状态 |
| --- | --- |
| 定时发布、采样、237D、保持分析、真实DPU、下发 | 已移到PS并实测 |
| 原有限日历、倒推预算、8次检查/12候选 | C++移植及接线完成；本地复现通过 |
| 原子提交、控制版本及command_pending保护 | 已实现并经历真实拒绝路径 |
| 未来模型/周期安装接口 | 已接线；本批实际均未改变 |
| 跳过未发布槽、原下一槽补更 | 生命周期检查有；尚无真实已跳过和实际补更 |
| 原计划可行时基于统一闭环收益主动跳更 | 新研究设计，未因迁移自动实现 |
| 增量预算、细分版本、更新后再验证候选 | 仍待设计实现和测试 |
| DPU分段/恢复、超网前缀共享 | 仍未实现 |

`finish()`已经把补更清偿限制为恢复期限和有效actuation期限的较小值；`command_begin()`会使旧保持观测失效。相较旧Python适配器，PS版本对生命周期守卫有补充。派发处仍有只按本机预算临时换模的分支、未来后继保持仍有条件假设，不能据此宣称新版完整规格已全部落地。

## 7. 下一步应该怎样做

优先解决**规划计算与可提交窗口不匹配**，而不是增加相同压力重复。

1. 给规划拆阶段计时：快照/复制、诊断、候选生成、每次完整检查、提交；同时记录CPU和墙钟，定位“1次检查也22 msCPU”的原因。对真实89份输入做板端离线剖析，无需先飞行。
2. 减少不必要规划：未改变配置的 `keep_current` 不必反复当大计划提交；沿用有效承诺，只在失效或明确机会时启动有界修改。不得因此停止新状态保持检查。
3. 把候选表示成针对未来槽的小变更。提交时若日历已推进，先按最新真实在途工作、成本、控制版本和期限重建受影响窗口，再做有界全组验证；重验证失败或预算不足仍拒绝。**不能直接删除全局revision检查，也不能只核对被跳飞机就批准。**
4. 明确两类版本：计划/义务结构变化，以及观测/执行进度变化。区分版本只是帮助知道要复核什么；不会自动证明正常推进无害。第一版可保留原严格CAS作为回退路径。
5. 先在离线和生命周期反例中确认旧任务完成、其他UAV发布、旧控制变化、期限收紧、成本增大等情况下的重验证正确，再进行短双机闭环。随后才验收一次跳过及原下一槽真实补更。

目标不是让89条都安装。目标是：**当前仍可行的候选及时安装；已经失效的候选继续被拒绝；保留任务与补更不因放宽提交而受损。** 是否能获得明显调度/控制收益，还需要后续实验。
