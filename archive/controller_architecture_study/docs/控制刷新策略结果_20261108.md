# 命令后配对时机对照

代码保留默认立即配对；新增默认关闭的`--refresh-at-release`和`--refresh-when-slack`仅供诊断。后者依据历史最大refresh墙钟及decision余量决定是否执行立即回读，不是WCET或安全证书。下一定时采样会将新状态与当前held control配对，命令改变后旧observation仍立即失效。

55项相关测试通过，随后新增slack分支检查也通过（PilotTests共8项）。新增测试覆盖下周期配对与控制版本，以及缺少回读余量时不启动重复RPC。没有调低预测成本或放宽期限。

本批`results/refresh_policy_20261108_v1/`五次双机真实板端飞行均完成、无接触、机身检查通过；严格时序均失败：

| 方式/轮次 | 交付 | 其他状态 | 周期修改 |
|---|---:|---|---:|
| 全部下周期配对0 | 1001 | 命令迟返1、推理丢弃1、busy丢弃1 | 0 |
| 全部下周期配对1 | 1000 | 准备丢弃2、busy丢弃2 | 0 |
| 立即配对0 | 626 | 推理丢弃1、busy丢弃2、准备丢弃1 | 5 |
| 有余量才配对0 | 1003 | busy丢弃1 | 0 |
| 有余量才配对1 | 1002 | 释放过晚1、推理丢弃1 | 0 |

全部延后模式两轮分别有2390/2391次unpaired_state跳过；只有1/4条实际决策。有余量模式跳过1068/308次，仍有898/1524次无可行修复。少量交错试验、实际周期不同，不可仅用请求数或丢弃数比较效率。

结论：延后回读减少执行链重复读取，但在当前“全组都要有有效状态—控制配对才能规划”结构中，会让全局规划缺输入。slack回读未证明同时解决两者，不作为新默认。收尾长尾和缺观测是两个不同约束；“移到下周期”未解决在线反馈问题。

下一步需要独立且有明确预算的观测发布路径，使用独立RPC客户端及状态/held-control版本检查，避免监测依赖本机控制任务完成；必须防止旧状态和新控制混配，并单独测量附加RPC/CPU开销。并不要求迁移PS，但这已是有边界的并发架构改动，不能声称本轮已完成。保留默认立即配对，实验标志不启用。
