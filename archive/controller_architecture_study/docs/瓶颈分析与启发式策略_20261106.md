# 路线B：从“哪里慢”到“哪些调整来得及生效”

日期：2026-11-06，Asia/Shanghai。当前交付为历史日志诊断、可执行的启发式参考实现和确定性PS/PL时序实验。路线A运行代码及冻结包未改动；本轮没有新试飞、重训或上板。

用户草案原件保存在 [原始快照](../../../docs/reference/Bottleneck_Aware_Joint_Control_Framework_20261106.original.md)。SHA-256为 `a33813f8d536a8e2c18d620dad0b13afca7059e1cf2ec79d133fed3e46aa2fb1`。草案是讨论材料，不是把所有建议自动实现的指令。

## 1. 建议把研究问题收敛到哪里

多机共享加速器时，发现危险后，系统需要回答两个不同的问题。

1. **眼前这次控制还来不来得及？** 已经排队的任务、正在运行的不可抢占段和已经承诺的释放时刻都会限制当前动作。
2. **新配置持续运行是否承受得住？** 缩短周期会增加未来到达；小模型可能降低计算需求，却未必满足恢复要求。

建议研究“**危险窗口内的有效资源转移**”。直观地说，某架飞机不危险，并不意味着它可以立刻把算力让给危险飞机；必须查清它让出的资源什么时候才能用得上。

本轮实现称为“关键窗口需求修复”。它有显式规则和明确检查，但仍是启发式。当前不声称全局最优、不声称物理安全已经被证明，也不把“用了EDF、CBF或超网”当成创新。

## 3. 四个更有用的insight

### Insight A：只有在截止时间前能兑现的资源才有救援价值

若平稳飞机的下一份可推迟任务在40ms才到达，而危险飞机必须20ms前拿到控制，那么延后这份40ms任务，对本次20ms危机的贡献为零。它可以减轻后续负载，不能消除眼前旧任务。

同样，DNN已经在PL内执行一个不可抢占段时，改它下一次任务的模型不会缩短当前段。动作具有自己的**最早生效时刻**。该时刻晚于本次危险期限的动作，应从本次修复候选中排除。

### Insight B：有用的调整必须减少真正紧张的那种资源需求

把PS与PL分别建模。如果紧张的是PS输入构造、派发或下发服务，仅减小PL计算量不一定有用。如果更细分段增加了PS派发次数，还可能让问题恶化。

因此用向量需求 `E=(E_PS,E_PL)`，不能用一个总利用率替代全部资源。当前参考实现只有一个被隔离的PS服务资源和一个PL执行资源；Zynq的其他CPU核及网络被视为外部服务，必须为其延迟提供有依据的界。这不意味着Zynq只有一个CPU核。

### Insight C：缩短周期产生的收益和负担具有不同时间尺度

保持前一条已生效命令不变时，下一条命令到达时间的变化是

\[
\Delta a_{next}=\Delta r_{next}+\Delta R_{next}.
\]

提前释放10ms，如果引发的额外排队超过10ms，就没有改善到达时刻。反过来，若下一次释放已经承诺且不能移动，本次修改周期的直接 `Delta r_next` 就是零，效果只能体现在后续任务。

代码必须分别保存“下一次释放时刻”和“后续重复周期”，不能把二者混成一个紧迫度。也不能用当前任务剩余倒计时直接推断以后要一直加频。

### Insight D：分段带来阻塞收益，也带来PS与上下文成本

设总PL计算为C，拆成m段，单次派发成本为s，跨任务切换成本为w。拆段可能把不可抢占阻塞从C降到最大段长q，却至少带来约 `m*s` 的PS服务需求，另有实际发生的切换成本。

因此 `q` 不是越小越好。当前DPU若只支持整任务执行，合法抢占点就是任务边界；自定义PL确认支持段暂停/恢复后，才允许额外边界。本轮对这两种能力分别实验，不以CPU随时抢占代替FPGA能力。

## 4. 时间定义先固定

仍使用绝对安全期限

\[
d_i^{safe}=a_i+B_i,
\qquad r_{i,next}+R_{i,next}\le d_i^{safe}.
\]

加上用户要求的周期期限，当前任务必须满足

\[
d_{i,next}=\min(d_i^{safe},\ r_{i,next}+T_i).
\]

`B`来自与保持控制版本配对的状态。过期状态不能从当前时刻重新起算。严谨意义下，返回的B应不大于真实可安全保持时间，才能作为允许等待的保守上限；仅找到一个比真实安全时间更大的数不能保证安全。

对未来多次任务，**当前一次B不能自动复制给所有将来状态**。本轮合成实验额外假设：在预测区间内，有外部给定、始终成立的保持时间下界H，并且所选模式对该时序合格。于是给未来任务一个保守相对期限

\[
D_i=\min(T_i,H_i-T_i).
\]

若每份任务均满足该D、没有丢失命令，便同时满足 `R<=T` 和相邻控制间隔不超过H的充分条件。对于一个给定响应界R，该简化契约允许的周期区间是

\[
R\le T\le H-R.
\]

当 `H<2R` 时，这个保守契约无解；它不等于任意控制实现都不可能安全，因为精确生效间隔还含前一次R。本轮真实日志审计没有擅自把单点B变成H。接入真实系统前，需要短窗口可达性/控制资格支持H，或者只验证下一条有效命令并在新观测后重算。

## 5. 核心公式与启发式

### 5.1 定位一个无法靠排序消除的缺口

对资源q和区间 `I=[s,d]`，定义

\[
E_q(I;z)=\sum_{j:\ r_j\ge s,\ d_j\le d} C_{j,q}(z),
\qquad F_q(I;z)=E_q(I;z)-S_q(I).
\]

z代表整组周期、模式和合法调度选择；`S_q`是该区间实际可提供的服务，扣掉不能移动的已占用段/管理服务。只把整份剩余路径都必须放在这个窗口内的任务计入需求；跨越窗口的任务不能随意全部计入。

当F>0，这个资源窗口装不下相应需求。排序不能让1ms资源产生2ms服务。两个资源分别通过也未必整体可行，因为还有PS→PL→PS先后依赖、段阻塞、通信和截止时间。

同时检查单任务的无竞争最早完成时间。若该时间仍晚于期限，单改优先级没有作用；必须在尚可行动时改变释放或合格计算需求。若连当前时刻立即启动的合法最快路径都赶不上，就不能靠把过去的释放时刻写早来“修复”。

### 5.2 用窗口内的真实需求减少量选动作

在最紧张的资源窗口 `(q*,I*)`，对合法动作a计算

\[
G(a\mid q^*,I^*)=E_{q^*}(I^*;z)-E_{q^*}(I^*;z\oplus a).
\]

第一选择规则是

\[
a^*\in\arg\max_{a\in\mathcal A_{local}}G(a\mid q^*,I^*).
\]

需求减少量相同时，依次偏好更少模型变更、更小的相对周期变化、更少调度变更。不引入训练评分器或任意加权的“安全总分”。模型资格必须由外部已有证据给出；缺证据的模型不会因为计算快就入选。

候选只改变一个回路的合法 `(T,c)` 或一次全组合法调度设置。一个回路内部可以联合改T与c，多个回路通过最多8步逐次协调。每步都根据新的缺口重新诊断，不采用固定“先T、再c、最后优先级”的顺序。

如果没有正需求缺口，但完整流水线仍失败，则查看失败任务的无竞争路径、PS/PL等待和段阻塞。v5沿等待链统计每个其他任务在目标等待区间内实际占用了多少PS/PL服务，按候选减少的相应服务比例估计可释放的时间，再尝试释放/模式调整或合法分段变更。这样可以发现“总需求装得下，但特定任务挡住了目标”的情况。这一分支是预测启发式，改变任务次序后估计可能不成立，仍须全组复核，不具有上述需求缺口的必要性证明。

### 5.3 可以证明什么

**局部排除性质。** 对同一资源和同一窗口，如果 `F>0` 而某动作 `G<=0`，该动作单独无法修复这个需求违例。证明直接来自修改后的缺口 `F'=F-G>=F>0`。

**当前缺口的单步最大减少。** 在给定有限合法单步动作集合内，上面的argmax使该窗口缺口的减少量最大。这是对一个窗口、一步动作的结论；不代表全局最优，也不保证后续贪心不会走入死路。

**旧工作不能凭空回收。** 若一个动作只改变窗口以后才出现的任务，则窗口内需求相同，G=0。当前实现把已承诺的carry-in保留，不通过删掉旧任务或重置期限获得可行。

**有界计算量。** 最多8次修改、最多5次完整流水线检查；每次只枚举局部动作，不枚举所有回路的笛卡尔积。逐回路贡献可缓存，避免每个局部动作都重建整个任务组。本轮已经用这项优化减少Python对象构造。

这些结论以明确的时间/资格假设为前提。经典processor-demand思想早已存在，不能把上面的必要条件本身写成原创定理。可能的研究贡献是将**动作生效时间、物理控制期限、PS/PL不同资源需求以及合法段边界**连接成低开销的联合修复机制，且给出相对于完整搜索的缺失率和真实系统收益。

### 5.4 不能证明什么

- 使用执行需求的真实下界发现F>0，才能证明相应物理资源条件下不可能。用测得的P99或上包络算出F>0，通常只能说这个包络无法通过，不能断言实际一定无解。
- 有限确定性流水线仿真通过，不是所有执行时间变化、所有未来到达或无限运行时间的可调度性证明。多资源先后依赖、阻塞和执行时间变化可能产生调度异常；不能直接把“各项都取上界的一次仿真”叫严格响应时间分析。
- 没有找到候选，可能是贪心、候选域或检查预算不足。不能声称整个框架不可能安全。
- 模型合格性在合成实验中是输入假设。当前真实数据尚未建立可靠的状态—模型资格差异，因此不能把合成结果解释为已找到最优DNN选择器。
- 本轮目标是有限时序可行和少改配置，没有计算真实飞行J，不声称J最优。

## 6. 实现位置和PS/PL边界

核心实现为 [bottleneck_joint.py](../../../controller_architecture_study/bottleneck_joint.py)，实验入口为 [bottleneck_experiment.py](../bottleneck_experiment.py)。不导入AirSim或PyTorch，不改变路线A。

模拟顺序是

```text
绝对周期释放
  → PS输入服务 → 输入传输延迟
  → PS派发 → PL不可抢占段 → [下一段PS派发 / PL段]
  → PS输出服务 → 下发/作动延迟
```

PS与PL可以并行。每个PS服务块和PL段内部都不被任意抢占；工作次序按FIFO或EDF比较。多个回路共享同一PL资源。已有不可移动PL服务通过初始占用表示，尚未开始的旧任务通过carry-in队列表示。这个参考模型还没有完整适配真实运行中每一种“半完成PS/PL链”的上下文，接入前必须完成映射。

共享内存/网络竞争目前由输入的延迟包络和切换成本表示，没有建立真实DDR仲裁器。最终包络需要上板验证。如果无法给出包络，才有必要显式增加相应资源；本轮不增加DDR、功耗、RL或动态核分区等额外模块。

测试见 [test_bottleneck_joint.py](../../../tests/test_bottleneck_joint.py)，覆盖段内禁止抢占、PS/PL并发、R超过T、旧任务保留、承诺释放不移动、未合格模型排除、全组时序检查和需求剪枝必要性。测试中的“缩短周期后变差”是资源干扰反例，不是宣称孤立理想控制器随采样频率必然变差。

## 7. 实验协议和证据边界

所有结果位于 `results/bottleneck_insight_20261106_v1/`。`synthetic_v1`、`synthetic_validation_v2`和`full_grid_*_v3`保留为开发记录。v1默认FIFO，v2扩展到四回路oracle，v3扩展为三个周期×两个模型。最终v4修正硬件能力公平性：支持分段的执行器也可以选择整任务运行；两种执行器都从EDF整任务基线开始。没有删除前期失败。

`confirm_segmented_v4` 与 `confirm_whole_v4` 使用新种子40000–40019。v4暴露出没有正需求缺口时漏算其他任务阻塞贡献的问题。修正后的最终 `causal_segmented_v5` 与 `causal_whole_v5` 使用独立新种子50000–50019，各覆盖四类服务成本条件和4/6/12回路，共480个成对参数案例。四类分别是均衡、PS压力、PL压力、切换压力。这里的成本都是注明的合成假设，未从WindowsCPU推算FPGA速度。

每回路3个周期×2个模型；模型资格按生成时固定的假设给出，不随算法结果修改。四回路完整枚举所有允许组合及调度选项，得到这个**离散空间**的可行性和少改配置参考。6/12回路不穷举，因此对应summary中的`oracle_feasible=0`表示未运行oracle，不能读成“已证无可行解”。

基线包括固定配置、只调T、只调c、只调调度、只看总PL需求减少的对照，以及联合启发式。没有把这些方法命名为原版FALCON，也没有重做FALCON离线全局J优化。

所有方法先按相同的0.5ms决策预留做确定性比较。随后把新规则实测Python耗时与0.5ms的较大值代入，再检查同一方案，分别保留两种结果。后者是事后时延敏感性检查，还不包含真实在线复核、状态获取和提交成本，不能宣称已闭合实时链。

**十二回路上联合方案尚不够好。** 同组只换模型原本通过22个，加入其各自实测耗时后仍通过15个，高于联合启发式的9个。整任务分支也有类似现象。更多自由度使这条贪心轨迹可能选错方向，更多计算还会消耗可用时间。当前不应将Python版直接接管十二回路，也不应只报告四回路的漂亮结果。

原始失败案例、选取动作、窗口证据、方法耗时和oracle配置全部保留在各目录的`cases.json`。参考实现和已测范围支持进一步研究，不支持“所有规模又快又好”的结论。四回路两种执行器最终可行数相同，也说明**目前没有证明必须分段或必须超网**。

v5运行时的源码已按哈希保存在`source_v5/`。交付检查额外补上“把下一次释放推到预测窗口外，也不能抹掉当前已有期限”的边界保护，并加入回归测试；v5生成的全部配置都不触及该边界。最终核验记录见`final_verification.json`，原始实验报告保持不变。

## 9. 下一阶段如何推进

1. 保持路线A冻结。用本轮案例作为确定性回归输入，把规则与检查移植为有固定数组/任务数上限的C++，完整计入输入准备、窗口检查、决策和提交。Python作为可读参考，不能靠平均时间小就直接宣称适合20ms在线决策。
2. **现在适合做板端时序测量。** 先用现有可运行的独立237D模型/DPU，测整任务PL时间、PS预处理/派发/下发、并发DDR和网络尾延迟。若板端尚无237D运行路径，先完成这一条最小链；不必为此先完成136配置超网加速器。
3. 自定义PL能暂停/恢复后，再测合法段长、切换和上下文成本，比较整任务、固定分段和按条件选择分段。没有接口时只启用整任务分支。
4. 从实际板端数据生成服务模型，重新运行同一案例和参数敏感性；不能简单把x86时间按频率缩放成ARM时间。固定界只用于其确有依据的运行条件。
5. 接入真实框架时，先实现完整未完成路径映射和一个新状态→一个当前控制版本→一个绝对期限的接口。模型资格不足时先固定c，只验证T与合法调度；不要让合成资格变成实飞资格。
6. 最后做多机异质路线配对，静态离线J选择与动态使用相同资源/模型池，报告碰撞、J、任务丢弃、截止时间、决策采用时间和总开销。没有通过瞬时需求和实施开销检查的建议不安装；丢任务本身不能当作安全恢复。

本轮建议先测板端时间，是因为Windows日志存在明显主机空隙、实际PL瓶颈仍未知。它不意味着换Linux后尾延迟就一定消失，也不意味着把较慢的Python规划搬到ARM会变快。
