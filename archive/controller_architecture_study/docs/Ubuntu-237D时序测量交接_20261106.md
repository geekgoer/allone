# 给 Ubuntu Agent 的任务：采集 237D 控制器的 Zynq 时序

用户已确认板上至少有一个可以运行的 237D 模型。用板子当前的 Linux、DPU 镜像、模型和可运行入口完成这轮测量。先记录原入口和实机版本，再在实验副本中加打点或使用独立测量入口。旧交接曾按 Vitis AI 1.2.1 / DNNDK 规划，实际运行时以板上现有安装为准。

这轮要拿到**无竞争路径、各资源服务和并发等待**三种不同数据，供 Windows 的 A/B/C 决策回放使用。先完成板内固定输入回放。实际控制器集成、硬件分段和闭环试飞是独立阶段。

## 1. 核对模型和测量边界

- 记录板型、实际镜像、内核、DPU 运行时和接口、可见 DPU 核数、CPU/DPU 频率和 CPU 亲和性配置，未知字段写 `null`。
- 记录实际模型 ID、模型二进制和归一化的 SHA-256、外部输入契约及张量类型。确认是本次 237D 控制器，核对四个输出的顺序、尺度和输入是否已归一化。板端张量如果带 padding，记录逻辑 237D 与物理布局的映射。
- 使用固定 237D 验证或已有板端黄金输入，保留输入身份及对应输出。先跑已知正确的参考例，按现有模型的验收口径核对输出；保留参考、误差及容差来源。若可取得的参考只有 FP32，单列 FP32 差值及量化容差的来源。
- 对每组注明输入起点。有原始状态和参考时，可测状态到 237D 构造；只有已经构造好的 237D 向量时，只从该向量开始计量，`feature_build` 标为未测。板内固定输入回放的终点是控制输出就绪，真实下发或执行器生效单独测。

## 2. 给单条请求打点

板内一律用同一个单调时钟，原始时间用整数纳秒。不同线程的事件用同一 `request_id` 关联。若另外测 Windows 到板端的往返，用 Windows 自己的时钟计算 RTT，板端仍独立给出内部时间。

| 字段 | 打点位置与用途 |
| --- | --- |
| `release_ns` | 本地开放式回放计划的释放时间，单请求实验可取实际开始时刻。 |
| `enqueue_ns` | 实际入板端软件队列，区分释放抖动和队列等待。 |
| `prep_start_ns`、`prep_end_ns` | 预处理起止，包括真实发生的复制、归一化、量化。若能分出 237D 构造，另记 `feature_start_ns`、`feature_end_ns`。 |
| `submit_ns`、`done_ns` | DPU 调用或提交起点、结果可读时刻。异步接口同时记提交返回时刻。`done_ns - submit_ns` 作为运行时墙钟。 |
| `hw_start_ns`、`hw_end_ns` 或 `hw_duration_ns` | 仅在现有 profiler 或计数器能逐请求关联时填写。计数器时钟无法对齐时只填写持续时间和换算依据。其他情况保留空值。 |
| `post_start_ns`、`output_ready_ns` | 输出反量化、转换及控制量就绪。若测了网络回复，追加 `reply_send_ns`。 |
| `status`、`error` | 成功、丢弃、超时或失败。给每个计划释放留一行记录，缺失阶段允许空值。 |

准备与后处理记录墙钟时间。如果能轻松取得对应线程的 CPU 时间，额外记录为 `prep_thread_cpu_ns`、`post_thread_cpu_ns`，帮助区分实际执行与被挂起的时间。热路径用缓冲记录，完成一轮后落盘。性能采样和开启 profiler 的采样分开标记。

几个常用派生值：

- 释放抖动是 `enqueue - release`，软件队列等待是 `prep_start - enqueue`。
- DPU API 墙钟是 `done - submit`，里面可能包括驱动、运行时排队和完成通知。只有可关联的硬件计时才单列为 PL 执行。API 墙钟和 PL 执行是包含关系，用于回放时不能相加。
- 板内响应是 `output_ready - release`，按相同请求 ID 计算。CPU 预处理、派发、加速器与输出端未归属的空隙也保留。固定 237D 输入测出来的响应范围起于向量就绪。

## 3. 先执行这几组

1. **单模型，单请求在途。** 复用常驻模型和执行对象，固定输入集，先预热至少 100 次。建议 3 轮，每轮至少 1000 个有效样本。冷启动单列。输出核对通过后，用这组数据估算 A 类的无竞争路径。
2. **同一模型，开放式并发回放。** 使用 1、6、12 路逻辑请求，首轮各路周期统一 50ms；采用错峰释放，再为 6 和 12 路补同相释放。每个条件建议 3 轮、每轮 30 秒。按绝对计划生成释放，记录实际排队策略、队列上限、并发上限、丢弃或超时，轮末保留未完成工作记录。若实际系统无法生成某组负载，记录限制与完成的条件。此组用于定位 B 类容量压力与 C 类执行等待。
3. **可选，板上确实已有第二个合格的 237D 模型。** 常驻两个模型，记录各自单路成本，比较交替调用 A→B 与连续调用 B→B。报告输入量化与模型分派成本，另记实际执行的模型。只有一个模型时，先交付前两组，换模型和段切换字段留空。

现有 DPU 能证实的执行边界用于填 `execution_boundary`。未测到任务内部可暂停与恢复时，回放按整任务运行。多请求可以提交并不表明可以抢占一个正在执行的 DNN。

## 4. 交回的文件

建议在新目录 `board_237d_timing_<date>_<run>/` 打包以下材料：

| 文件 | 内容 |
| --- | --- |
| `environment.json` | 第 1 节的设备、镜像、模型、输入边界、计时钟、实际执行边界、工具版本。 |
| `commands.md` | 编译、启动和复跑命令，参数及测试顺序。附上实际使用的打点代码或相对路径和提交版本。 |
| `requests.csv` 或 `requests.jsonl` | 每次计划释放一条，含上述时间戳、`run_id`、`condition`、`request_id`、`source_id`、`input_id`、`model_id`、实际执行模型、周期及状态。 |
| `summary.json` | 每个条件的计划、完成、失败、丢弃数。各阶段的样本数、P50、P95、P99 和观测最大值，单位注明为 ms 或 ns。每项注明测量边界。 |
| `output_check.json` | 输入与黄金参考的身份、输出误差和采用的验收口径。 |

若拿不到纯硬件计时，仍交完整 API 墙钟和 CPU / 队列事件。Windows 侧可以先做黑盒整任务敏感性分析，PS/PL 分解保留为未知。若暂时拿不到真实 237D 构造、网络下发或调度核的板端成本，这些阶段也单列为未测。实测分位数和最大观测值用于经验回放，严格上界需要另外验证。

对应 Windows 实现和结果见 [路线 B 决策说明](Route-B的ABC决策策略_20261106.md)。旧模型池交接中的归一化、黄金向量和现有板端接口可参考 [237D 模型池交接](../../../controller_architecture_study/docs/Ubuntu-237D-DPU模型池实验交接_20261016.md)。
