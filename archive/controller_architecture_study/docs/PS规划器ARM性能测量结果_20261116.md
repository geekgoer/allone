# ARM Planner Profiling and Report-Copy Optimization

2026-11-16。执行[PS规划器计划](PS规划器修复计划_20261116.md)的核心函数剖析及第一项优化。当前Agent直接从Windows经Ubuntu构建机访问Zynq完成；没有让其他Agent代跑。

## 1. 结论和范围

**确认了规划计算的一项实际瓶颈：调度模拟结果和报告对象被反复深拷贝。移除这些重复拷贝后，ARM离线规划均值由8.533 ms降到4.473 ms，减少约47.6%，完整决策保持一致。**

这验证的是PS上的规划核心函数，不包含实时快照锁、控制线程并发、install及日志服务。当前没有将优化替换进v5真实控制程序，也没有重新飞行。原记录24.987 ms长尾、89条context_changed和真实跳更补更尚不能因此标为已解决。

## 2. 实际怎么测

板端为AXU3EGB、AArch64/Linux5.4，CPU governor仍为userspace，频率1066666 kHz，boot_id与交付一致。使用现有Ubuntu SDK交叉编译，保持原O2、C++14和禁用浮点收缩口径。源码及程序均放新研究目录，没有更改原18模型、驱动或系统设置。

冻结91份真实规划输入：原T30三轮的89份skip快照，加最长keep和普通keep各一份。它们是已有实验捕获的任务、模式和期限；没有人为修改成本或拖慢DPU。

每份先预检，再重复10次；每种程序做两批，第二批反转程序执行顺序。每一批内按固定种子打乱快照顺序。每种程序1820条，四种共7280条ARM回放；先后两轮优化对照共14560条。

四种程序分别为：原始无探针、原始阶段计时、优化无探针、优化阶段计时。表内主要性能比较使用无探针版本；探针版本用于归因及估计计时开销。

输入解析、完整决策核对、结果序列化在核心计时区间外。每次核对整个决策对象，包括forecast、trace、动作、模式、顺序、补更和期限，浮点容差为绝对1e-10＋相对1e-12。没有只核对一个accepted标志。

本回放运行在板端CPU，**不调用DPU或AirSim**。不应把14560条规划回放写成14560条控制命令。

## 3. 原来CPU主要花在哪里

第二轮同输入集、原始计时版本的互斥阶段均值如下。嵌套调用暂停父阶段累计，避免将子时间重复相加；约4.91次完整检查/决策，主要由这批skip输入构成，不代表所有正常控制周期都要这么多次检查。

| 阶段 | 平均线程CPU(ms) | 对应系统在做什么 |
| --- | ---: | --- |
| 仿真报告 | 2.400 | 组织每个候选的任务、余量、等待、时间轴等JSON结果并返回 |
| 全组检查外层 | 2.165 | 同机槽重叠检查及包装完整仿真结果；含结果深拷贝 |
| 仿真内部 | 1.480 | 推进PS/DPU事件，维护队列、等待和完成时刻 |
| 候选组织 | 1.460 | 记录检查结果、建立已批准候选及其报告 |
| 规划其他部分 | 0.709 | 排序、保底选择、升级相关和其余对象组织 |
| 预处理 | 0.288 | 字段验证、任务/模式表转换 |
| 倒推预算 | 0.161 | 根据尾任务义务求连续设备预算 |
| 初始诊断 | 0.143 | 路径和窗口需求证据 |

因此，当前不能把这批开销归结为“倒推公式太复杂”或“诊断算法算不动”。大量CPU工作发生在结果组织和复制上。表中的检查外层还包括必要的同机重叠判断，不能把整个2.165 ms全部当无用工作。

线程CPU时间与墙钟几乎相同，也支持独立回放中CPU计算占主导；这个结论不排除真实并发运行中另有锁等待、分配器争用或操作系统长尾。

## 4. 做了什么修改

分两次验证：

1. 将`simulate()`已构造好的7个报告容器移入返回结果，避免再次完整复制；ARM均值8.533→6.988 ms。
2. 同样减少`evaluate_impl()`包装forecast，以及批准候选包装jobs/forecast时的复制；最终均值8.533→4.473 ms。

原来的直观过程类似“报告写好→整份复制到检查结果→再整份复制到批准方案”；现在把已经完成、后面不再使用的对象直接交给下一层。

保留全部报告字段、候选预算、模式选择、模拟事件、期限、补更及全组检查。没有关闭版本守卫、减少检查数量、裁剪输入或改变物理资格。

最小可复用补丁在 [report_moves.patch](../../../controller_architecture_study/ps_planner_repair/report_moves.patch)，以原冻结`scheduler.cpp`为基准。实际验证的优化源码在[本轮payload](../../../controller_architecture_study/results/ps_planner_profile_20261116_004/payload/move_baseline/scheduler.cpp)。当前代码保留为独立优化版本，不冒称已用于真实控制。

| --- | ---: | ---: | ---: | ---: |
| 原始无探针 | 8.533 | 9.135 | 9.180 | 8.531 |
| 原始阶段计时 | 8.806 | 9.482 | 9.546 | 8.803 |
| 优化无探针 | 4.473 | 4.785 | 4.877 | 4.473 |

探针版本的均值增加约0.20～0.27 ms，所以不能把探针耗时直接当实际部署成本，也不能给每个小函数无限增加时钟读取。P99按线性插值计算；本表最大值只是观测最大值，不是WCET。

两个keep案例单独看：

| 实际输入 | 原始平均/P99(ms) | 优化平均/P99(ms) |
| --- | ---: | ---: |

| 普通keep快照 | 2.988 / 3.173 | 1.657 / 1.846 |

普通keep尚未达到计划中P99约1 ms的初始目标；总体修复尚未达到约3 ms P99目标，但独立回放观测最大已低于5 ms。需要继续按真实可修改窗口评价，不能把部分目标达成写成全部问题解决。

## 7. 仍然缺什么

### 7.1 不能用离线结果解释完整24.987 ms长尾

同一异常快照在原始核心独立回放平均约3.95 ms，明显小于原实时记录24.987 ms。说明原记录除了核心自身成本，还可能有快照建模、并发分配/缓存、锁和调度环境影响。当前不能给这些原因分配百分比。

下一步应在独立的新控制版本中给快照等锁/锁内建模、规划、install等锁/检查、日志入队分别记录CPU/墙钟；先保持原策略验证探针，再考虑应用本补丁。本文没有宣称完整管理服务长尾消失。

### 7.2 提交活性尚未修复

原89条候选仍是历史context_changed拒绝，没有因离线回放而变成已安装。降低核心耗时可能增加提交机会，但其他任务仍可能在4 ms内推进，不能指望仅靠变快解除全局CAS限制。

随后实施有界“最新状态重验证未来变更”：保留实际在途任务、控制版本、较紧期限和补更，最多一次重验证，实际提交时再核对。这个机制与报告移动优化是两个独立修改，应分别验证和保留失败证据。
