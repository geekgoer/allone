## 一、最终目标与需要验证的命题

研究多条神经控制回路共享加速器时，能否通过可解释、低开销且经过明确检查的在线资源分配，在真实计算预算下获得更好的控制质量、安全表现或可支持回路数量。

候选核心问题是：**某条回路需要及时的新控制时，哪些计算资源可以在其控制有效期内真正转移过来，怎样调整才不会把其他回路推入失败？**

三个前提必须分别建立：

| 前提 | 要证明的事实 | 不成立时怎么办 |
|---|---|---|
| 控制器够用 | 现有DNN在至少一类合理任务中，低负载且及时执行时能重复完成 | 先调整任务范围；只有任务必须保留而仍做不到时，才考虑换教师/微调 |
| 存在值得利用的差异 | 真实可遇到的延迟、模型选择或执行顺序，会产生有意义的质量/恢复差异 | 调整基准或收窄主张，不强迫T、c、σ都重要 |
| 资源分配有作用 | 问题来自可调度的真实资源竞争，并且修改确实及时生效 | 先修执行链；不把主机故障当作FPGA算力不足 |

不要求静态一定撞门、动态一定全救回。也可以证明在相同控制质量/期限要求下支持更多回路，或在安全保持的同时减少资源使用。单纯“程序跑通”“平均J增加”“换了超网”不足以完成研究目标。

## 二、当前已知状态与暂时边界

- 当前实际可用闭环服务：`192.168.77.2:5238`，RC1模型11，237D输入、4维物理输出，tag `8a1f973e89710236`。保留现有归一化、权重与输入范围拒绝检查。
- 输出经校准转换后调用`moveByAngleRatesThrottleAsync`；是角速度设定＋油门，并非速度/位置导航，也非直接电机PWM。
- 当前c只有一个可用候选，σ是整任务排队，不能在DPU执行中随意抢占。板上DPU已实际运行，但整个控制热路径尚未运行在PS。
- 122次批次审计表明：4机有完整配对但尚无严格配对救回；高机数前端等待和输入拒绝突出。板端内部服务约1.32ms，不能据此认定12机已耗尽DPU容量。
- `calendar_coverage_passed`混合了运行错误与释放覆盖，比较资格需要拆开；经验成本长期累计阶段历史最大值，可能过于保守。这两点均为待修问题，不应依赖其原标记宣称安全或真实无解。

证据：[批次审计与研究复核](../../controller_architecture_study/docs/IP37批量实验发现与研究调整_20261108.md)，派生数据：`controller_architecture_study/results/ip37_campaign_analysis_20261108_v1/audit.json`。

本计划暂不做：全量18模型重训、超网重训、自定义PL/HLS加速器、RL决策、大维度状态表、外部物理扰动以及未辨明原因的大矩阵扫描。它们不是被永久排除，而是尚未成为当前最小问题的必要条件。

## 四、阶段0：先把基线和评价口径固定

**做什么**

1. 冻结模型11的身份、量化/归一化、输入输出单位、控制接口与初始条件；旧数据和失败记录不改。
2. 将“物理接触/余量失败”“模型输入拒绝”“飞行保护退出”“释放覆盖”“观察覆盖与时钟有效性”“期限违反”分别记录。完整观察到一个失败过程，可以计算失败代价；不能把它称为正常完成。
3. 统一T、R与真正命令间隔：T是计划释放间隔，R覆盖释放到命令提交返回的路径，命令间隔由相邻实际下发/ACK计算；RPC ACK仍是生效代理。不能用成功返回子集的R均值代表所有任务。
4. 保持统一评价频率与完整窗口，包括失败后真实状态；单独测评价线程对系统的额外负载。

**验收与交付**

少量离线重算和必要模拟集成能解释“为什么有效/无效”，不因一个输入拒绝就把释放覆盖自动标为失败。输出一个基线身份文件、指标说明和修正后审计；不为修改统计而自动补跑旧批次。

**范围**：这是后续实现任务，本次仅写计划；不默认已经修复。

## 五、阶段1：为旧DNN找到合理环境初筛范围

**目标**：先回答“当前控制器正常执行时能否完成”，而不是寻找静态失败案例。

**做什么**

1. 单机开始，继续真实板端DNN；Windows运行场景和现有控制前端。采用测得能正常交付的固定周期，如50ms；若该条件本身频繁丢弃，先回阶段0/2处理执行链，不能用它判定控制能力。
2. 复用已保存的平稳路线作正向参考，保留当前急弯失败路线作反向参考；身份/几何不一致时不能直接复用旧通过结论。
3. 优先改变转弯强度一个因素。建议首轮固定净宽3.0m，从原路线构造侧向/高度变化强度λ为1.0、0.7、0.4的同族候选。λ是待实现的场景参数，不是当前脚本已有选项。
4. 一个可行构造是对连续位置轨迹做固定仿射缩放，保留纵向时间推进，缩小侧向/高度偏移；同步重算速度、加速度、参考姿态及门的方向，并检查C2连续性与初始静止条件。不能只挪门却保留错误的参考。
5. 首轮每候选最多两次，总计最多6次实际飞行。必要时再加一个较宽净门宽（如3.8m）作能力参考，不无界交叉扫描所有宽度和强度。

**如何判断**

| 现象 | 阶段结论 |
|---|---|
| 及时执行仍反复碰撞/保护退出 | 任务可能超出控制器能力，降低强度或检查实现 |
| 通过且有合理余量、输入无拒绝、观察与时序可信 | 环境初筛候选，进入后续测量 |
| 都能过且质量近似 | 不立即丢弃；阶段4检查是否仍存在过程指标或实际延迟差异 |
| 因输入拒绝/执行链延迟失败 | 单列原因，不能直接宣称物理控制能力不足 |

**验收与交付**

至少一类低负载可重复完成的自然任务；场景参数、参考/门框审计、峰值误差、最小余量、命令间隔及范围检查均保存。初筛时可以调整环境；最终冻结后不得看着某策略失败轨迹再移动门框。

**条件分支**

如果适度任务已经可用，继续使用旧DNN。如果必须研究的任务始终做不到，才提出改教师并迁移一个代表性模型的任务。不能把“尚未找到调度收益”当作必须微调的理由。

## 六、阶段2：决定控制热路径放Windows还是板端PS

### 6.1 先明确：控制逻辑没有必须在板端的理论规定

Windows主机管理控制、远端DPU执行推理，是合法的分布式系统架构。只要按真实主机、网络、板端成本建模并验证，就可以研究调度；不能把它写成“全部运行于Zynq PS＋PL”。

迁移的理由应是消除已测得的关键等待、减少无关主机干扰、提高可测性，或满足最终嵌入式部署目标。**ARM CPU不保证比PC快，Linux也不自动提供所需硬实时保证。**

### 6.2 已有证据与收益判断

同3.0m、T120ms候选，4机采样到输入就绪均值约6.94ms，12机约104.94ms，板端内部服务均值都约1.32ms。因此热路径优化有较大潜力，但不能把104.94ms全当作可被迁移消除的时间。

尤其不能用这些均值直接相加或算响应时间占比：预处理统计含有后续被丢弃的任务，响应均值只含有命令返回的任务，两者样本集合不同。

只把平均不到1ms的规划模块搬到PS，而采样、参考构造和输入准备仍按原方式等待，未必能解决主要瓶颈。

### 6.3 比较范围，先小后大

| 方案 | Windows负责 | Zynq PS负责 | PL负责 | 当前状态 |
|---|---|---|---|---|
| A：现有路线B | Python控制前端、IO、准备与规划 | 现有推理服务及归一化等 | DPU推理 | 已实际使用，但高机数前端劣化 |
| B：优先尝试的轻量方案 | 原生IO＋必要热路径C++，同一启发式核心；Python只做实验与分析 | 保留现有服务 | 同一DPU | 旧路线A有部分可复用原生工作，路线B接入待做 |
| C：按收益决定的板端方案 | AirSim、场景、原生状态/命令桥接及离线分析 | 日历、输入准备、规划/队列、版本期限与推理服务 | 同一DPU | 尚未实现完整控制服务 |

**推荐**：先做B的最小接入和测量。若其在目标规模已能可靠供给任务、主机等待不再主导，就继续在Windows快速迭代；若主要瓶颈仍是这条热路径，或最后必须声称嵌入式PS部署，再做C的最小链路。阶段2不要求先移植整个系统。

### 6.4 具体测什么、何时决定

1. 用相同历史状态/任务快照重放，比较A、B的准备、调度和完整请求路径；保持同一237D契约和同一板端模型。重放可测软件成本，不能直接推断闭环安全。
2. 若B仍无法满足目标，再让Ubuntu Agent测C的最小PS软件原型；先给出功能/数值一致性和成本，不先做完整多机飞行。
3. 选出的候选在1机、4机各做少量同条件闭环检查；只在前端仍正常时增加目标规模。若只有4机合格，不能宣称12机也合格。
4. 初轮闭环对照以2～4次为目标，不开展另一轮百次批量。记录CPU执行与等待、P99/最大值、丢弃、评价额外开销，并说明计时精度。经验最大值不等于WCET。

迁移决策不以“均值降低了”单独通过：还要看长尾、完整任务覆盖、数值契约、正常控制是否保持，以及剩余等待是否仍主导关键期限。

验收的时间预算从计划采用的最小周期/物理期限倒推，并预留网络、DPU和下发余量。不能为了PASS临时加大所有期限，也不先杜撰“迁移必快多少倍”。

### 6.5 Ubuntu是否每次都要参与，是否每次都要Vivado

- **开发位置**：算法和可移植C++核心可以在本工程编辑，Windows做逻辑/回放检查；Ubuntu沿用已验证工具链交叉编译、链接板端库、部署与测量。不能假设Windows编译的exe能直接在ARM Linux运行。
- **普通参数变化**：轨迹、门、周期候选、配置等优先放数据文件，通常传文件并重启应用即可；须保存版本和哈希。
- **PS应用逻辑变化**：需要重新编译/部署对应软件；若PL接口、DPU硬件与系统平台不变，通常不需要重新综合PL或生成bitstream。
- **PL结构/接口变化**：新增加速器、改变DMA/寄存器接口或抢占能力才涉及相应硬件构建，这是后续另一个阶段。
- **运行链路**：Windows可直接与板端通信，Ubuntu用于开发/部署，不必成为每条控制请求的转发中间节点。已有交付文档已经说明这一点。

共享核心的目标是复用同一套决策逻辑、输入和测试向量，平台只适配时钟/IO/线程接口，不开发两套不同算法。这个结构是设计目标，不能当作当前已移植成果。

### 6.6 若采用C，必须先固定的边界

Windows保留AirSim RPC桥接；PS若负责日历，则PS独占任务释放/期限决策，Windows不得再同时运行另一套控制日历。若把237D输入准备搬到PS，参考轨迹和门配置也要提供给PS；只把已构造好的237D传过去并没有消除Windows构造输入的成本。

协议必须带任务序号、状态/控制版本和时间语义，过时回复不能覆盖新控制。不同机器的单调时钟不能直接相减；可用同一端测完整往返并以ACK作保守代理，或另行核对同步误差。主机桥接和网络依然在端到端R内，不会因调度在PS就消失。

**阶段交付**：`placement_decision.md`记录选择B或C的原因、同输入测量、剩余瓶颈、开发代价和最终论文的平台范围。没有这个证据前，不宣布全量迁移。

## 七、阶段3：在选定执行链上复核并冻结环境

1. 使用阶段1的候选和选定部署方式，不再同时改控制器/参考/门。
2. 优先少量重复，确认通过不是一次偶然；保存原始接触与机体余量，两者分开。
3. 冻结开发场景及候选运行域，另留未参与环境选择的路线/种子用于最终复核。
4. 若执行链变化使原结论消失，回到阶段1解释原因；不把平台变化误算成调度收益。

**交付**：环境清单、场景文件/哈希、平台/模型身份、初态与工作范围。可以得到一条平稳、一条适度弯曲的最小任务族，不追求大量场景。

## 八、阶段4：固定模型，找真实可用的时间差异

**研究对象**：当前DNN不变，分开T、端到端R、真正命令间隔及信息年龄，不能把名义T当作已执行频率。

1. 从实测硬件、通信与队列记录确定可能的R范围；不得仅人为加100ms等待，就宣称FPGA调度必要。
2. 离线粗筛正常段/弯曲段的T与R组合，模型仅缩小实飞范围；保留不敏感和失败结果。
3. 如需找周期平台边界，可以按30/60/120/240/480ms等倍增诊断；这是标定，不是建议正式部署480ms。保持预测网格、参考和控制律含义清楚。
4. 正式比较尽量满足同模型下只改变一个因素，且遵守本研究的R<T资格。R≥T的区域标为不满足周期任务约束，不能混入可行控制配置。
5. 观察全过程误差、最小余量、接触、完整完成、实际命令间隔、期限和丢弃，不只看过门中心偏移。

**预算**：先模型粗筛，再选择约6～8次有信息量的实飞；不先搭整个大搜索器。初步差异与独立复核分开记录。

**分支决定**

| 结果 | 后续主张 |
|---|---|
| R或更新间隔明显影响表现，T在30～120ms平台 | T用于控制到达率，重点研究σ与新鲜度；不强迫短T改善安全 |
| 平稳段容忍较慢、弯曲段需要较及时 | 支持状态相关时序分配，再研究低开销决策 |
| 仅在不现实的大延迟/长周期下退化 | 尚未证明真实部署需要动态资源分配 |
| 合理时间区间均不敏感 | 收窄任务/论文主张或换有依据的基准；不靠调弱增益制造差异 |

不添加外部风或状态冲击作为本阶段前提。若未来研究鲁棒性，另行声明并单独设计。

## 九、阶段5：模型复杂度c是否值得进入决策

阶段4有了合适时间条件后，才接入第二个模型；不先把18个旧模型全部接进服务。

1. 选择两个共享教师/特征契约、确实能部署的模型，分别验证黄金输入、输入运行域、FP32/量化误差和实际板端服务。
2. 用尽量对齐的控制到达时刻比较其控制能力，避免把精度差异和延迟差异混合；再比较各自真实运行成本下的结果。
3. 小模型快、大模型慢不是充分条件；大模型必须在至少一类任务/状态有可复核的控制价值，不能为了占资源而选择又慢又差的受支配模型。
4. 旧5237双模型和RC1 5238的tag、量化包及范围不能混用。新增当前可用模型池需Ubuntu Agent按独立任务交付，不默认旧模型6已经适合本轮闭环。

**验收**：得到少量有效的能力—计算成本取舍；无取舍就固定c，继续研究σ/到达率是否有价值。不同模型能力不假设随复杂度单调。

**微调条件**：仅当有明确任务需求且现有模型族能力不足，或需要另一种已验证教师时启动；新标签、验证目标、优化器状态等另开任务。当前不默认换教师。

## 十、阶段6：围绕证据完成启发式，而不是增加模块

保留明确的A/B/C思路，使用阶段2得到的真实成本与平台范围：

| 瓶颈 | 有理由考虑的动作 |
|---|---|
| 下一次任务释放过晚 | 提前未来释放/调整T |
| 已就绪但排在不紧迫工作后 | 调整合法执行顺序σ |
| 关键窗口内实际计算需求过大 | 有资格时调整c、减少未来需求 |
| PS/桥接/输入准备拥塞 | 修正对应资源安排，不能只优化PL |

每个动作至少说明：何时生效、在目标期限之前能释放哪种资源、会影响哪些其他回路。不能把未来降低利用率当成当前旧工作已经消失。

用少量候选和显式全组检查完成决策，保留已发布任务、当前不可抢占执行、状态/保持控制版本与真实期限。普通DPU只有整任务边界；没有硬件支持就不添加模拟任意抢占。

第一版不引入新的黑盒评分器、RL或大状态表，不默认加入可选任务drop机制。既有超期丢弃仍记录违约；未来若允许丢弃可选更新，需要证明未放弃必须及时到达的控制，不能把drop当成硬期限PASS。

当前经验成本过保守与过期/无快照问题先单独修正，既记录完整决策服务开销，也区分执行与等待。若找不到可行修改，明确报告不可行；回退旧配置不是安全证明。

**理论目标**：在给定有效的物理时间预算、服务/通信界和平台模型下，给出提交修改所需的充分条件及有界算法开销。不把一次B复制给未知未来状态，不用有限试飞代替全局WCET/鲁棒安全证明，不在未证明时写“最优”。

**交付**：算法说明、工作/时间模型、可复现回放、关键反例、必要测试及与近邻方法的差异。已有状态调度和模式切换文献的覆盖不能忽略，漂亮公式本身不等于学术创新。

## 十一、阶段7：最后再扩大静态/动态实验

进入条件：环境可用、执行链可信、存在真实时间/能力差异、动态修改在回放和少量闭环中确实能按时生效。

1. 从4机开始，再7、10、12机逐级增加；每次确认瓶颈归属，不一次铺满所有组合。
2. 使用冻结的代表性任务族、同样模型池和硬件。对每个已知任务条件单独用相同搜索预算选择静态配置，冻结后新跑配对；不能让静态不知道测试路线而动态提前知道。
3. 先做不超过约24次的扩展试验，检查是否确有稳定方向，再决定最终统计规模；不预先启动另一轮216次扫描。
4. 基线至少有最佳找到静态、常规合法EDF/状态期限方法；T或c作为贡献时再加入相应单变量消融。需要比较无过渡工作检查的版本时，必须保留其失效而非偷偷删除旧工作。
5. 同时报告J、逐机质量、实际接触、机体余量、任务完成、范围拒绝、期限/丢弃、真实命令间隔、规划采用与对其他回路的损害。失败和观察无效不能静默删去。

J沿用工程的声明口径，不能把它称为原论文环境/参数的逐项复现。少数重复先报告配对原值，不提前宣称统计显著；连续控制采样点不是独立重复试验。

最终论文重点取决于证据，可以是相同质量下支持更多回路、在紧迫窗口减少失效，或以较少计算维持要求。没有必要证明所有静态都撞，也不能把平均J稍高自动等同于更安全。
